# /tdd-update spec — spec の遡及整備

## 目的

spec への反映の拍（tdd-feedback の成果物レビュー）が無かった間にアーカイブされたプランの分を、`docs/spec.md`（または `docs/spec/<context>.md`）に遡って起こす。
spec が無いリポジトリでは新しく作り、あるリポジトリでは既存の記述を保ちながら欠けた context・概念を補い、現状と食い違う記述を洗い出す。
レポジトリごとに実質一度きりの移行だが、**一括の機械処理ではない** — context ごとに素材を読み、提示 → 承認で進める。

先に必ず Read する:

| ファイル | 内容 |
|---------|------|
| `${CLAUDE_SKILL_DIR}/../tdd-feedback/subcmds/spec.md` | 何を・どの粒度で・どんな構成で書くか（毎周の反映と同じ規則。本手続きはこれを遡及の素材で回す） |
| `${CLAUDE_SKILL_DIR}/../tdd-run/norms/dialogue.md` | 対話規範 — 提示 → 承認の作法 |
| `${CLAUDE_SKILL_DIR}/../tdd-run/norms/vocabulary.md` | 語彙規範 — 語彙登録ルール（名前の無いものを書きたくなったときに使う） |

## 適用条件

- `docs/dictionary.json` に context と概念があり、`plans/archives/` にアーカイブ済みプランがある
- そのうえで、`docs/spec.md` も `docs/spec/` も無い、または在るがアーカイブされたプランの機能が書かれていない

辞書もアーカイブも無いリポジトリ（tdd-skills をこれから導入する）は適用外。spec は feedback の毎周の反映で前向きに育てる。

## 原則

1. **現在の姿だけを書く。** 再定義を経た振る舞いは最終形のみ。歴史はアーカイブと git が持ち、spec には書かない。
2. **正は各台帳。** 辞書に無い概念は書かない（書きたければ先に語彙登録ルールで登録する）。台帳に登記されていない行為は行為一覧に載せず、その周の findings で外れたまま終わった振る舞いは書かない。接続マップは実装の所在を確かめる材料であり、ソースパスを spec に写す理由にはならない。
3. **context 単位で進め、承認を得てから書く。** 一つの context の節を起こし、承認を得て書き、次へ進む。途中で止めて別セッションで続けてよい（context ごとに独立している）。
4. **既存の spec は捨てない。** 既存の記述で現状と食い違う箇所は削除せず、食い違いとして列挙してユーザーに諮る。

## 手順

**1. 現状の確認**

`<meta>` は skill.md の手順で確定済みとする。

```bash
ls <meta>/docs/spec.md <meta>/docs/spec/ 2>/dev/null
node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/dict-search.js" -a -s        # コンテキスト一覧と概念の1行サマリー
node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/acts-search.js" -a -s        # 登記済みの行為
ls <meta>/plans/archives/
```

spec が単一（`docs/spec.md`）か小分け（`docs/spec/`）かは現状に従う。どちらも無ければ一度だけユーザーに聞く（小分けなら context.dir ごとに1ファイル）。
既存の spec があれば見出しの一覧だけを取り、context との対応を掴む（全文は読まない）。

**構成の組み替え（既存 spec が context 単位でないとき）。** 見出しが機能別・画面別などで辞書の context と対応しないなら、遡及に入る前に組み替えを提示し、承認を得る:

- 既存の見出しを context にどう割り当てるか（対応が付かない見出しは保留として残し、捨てない）
- 単一のままにするか `docs/spec/<context.dir>.md` に小分けするか — context が複数あり、一つの context の記述が読み通せない量になるなら小分けを勧める

組み替えは移し替えであり、この時点で内容は書き換えない（現状との食い違いは手順3の提示に載せる）。

**2. context ごとに素材を集める**

一つの context を選び、次を集める:

- 辞書のその context の概念（`dict-search.js -d1 <概念名>` で関連を展開する）— 説明に使う語と、要素どうしの関係
- 台帳のその context の行為（`acts-search.js -f context=<dir>`）— 末尾の行為一覧と、機能の節で「何ができるか」を説明する材料
- 接続マップ `docs/map.json` のその context — 実装とテストの所在（内容の確認用）
- その context に属するアーカイブ済みプラン（アーカイブの problem.md の `**コンテキスト:**`、辞書のエントリの出どころ、台帳の `settled.project` から辿る）
  - problem.md の「障害・制約」「範囲外」「問題」 → 前提・不変量・制約（なぜを落として写す）
  - test-tree.md の root と中間ノードの連なり → 機能の節の説明（要素がどう噛み合って全体が成り立つか）
  - findings.md の利用仮説の照合 → 外れたまま終わった振る舞いを除外する。清算済みの限界は制約として書く
- 生きているコード・テスト — 設定キー・既定値・記法・永続化ファイルなど、インターフェースの列挙に必要な分だけ開く
- 既存 spec のその context の節（あれば）

**3. 節案を作り、提示する**

構成は毎周の反映と同じ（context の一文 → 機能ごとの節 → 末尾の「行為一覧」の節。節の単位は全体としての振る舞いで、装置ごとの節は作らない）。要素の目安（説明・インターフェース・規約と不変量・前提・制約と失敗時・具体例）に沿って必要なものだけ書く。

提示は次を含める:

- 節案（既存 spec があれば、その context の節に対する差分として）
- 書かなかったもの — 辞書に無い概念、台帳に無い行為、外れたまま終わった振る舞い — とその理由
- 既存 spec の記述で現状と食い違うと見えるもの（該当する場合）

提示はターンの最後のテキストで行い、承認はユーザーのテキスト返答から取る。

**4. 承認を得た分だけを書き、次の context へ**

承認されなかった箇所は書かない。食い違いの扱い（削除・改訂・保留）はユーザーの判断に従う。
辞書に無い概念をどうしても書く必要があると判断されたら、先に語彙登録ルールで登録し（表＋承認）、そのあとに書く。

**5. 完了報告**

- context ごとに書いた節
- 書かなかったもの（辞書に無い・台帳に無い・未清算）と、それが辞書や台帳の欠けを示していれば /tdd-refactor（診断）への入力として持ち帰る旨
- 既存 spec の食い違いで保留になったもの
- 手続き自体で困った点があれば列挙する — スキルリポジトリへの改善入力として持ち帰る

## 補足 — プロジェクト側の作業手順に spec の更新がある場合

プロジェクトの CLAUDE.md 等に「実装後に docs/spec.md を更新する」といった手順が残っていると、tdd-run の途中で清算前の仕様が書かれる。
spec の書き手は tdd-feedback の成果物レビューに一本化されたので、その手順は外すか「feedback が書く」に書き換えるようユーザーに案内する。
