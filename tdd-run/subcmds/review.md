# /tdd-run レビュー — ブラインド品質評価

実装の品質（理解容易性・拡張容易性・頑健性）を、実装文脈から切り離された視点で評価する。
合成の終了前に実行する（新規型・再節合型のどちらでも行う）。
ユーザーがコミット範囲を指定して単独で依頼することもできる。

評価は**サブエージェント**が行う。
サブエージェントはこのセッションの会話コンテキストを引き継がないため、ブラインドが規律ではなく構造として保証される。

## なぜブラインドか

このワークフローの内部資料（problem.md・辞書・test-tree.md）を知る読み手にとっての分かりやすさは、資料が補助輪として働くため、コードそのものの品質と区別できない。
「よい構造が構築された」ことの実質的なテストは、何も知らない読み手がコードだけから概念と設計を了解できるか、である。
だからレビュアーには対象コードと評価軸だけを渡す。

形式的一致（`@vocab`・`src` の対応）はここでは評価しない — それは合成の突合（lint）が担う衛生である。
効能と衛生を混ぜない。

## 評価軸

問い方は工程の型で変わるが、評価軸は共通である:

- **理解容易性** — 初見の読み手が、コードから概念と設計のあらましを了解し、実装を辿れるか
- **拡張容易性（作業の着手しやすさ）** — 次の変更をどこに入れればよいかが見えるか
- **頑健性** — 誤用・境界・失敗に対して壊れにくいか
- **匿名の処理** — 名前を持たず、振る舞いとして個別に検査されない処理がどれだけあるか。多いほど複雑性は高いが、妥当な場合もある（局所的なヘルパー等）— 量と代表例を挙げ、正当かどうかの判断を添えさせる
- **処理の散在** — 同じ処理をするコードが複数箇所に散在していないか。常に共通化すべきとは限らない — 偶然の一致か本質的な重複かの判断を添えさせる

## 手順

### 1. 対象範囲の確定

このセッション（または指定されたコミット範囲）で作られた変更を `git log` / `git diff` で確定する。

工程の型は `test-tree.md` の最新セクションの見出しから読む（[ツリー規範](../norms/tree.md)の台帳規約）。
単独起動で型が読めない場合はユーザーに問う。

### 2. サブエージェントの起動

サブエージェント（Task ツール）に、次の内容だけを渡す。
**problem.md・辞書・test-tree.md など plans/ 以下の資料への言及・参照をプロンプトに含めない。**

**再節合型（比較評価）:**

```
あなたはコードレビュアーです。対象リポジトリ: <work_repo_abs>

<コミット範囲> はリファクタリングです。
この変更によって次の観点の品質が上がったか下がったかを、コード・テスト・diff を読んで評価してください。

- 理解容易性: 初見の読み手が、コードから概念と設計のあらましを了解し、実装を辿れるか
- 拡張容易性（作業の着手しやすさ）: 次の変更をどこに入れればよいかが見えるか
- 頑健性: 誤用・境界・失敗に対して壊れにくいか
- 匿名の処理: 名前を持たず、振る舞いとして個別に検査されない処理がどれだけあるか。量と代表例を挙げ、それが正当かどうかの判断を添えてください
- 処理の散在: 同じ処理をするコードが複数箇所に散在していないか。偶然の一致か本質的な重複かの判断を添えてください

よくなった点だけでなく、**悪くなった点・新たに生まれたリスク・やり残し**を必ず挙げてください。
評価の根拠は具体的なファイル・関数を指して示してください。
リポジトリ内の設計資料・計画資料・ドキュメント類は読まないでください — コード・テスト・diff だけを根拠にします。
結果を <出力先> に Markdown で書き出し、要約を報告してください。
```

**新規型（絶対評価）:**

```
あなたはコードレビュアーです。対象リポジトリ: <work_repo_abs>

<コミット範囲> で新しい機能が実装されました。
この実装の品質を、コード・テスト・diff を読んで評価してください。

- 理解が容易か: 初見の読み手が、コードから概念と設計のあらましを了解し、実装を辿れるか
- 拡張が容易か: 次の変更をどこに入れればよいかが見えるか
- ロバストか: 誤用・境界・失敗に対して壊れにくいか
- 匿名の処理: 名前を持たず、振る舞いとして個別に検査されない処理がどれだけあるか。量と代表例を挙げ、それが正当かどうかの判断を添えてください
- 処理の散在: 同じ処理をするコードが複数箇所に散在していないか。偶然の一致か本質的な重複かの判断を添えてください

**リスク・ネガティブな点**を必ず挙げてください。
評価の根拠は具体的なファイル・関数を指して示してください。
リポジトリ内の設計資料・計画資料・ドキュメント類は読まないでください — コード・テスト・diff だけを根拠にします。
結果を <出力先> に Markdown で書き出し、要約を報告してください。
```

`<出力先>` は `<plans_dir>/review.md`（絶対パスで渡す）。
サブエージェントは出力先のパスを知るだけで、plans/ の構造や他の資料の存在は知らない。

### 3. 結果の受け取りと実装者の判断

`<plans_dir>/review.md` が書かれたことを確認し、要点（評価の要約と、指摘されたリスク・ネガティブな点）をユーザーに報告する。

指摘ごとに、実装者としての判断（同意・部分同意・不同意）とその理由、対応方針を表で提示する:

| 指摘 | 判断 | 理由 | 対応方針 |
|---|---|---|---|
| <指摘の要約> | 同意 / 部分同意 / 不同意 | <理由> | 即時対応 / 対応不要 / 持ち越し |

対応方針は次の三つのいずれかである。

- **即時対応** — このセッションの残作業として対応できる規模の指摘（局所修繕）。提示のあと対応してから終了へ進む
- **対応不要** — スコープ外・的外れ・既存の設計判断と衝突する等の理由で対応しない。理由を表に明記する
- **持ち越し** — 指摘は妥当だがツリーの組み替えを要する等、このセッションの範囲を超える。observations に記録し、差し戻し先の判断は tdd-feedback に委ねる。構造的な問題はこのセッションで自律的に組み替えない — ユーザーが直接指示した場合のみ部分木再入の通常ルートを通る

表の提示と承認は[対話規範](../norms/dialogue.md)に従う（提示はそのターンの最後のテキストであること）。

再節合型の場合、この判断は利用仮説「構造の改善」の清算材料でもある。判断の結果に関わらず、仮説と食い違う指摘（改善が観測されない・劣化がある）は observations に記録する。
