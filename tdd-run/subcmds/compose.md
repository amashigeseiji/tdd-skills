# /tdd-run 合成 — ツリーを縫いつけて使える状態にする

確認済みのツリーを仮説として、依存を縫いつけていく。
分解が「この粒度・このインターフェースで要件は実現できる」という仮説であり、合成はその実験である。

## 入口条件

`plans/<project>/test-tree.md` が存在する（＝確認済みのツリーがある）。

冒頭で次を読む:

```bash
cat <plans_dir>/test-tree.md
```

**あわせて次の三つの規範を冒頭で読む**（リンク先の参照ではなく、実際にファイルを読む）:

- `../norms/vocabulary.md` — 辞書の読み書き作法、語彙登録ルール、不可逆性チェック
- `../norms/dialogue.md` — 提示 → 承認の作法
- `../norms/tree.md` — ツリー規範 — できるのツリーの記法・整形式、test-tree.md の台帳規約

いずれも合成の全体に及ぶ規範であり、「必要になった時点」を読む前に判断することはできない。
辞書検索のコマンドの形も語彙規範にある — 記憶から組み立てず、そこに書かれた形をそのまま使う。

**現在位置の導出:** テストスイートを一度実行し、その通過状態から現在位置を導出する。
進捗を別途記録することはしない — 初回ならすべて赤、再開なら途中から。

導出は**最新のツリーセクションのノード**に対して行う（テストファイルには過去フェーズの
`describe()` も蓄積しているため、過去フェーズの緑は現在位置の判定に含めない）。
ただし過去フェーズのテストが赤になっている場合は退行なので、そのまま進めずユーザーに報告する。

テストがすべて緑の場合、このセッションの仕事はルーティング時に読んだ findings の該当項目
（戻し先が `/tdd-run` のうち、ツリーに触らないもの）である。findings がないのに全緑なら、
行うべき仕事が見当たらないことをユーザーに告げて確認する。

**セクションの型による読み替え:**
最新のツリーセクションの見出しには工程の型が記録されている（[ツリー規範](../norms/tree.md)の台帳規約）。
**再節合型**のセクションでは、次のように読み替える:

- 装置ノードに添えられた**移設元**（ファイル・関数）が実装の出発点である — スタブに新規のロジックを書き起こすのではなく、移設元の断片を移して整える
- root・行為層は挙動保存の固定点である。挙動保存の検証（既存テスト・特性テスト・受け入れテスト）が赤になったら退行なので、そのまま進めずユーザーに報告する
- **基盤節**のノードの「緑」は、影響先として列挙されたすべての上位ノードが緑のままであることを含む
- ツリーの**残余**の宣言は完備性の約束である — 移設の過程で残余に無い断片が浮いたら、装置への帰属か残余への追加を提示する

---

## テスト作法

- **テストは「できる」を宣言する最小限に留める**（機械的に量産しない）
- **テストは実装をロードしてロジックを検証する** — テストファイル内に定義したローカル関数を
  検証するテストを書かない
- **実装を始める前に、ツリーの全ノードをスケルトンテストに書く**
- **ノードを省略する判断は、`it()` を書こうと試みたあとに行う**（書く前にスキップしない）

---

## 手順

### 1. 材料化 — 確定ツリーからの機械的導出

確定したツリーの名前から出発して、次の四つを作る。
**再開時、材料がすでにできているものはスキップする。**

**四つとも、対象は能力層（装置主語）ノードのみである。** 主語が `domain: "actor"` の登録済み
役割であるノード（root・行為層）は材料化しない — その対応物は受け入れテストと利用仮説である。

#### テストスケルトンを生成する

テストファイルは `tests/<dir>/` に置く（`<dir>` はツリーでそのノードに宣言された `[context]` ラベル）。
ツリーの各ノードに対応する `describe()` ブロックを、ネスト構造を保ったままテストファイルに書く。
未実装の `it` は `it.todo()`（ランナーに無ければ pending 扱いの `it.skip()`）で置く。
中身が空の `it('TODO', () => {})` は自明に合格し、実装漏れが「全緑」の報告に紛れる — 未実装は赤か pending として見えていなければならない。

`describe()` の主語には日本語のノード名をそのまま使う:

```javascript
describe('フロントマターテンプレートローダーは xxx できる', () => {
  describe('テンプレートマッチャーは aaa できる', () => {
    it.todo('TODO')
  })
  describe('フロントマター文字列ビルダーは bbb できる', () => {
    it.todo('TODO')
  })
})
```

この時点でツリーとテストファイルは1対1に対応する。
**スケルトンに現れていないノードのまま実装に進まない。**

#### スタブを生成する（scaffolding）

ツリーの各ノードについて `.claude/tdd/scaffold.sh` を呼ぶ:

```bash
.claude/tdd/scaffold.sh <Subject_en> <verb_en> <context>
```

- `Subject_en`: ノードの主語 S を辞書の `en:` フィールドから解決する — PascalCase の英語識別子
- `verb_en`: ノードの述語 V を英語 camelCase に直訳したもの
- `context`: ツリーで宣言された `[context]` ラベル

各ノードは独立したファイルに対応する。複数のノードが同じ S を共有する場合、スクリプトは
既存のファイルに関数を追記する。

`describe()` の日本語名と実装の英語識別子は互いに対応する — 概念の宣言（日本語）と
識別子の宣言（英語）は別のフェーズで起こる。
スタブが置かれていれば、実装フェーズで「どの関数に書くか」を決める必要がない。

スタブを作るとき、関数シグネチャの引数と戻り値に型を付ける（`@param`、`@returns`、
TypeScript の型注釈等）。
この段階ではプレースホルダでよい。引数の型が複雑な場合やデータ概念に対応する場合は、
型スタブに格上げする。

**スタブのパスを `src` に記録する。**
`scaffold.sh` がファイルを作成（または追記）した時点で、そのノードの実装ファイルは確定している。
発生源で書くこと。あとの突合に持ち越さない。

- **すでに辞書に登録されている概念**（分解で登録した概念 — 装置主語 root X、構造的仮登録の
  `ui` エントリ等）: `dict-write.js update` で
  `src` にスタブのファイルパスを設定する:
  ```bash
  node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/dict-write.js" update --to <plans_dir>/dictionary.json --name <概念名> <<'EOF'
  { "src": "src/<dir>/<file>.js" }
  EOF
  ```
- **まだ登録していない概念**（このあとの「solution ドメインの語彙を登録する」で登録するもの）:
  登録時のエントリに `src` を含める

複数のノードが同じファイルに追記される場合、`src` は同一パスでよい。

#### 型スタブを生成する

データ概念に対応する辞書エントリについて、型定義を生成する。

データ概念の基準:

- 定義が属性・構造を述べている: 「〜を持つもの」「〜の集まり」「〜の状態」
- ツリーの主語 S としてではなく、他のノードの間で受け渡される引数・戻り値として現れる
- 複数のノードにまたがって同じ形で現れることが見込まれる

型名には辞書の `en:` フィールドを使い、言語の慣習に従って定義する。
フィールドはプレースホルダでよい。辞書エントリへのリンクとして `@vocab` を付ける。

装置の概念（ローダー、ビルダー等 — ツリーの主語 S として機能するもの）は関数・クラスになり、
型にはならないので除外する。

#### solution ドメインの語彙を登録する

ノード名のうち solution ドメインに対応するもの（装置・変換・操作の名前）を、
[語彙規範](../norms/vocabulary.md)の**語彙登録ルール**（表＋承認 — ツリー確認がカバーしたのは
名前と述語だけであり、定義と関係はカバーしていない）に従って提示し、
`dict-write.js` 経由で `plans/<project>/dictionary.json` に追加する（JSON を直接編集しない）:

```bash
node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/dict-write.js" add --to <plans_dir>/dictionary.json --discovered tdd-run <<'EOF'
[
  { "name": "<概念名>", "en": "<ConceptName>", "context": "<dir>", "domain": "solution",
    "definition": "...", "relations": [{ "type": "references", "target": "<概念名>", "note": "" }] }
]
EOF
```

`wip` フィールドは自動付与される。バリデーションエラーは書き込み全体を拒否する —
入力を修正して再実行する。

除外するもの: root ノード、すでにアプリケーションドメイン語彙として登録済みの概念、
実装詳細の細分化。

### 2. 葉から上へ — red → green → refactor

葉ノードから始めて red → green → refactor を繰り返す。
緑になったら一つ上のノードへ移り、そこで合成する。

各ノードのテストを書く:

```javascript
describe('A は aaa できる', () => {
  it('xxx したとき yyy になる', () => {
    // 実装の前にインターフェースを定義する
  })
})
```

**実装への参照:**
`@vocab` と `@test` のアノテーションは材料化の scaffolding ですでに書かれている。
実装を埋めるときにこれらを削除・変更しない。

**テスト実行コマンド:**

```bash
npm test -- <test-file-path>   # または bun test <file> 等 — 検出されたものを使う
```

**型と関数シグネチャ:**
引数と戻り値に型を付けるのが基本姿勢である。型は関数どうしの関係からも、語彙どうしの関係からも生じる。

材料化で作った型スタブのフィールドは、実装が何であるべきかを明らかにした時点で確定させる。
あとの工程まで持ち越さない。

引数の型を書いていて次に気づいたら、名前付きの型として抽出する:

- 同じ引数の形が複数の関数に現れる
- インラインのオブジェクトが肥大した
- 材料化では型スタブを作らなかったが、実装を通じてデータ概念だと判明した

型を抽出したら、言語の慣習に従って定義する。そのうえで**その型が概念の名に値するか**を判断する — 定義が属性・構造として、ドメインまたは solution の語りに接地するか（材料化の「solution ドメインの語彙を登録する」の基準に照らす）。

**値する場合** — まず既存語彙を確認する:

```bash
node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/dict-search.js" -s <keyword> [<keyword2> ...] <plans_dir>
```

既存エントリがあれば、それを `@vocab` で参照する。実装を通じて定義が変わっていれば、定義の更新を提案する。
無ければ[語彙規範](../norms/vocabulary.md)の**語彙登録ルール**（表＋承認）に従って `dict-write.js add` で登録し、そのうえで `@vocab` を付ける。

**単なる構造上の便宜の型である場合**（局所的な引数まとめ等） — 登録せず、`@vocab` も付けない。`@vocab` は辞書エントリの存在を意味する注釈であり、宙づりにしない。

#### 実装オプションの評価

依存グラフから孤立したモジュール——合成に参加していないノード——のテストは**偽陰性**を生む。
実装が変わってもテストは通り続ける。

実装の選択肢が複数あるときは、次の四つで評価する:

- **テスト可能性** — モジュールとして独立に検証できるか
- **依存追跡可能性** — 依存グラフ上で依存を追跡できるか
- **偽陰性リスク**
- **変更コスト**

複数の基準で劣る選択肢は、実装の問題ではなく**設計の問題**として扱う。

#### 不通過時の診断規則

テストが通らないとき、**回数ではなく徴候で**何が起きているかを判定する。

| 徴候 | 診断 | 対処 |
|---|---|---|
| テストを満たすには、インターフェースが提供していない情報や能力が必要 | **インターフェースの反証** | 当該ノードのインターフェースとテストを引き直す（局所修繕） |
| 実装が、どこにもテストのない設計判断を含んでいる | **隠れた子ノード** | 子を追加してテストを書く（局所修繕）。複数の葉が自明に潰れるなら過剰分解として統合する |

局所修繕は**合成の流れの一拍**として行う。再入ではない。
修繕後にテストを再実行すれば、現在位置は自動的に正しくなる。

#### 修繕がツリーに波及するとき

修繕が当該ノードの近傍を越え、**確認済みツリーの形（`test-tree.md`）に触れそうになったら、
自律的に再構築せず、徴候を提示して停止する。**

上位ノードの「できる」の性質が変わったことに気づいた場合も同じである。
まず `problem.md` と突合する — 新しい合成は `problem.md` の「できない」を解決するか。
そのうえで徴候と突合の結果をユーザーに提示する。

構造的変更は[分解の部分木再入口](./decompose.md#部分木再入口)を通る。これはユーザーの判断による。

### 3. root が緑になったことを確認する

分解の手順3と同じく、root の主語の型によって読み分ける。

**装置主語 root のフェーズ:** 合成が root に達したら、分解の手順3で置いた root テストが
緑になることを確認する。

**役割主語 root のフェーズ:** root のユニットテストは存在しない。
**能力層の全ノードが緑になった時点**をこの節目とする。
root の「できる」の最終検証は、手順6のユーザーストーリー実行（受け入れテスト）が担う。

緑になったら、ユーザーに確認を求める。
ユーザーが受け入れたら手順4へ進む。

### 4. 組み込み — 実際に使える状態にする

テストが緑になったところで止まらない。**実際に使える状態**まで持っていく。

#### 0. WIP 登録済みの確認

分解の**インターフェース確定**で書かれた構造的仮登録（`src: null` の `domain: "ui"` エントリ）が
あるかを先に確認する:

```bash
node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/dict-search.js" -s --filter domain=ui <plans_dir>
```

ここで見つかったエントリが、これから充填する対象になる。

#### 統合

- root モジュールが、分解の手順2で宣言したエントリーポイントから実際に参照されていることを確認する
- 変更をユーザーが触れるエントリーポイント（UI、CLI、エンドポイント等）に統合する
- 実アプリを動かして end-to-end の動作を確認する
- 統合に判断が要るが情報が足りない場合は、合理的なデフォルトで統合し findings に記録する

#### 意匠の完成

画面・ボタン・リストなど、ユーザーが直接触れる部品をエントリーポイントに組み込むたびに、
部品ごとに次を行う。**このエントリーポイントにユーザーが直接触れる部品がない場合、この手続き
全体をスキップする。**

1. **構造的仮登録の充填** — 手順0で見つけたエントリにその部品が対応するなら、`src` を充填する:
   ```bash
   node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/dict-write.js" update --to <plans_dir>/dictionary.json --name <概念名> <<'EOF'
   { "src": "src/<dir>/<file>.js" }
   EOF
   ```
   併せて `src` ファイルに `@vocab: <概念名>` を付ける（他ドメインと同じアノテーション規約）。
2. **再利用の確認** — 仮登録がない部品については、同じ・類似のシグニファイアがすでにないか検索する:
   ```bash
   node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/dict-search.js" -s --filter domain=ui <plans_dir>
   ```
   既存のもので足りるなら、新しく作らずそれを使う。
3. **トンマナの適用** — その部品の役割（破壊的操作・主要操作など）に対応する `design-token`
   エントリを検索する:
   ```bash
   node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/dict-search.js" -s --filter domain=design-token <plans_dir>
   ```
   該当するトークンがあれば、リテラルな色・px値を直接書く代わりにそれを参照する実装にする。
   適用したら `relations: references` で繋ぐ。
   **該当するトークンがヒットしない場合、その役割と部品を findings に記録する。**
   トークンの登録自体は `/tdd-vocab` の仕事であり、ここでは行わない。
4. **命名・登録** — 仮登録も再利用もできない新規の部品だけを、実装と同時に
   [語彙規範](../norms/vocabulary.md)の**語彙登録ルール**（表＋承認）に従って `domain: "ui"`
   として登録する。エントリの形・登録の基準・`states`・`affordances` の扱いは
   [分解のインターフェース確定](./decompose.md#インターフェース確定の契機)に従う。
5. **UIパターン照合** — このエントリーポイントに複数の `ui` エントリが蓄積したら、
   [構造パターン照合手続き](../norms/pattern-matching.md)を domain=`ui-pattern` で実行し、
   master-detail 等の構造的再利用がないか確認する（例: 単一概念の複数インスタンスを列挙する
   `ui` エントリと、その単一インスタンスを表示する `ui` エントリが揃っている）。

### 5. 突合（暫定）

> **暫定的な手順である。** `@vocab` / `describe()` / 実装名 / `src` の対応検査は lint として機械化する予定であり、**lint の整備が済んだらこの節は削除する**。
> 現時点で機械化されているのは下記スクリプトの範囲まで（`describe()` の主語と型定義は目視のまま）。
> 材料化と組み込みの時点で規約を守っていれば、人手の突合は不要になる想定。

語彙・テスト・実装・型の対応を確認する。
対応表を手で作る前に、機械的に出せる分をスクリプトから取る（プロジェクトルートで実行する）:

```bash
# 接続マップ（語彙 → 実装 → テストの繋がっている側）。src-dirs 省略で config.json の vocab_scan.roots
node "$(realpath "${CLAUDE_SKILL_DIR}")/../tdd-vocab/scripts/generate-map.js" [src-dirs]
# 整合性チェック（壊れ・欠けの側）。test-dir 省略で tests/
node "$(realpath "${CLAUDE_SKILL_DIR}")/../tdd-vocab/scripts/check-vocab.js" [test-dir]
```

これは `/tdd-vocab check` の「実装・テストとの整合性」の部分だけを取り出したものである。
**辞書ネットワーク全体の監査（孤立概念・重複・矛盾・wip の再定義フラグ）はここでは行わない** —
合成の途中で wip エントリが未完なのは正常であり、突合が問うのは今回実装したノードの対応だけである。

**指摘の読み方は [`/tdd-vocab check`](../../tdd-vocab/subcmds/check.md) に従う。**
そのうえで、このセッションの範囲に絞って対処する:

- `[リンク切れ]` `[ファイル不在]`（エラー） — 材料化・組み込みで書いた `@vocab` / `@test` の食い違い。その場で直す。
- `[src不在]` `[src不一致]` — 材料化で記録した `src` が、その後のリネーム・分割に追随していない。実装を正しい名前に直すか、`dict-write.js update` で `src` を直す。
- `[src未注釈]` — 材料化で `src` を記録したのに、その概念の `@vocab` を実装側に書いていない。スタブに `@vocab` を書くか、`src` の指し先を実装本体に直す。
- `[未実装]` — 今回実装したノードのものだけを `@vocab` の付け忘れとして直す。**触っていない概念のものは扱わない。**

スクリプトが見ない対応（`describe()` の主語がノード名と一致しているか、型定義の有無）は
接続マップを下敷きに目視で確認する:

```
語彙（plans/dictionary）  | テスト describe()  | 実装（関数・モジュール名）| 型定義
--------------------------|-------------------|--------------------------|-------
ツリービルダー             | なし               | buildTree()              | なし（装置）
ネスト変換                 | ✓                 | buildTree() 内部         | なし
ツリーレンダラー           | ✓                 | renderTreeHtml()         | なし（装置）
記事                      | -                 | -                        | Article（型定義あり）
```

対応が取れていない行があれば、実装を正しい名前に直すか、`dict-write.js update` で辞書を直す。
どちらとも判断できない場合は findings に記録する。

**ツーリングの注記（依存グラフ検査）:** `.claude/tdd/config.json` に `depgraph.regen` があれば、
グラフを一度再生成して2つの検査をかけられる — 孤立ノード検査（実装したファイルが
`entry_points` から到達可能か。到達不能なら偽陰性リスクとして findings に記録 —
孤立したモジュールのテストは実装が変わっても通り続ける）と、
配線検査（`ui` エントリの `src` から `references`/`contains` の対象の `src` が到達可能か）。
**どちらも `depgraph-search.js` を通す**（`dependency-graph.json` を直接読まない）:

```bash
# 孤立ノード検査 — 結果が entry_points のいずれかに一致するか
node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/depgraph-search.js" --from -d 999 -s <depgraph.graph> <file>
# 配線検査 — 対象の src が結果に現れるか
node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/depgraph-search.js" --to -d 999 -s <depgraph.graph> <ui エントリの src>
```

`depgraph.regen` がなければこの注記全体をスキップし、検査を行わなかったことを findings に
記録する（`/tdd-scaffold depgraph` がオプトインの設定手順）。詳細は lint 化の際に機械化する。

### 6. ユーザーストーリー実行

`/tdd-userstory run <project>` を実行する。
`plans/<project>/user-story.md` がなければスキップする。

**結果ごとの対応:**

| 結果 | 対応 |
|--------|--------|
| `pass` / `pending` | 終了へ進む |
| `fail`（アサーション失敗） | 失敗の詳細を findings.md に記録して終了へ進む（下記参照） |
| `execution-error` | エラー対応ループへ入る（下記参照） |

**`execution-error` のとき — 対応ループ（最大3回）:**

1. エラーを分析し、対応を検討する
2. 分析と対応をユーザーに提示し、実装の前に承認を得る
3. `/tdd-userstory run <project>` を再実行する
4. `execution-error` が続く場合、1〜3を繰り返す（最大3回）

3回試みても `execution-error` が解消しない場合:

```
⚠️ ユーザーストーリーテストを3回試みましたが実行できませんでした。

エラー種別: <種別>
最後のエラー: <エラーメッセージ>
試みた対応策:
  1回目: <対応内容>
  2回目: <対応内容>
  3回目: <対応内容>

ユーザーストーリーテストをスキップして次のステップへ進みます。
```

これを findings.md に記録して終了へ進む。

**findings.md への記録:**

`fail` の場合: 失敗したシナリオ（US 番号、シナリオ名）、期待した出力と実際の出力、
どこへ差し戻すか（/tdd-problem か /tdd-run か）を書く。

`execution-error`（3回で打ち切り）の場合: エラー種別、最後のエラーメッセージ、
試みた3つの対応を書く。

### 7. ブラインド品質レビュー

同じディレクトリの [review.md](./review.md) を読み、実行する。
新規型・再節合型のどちらでも行う — 問い方は工程の型で変わる（review.md が定める）。
再節合型では、レビュー結果が利用仮説「構造の改善」の清算材料になる。
