# /tdd-run 再節合 — 固定した振る舞いの下で分解をやりなおす

リファクタリング問題の分解工程。分解（decompose）と対をなす。
リファクタリングとは語の成立からして**因数分解のやりなおし**である — 積（振る舞い）は変えず、因数への分け方（装置の構成）を変える。
積が同じであることはテストを通してしか観測できない。

成果物は decompose と同じ契約 — 承認済みの `plans/<project>/test-tree.md`（＋語彙作業＋受け入れの敷設）— であり、合成（compose）が両方を受ける。

## 入口条件

ルーティング（skill.md）で `plans/<project>/diagnosis.md` が入口文書と判定されて入る（**再節合型** — root は**固定点**）。
diagnosis.md は /tdd-refactor（コードの診断）の成果物であり、何に問題があるか（軸の言葉）と発見の観察を運ぶ。
この工程はその診断を受けて、どう作り直すかを考察し、ツリーに落とす。

- **新規実行** — 手順0から始める
- **新フェーズ** — 既存の `test-tree.md` があっても、新しいスコープの再節合として入ってよい。手順0から始める
- **部分木再入** — feedback 等からの構造的修正。末尾の「部分木再入口」から始める

冒頭で次を読む:

```bash
cat <plans_dir>/diagnosis.md
```

**あわせて次の三つの規範を冒頭で読む**（リンク先の参照ではなく、実際にファイルを読む）:

- `../norms/vocabulary.md` — 辞書の読み書き作法、語彙登録ルール、不可逆性チェック
- `../norms/dialogue.md` — 提示 → 承認の作法
- `../norms/tree.md` — ツリー規範 — できるのツリーの記法・整形式、test-tree.md の台帳規約

いずれも再節合の全体に及ぶ規範であり、「必要になった時点」を読む前に判断することはできない。
辞書検索・書き込みのコマンドの形も語彙規範にある — 記憶から組み立てず、そこに書かれた形を使う。

`plans/<project>/dictionary.json` がなければ、ツリーを構築する前に `/tdd-vocab plan` を呼ぶ。

## この工程でのツリーの意味

記法・層の意味論・整形式は[ツリー規範](../norms/tree.md)が定める。
decompose との違いはツリーの意味にある:

- **root と行為層は固定点である。**
  既存の振る舞いからの**回収**であり、発明しない。リファクタリングの前後で不変。
  人間にとって、最終的な振る舞いが変わらなければ中間のコード群はどれだけ変わっても問題がない。
  **行為層が緑のままであること自体が挙動保存の確認になる。**
- **可変なのは能力層だけである。**
  固定した root から分解ツリーは**複数**導出できる。
  そのどれを選ぶか — 複数の案を検討し、自立する中間ノードを考慮し、全体を解す — これが再節合という操作の意味である。
- **問いは導出ではなく発掘である。**
  「できるためには何が必要か」（decompose の問い）を既存挙動に当てると「すでに全部できている」ため空転する。
  問うのは**「既存実装のどの断片が、どの名前の装置に属するか」**。
- **メタな解決条件はノードにしない。**
  「開発者が名前で発見できる」「辞書と実装が対応する」の類はリファクタリングの目標だが、ツリーのノードではない。
  ツリーは装置の再節合を書く。
  効能（構造の改善）は利用仮説として記録し、合成後のブラインドレビューで検証する。
  形式的一致（`@vocab`・`src` の対応）は合成の突合（lint）が担う衛生であり、そのどちらでもない。
- **作業主体を actor に仕立てない。**
  「コード保守者」のような開発者主語のノードは、上のメタがツリーに漏れ出した形である。
  root と行為層が既存挙動からの回収である限り、そこに発明の余地はなく、この圧力は発生しない。

## 手順

手順の並びは、一般的なリファクタリング操作の列 — 評価 → 発見 → 改善案 → 影響範囲調査 — に合わせている。
前半二つ（評価・発見）は診断 = /tdd-refactor が済ませており、diagnosis.md がその成果である。
この工程は改善案（再設計案の考察）から始め、影響範囲（触る範囲と回帰面）を確定し、挙動保存を敷いてから分解に入る。

### 0. 読み込みと診断の対応表

`diagnosis.md`（軸ごとの診断・発見の観察・復元テストのギャップ・「/tdd-run への申し送り」）・辞書・対象コード（診断のスコープ）を読む。

**diagnosis.md の各診断項目・申し送り項目を、この工程のどの手順で扱うかの対応表として提示する:**

```
| 診断・申し送り項目 | 扱う手順 |
|-------------------|---------|
| <軸ごとの診断の項目の要約> | 手順1（再設計案の考察の入力） |
| <発見の観察の項目の要約> | 手順6・7（装置への帰属・基盤節の候補） |
| <復元テストのギャップの要約> | 手順8（再定義・再配線の候補） |
| <申し送り項目の要約> | 手順5（ユーザーの再設計案 — 考察の候補の一つ） |
| <項目の要約> | 扱えない — 要相談 |
```

対応表は一項目ずつ処理しないと作れないため、診断項目の素通りが構造的にできない。
扱えない項目はその場で露呈する — ユーザーに諮る。

### 1. 再設計案の考察

診断（何に問題があるか）から、どう作り直すか（改善案）の候補を挙げる。
診断が根拠として指すファイル・関数のコードを読み、軸の悪さがどの構造から来ているかを確かめたうえで、再設計の方向を複数考察する。
申し送りに「ユーザーの再設計案」があれば、候補の一つとして並べる — 採用の決定ではない（決定は手順5の前提決定が担う）。

ここではまだ決定しない。
候補を、触る範囲（context・ファイル群）が見える粒度まで具体化する。

### 2. 触る範囲の確定

再設計案の候補が触る範囲（context・ファイル群）を確定し、ユーザーに提示する。
候補が複数残っている場合は広い側に合わせる — 回帰面の取りこぼしを防ぐ。

### 3. 回帰面の確定

触る範囲に支えを持つ行為の一覧 = 回帰面を、**台帳（`docs/acts.json`）から引くことを第一手にする**:

```bash
node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/acts-search.js" -f context=<dir>
```

- 触る範囲の context ごとに該当する行為を引く
- **越境分を依存グラフの境界の辺で広げる** — 触る範囲に依存している外部（外から入ってくる依存）を列挙し、その先の行為も回帰面に加える。diagnosis.md が境界の辺を列挙していればそれを出発点にし、依存グラフで現状を確認する:

```bash
node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/depgraph-search.js" --to -d 999 -s <depgraph.graph> <触る範囲のファイル>
```

引いた行為一覧（actor・claim・witness）が **root と行為層の固定点**になる。
役割主語のまま置き、発明しない。
**複数 root を同時に固定してよい** — 基盤の導入（手順7）が複数の root を一括で解決することがしばしばあるためである。
台帳は entry point を持たないため、Entry point 宣言（「この行為が系に入る場所」）はコードから確認して各 root に添える:

```
Entry point: <entry-point-file> → <root の行為>
```

**被覆確認の問いは「台帳との差分は何か」** — 台帳にあるのにコードから読めない行為、コードにあるのに台帳にない行為。
コードと UI の読解は、台帳に無いものの穴埋めに縮小する。

- **台帳にあるのにコードから読めない行為** → ユーザーに提示し、回帰面に含めるかを確定する
- **コードにあるのに台帳にない行為** → 回帰面に加えたうえで、**findings に「未登記挙動」として記録する**。登記はここでは行わない — 拍は feedback（成果物レビュー）、判定は遡及の規則（`/tdd-update acts` の登記判定）に従う

**actor が辞書に無い場合**（穴埋めで回収した行為）: 作業主体（開発者）を actor に仕立てるのではなく、既存エントリーポイントの利用者から回収して立てる。
判定の目安: **リファクタリング完了後も、その主体はアプリを使い続けるか。**
使い続けるなら actor として語彙登録ルール（表＋承認）で登録する。
作業とともに消えるなら actor ではない — それは効能の話であり、利用仮説の側に置く。

被覆確認の承認は単独では求めず、手順9のツリー確認が root を頂点として含めて行う。

**フォールバック: 台帳が空・未整備のプロジェクトでは、従来のやり方に従う** — 回帰面は既存エントリーポイントとコード・UI の読解から行為を回収し、挙動保存（手順4）は特性テストで敷く。

### 4. 挙動保存の敷設

挙動保存はテストを通してしか観測できない。
分解をやりなおす前に、等号を確かめる手段を敷く。

- **witness のテストを走らせることを第一手にする** — 回帰面の各行為の witness（`witness.acceptance` が指すテスト）を実行し、緑を確認する。赤ならリファクタリング以前に退行が起きている — 進めずユーザーに報告する
- **特性テストは、台帳に目撃者がいない挙動にだけ書く** — 穴埋めで回収した行為・witness の無い挙動に、現状の振る舞いをそのまま固定するテスト（または受け入れスケルトン）を置く。回収した行為が検証できる粒度でよい

受け入れの対象は**挙動保存のみ**である。
辞書↔実装の対応を主張するメタなテストは書かない（「この工程でのツリーの意味」を参照）。

### 5. 前提決定

能力層の構造を分ける選択肢があれば、分解に入る前に明示する。
コードには素数がない — 挙動の一意な原子的分解は存在しないため、因数分解のやりなおしには常に実質的な選択がある。
手順1で挙げた再設計案の候補は、ここで並べて決定する。
申し送りの「ユーザーの再設計案」も他案と並べて検討する — 申し送りに載っていることは採用の決定ではない。

判定は decompose のインターフェース確定と同型: 両案について分解を一段だけ描き、**子ノードの集合（既存断片の帰属）が変わるか**を見る。
変わるなら実質的な選択であり、ユーザーに提示して決定する。
**採らなかった案と理由を一行、test-tree.md に残す。**

### 6. 能力層の発掘

問いは「**既存実装のどの断片が、どの名前の装置に属するか**」。

- **各装置ノードに移設元（ファイル・関数）を添える** — ツリーがそのまま作業対象の特定になる
- 装置に割り当てられない残りは**残余として宣言する**（例: 「main.js には DOM 配線と描画関数のみ残す」）
- **完備性条件:** 対象範囲の全断片が「どこかの装置へ移る」か「宣言された残余」かのいずれかになる。分解の漏れがツリー承認の時点で見える

diagnosis.md の「発見の観察」（同じ形が複数箇所に現れている）に挙がった断片は、ここで装置への帰属を検討する — 名前を与えて括り出すのは診断ではなく本工程の仕事である。

装置の命名では、まず既存語彙で表現できないかを確認する（語彙規範の既存語彙の確認）。
既存エントリの定義が実装の実体とずれている場合、それは新しい名前を作る理由ではなく**再定義の候補**である（手順8で扱う）。

### 7. 基盤節

複数の行為ノード（root を含む）から共有される装置は、木の中に無理に位置づけず、**木の外の基盤節**として置いてよい。

基盤節では辺の意味が逆向きである。
decompose のツリーでは辺は上から下への導出だが、基盤は「共通のノードを構築したら複数の上位ノードに影響がある」— 下から上への遡及である。
どの root を分解しても基盤（ログ機構の類）は析出されない。
散らばった断片への気づきから構築され、構築されて初めて複数 root に効く。
代数の言葉で言えば**共通因数のくくり出し**（ab + ac = a(b+c)）であり、複数の項に現れる断片を一度だけくくり出す操作である。

- **発見基準:** 発掘中に**同じ断片が複数の枝から出てきたら基盤候補の徴候**である（例: 多数のハンドラに散った画面再描画の手動呼び出し → 画面反映器に凝集）。diagnosis.md の「発見の観察」の複数 context・複数の枝にまたがる項目も同じ徴候である
- **基盤ノードには影響先の上位ノードの列挙を添える**（装置ノードに移設元を添えることの逆向き対応物）。これで基盤の挙動保存が機械的に述べられる — 「影響先として列挙されたすべての上位が緑のまま」。共有が広いほど回帰面が広いことがツリーから読める

### 8. 語彙作業

新規登録に加えて、**既存エントリの再定義・再配線**を扱う。
diagnosis.md の復元テストのギャップ（辞書・台帳の陳腐化に帰属された項目）と申し送りの語彙の種から、再定義・再配線の候補を取る。
語彙登録ルールと同じ表＋承認の作法で提示する（新規と再定義を同じ表に並べ、再定義は現行定義と案を併記する）。

**登録するのはソフトウェアを語る概念のみ。**
リファクタリング作業自体を語るメタ概念は登録しない。
判定の目安: **リファクタリング完了後もその概念は残るか。**
（「状態管理の外部化」は作業が終われば消える語。「アプリ状態ストア」は残る語。）

**この時点では `src` を指定しない。**
移設先のファイルは合成の材料化で `scaffold.sh` が生成するため、この手順の時点ではまだ存在しない。
`src` を指した状態で `dict-write.js add` を実行すると、ファイル不在でエラーになる。
[分解の構造的仮登録](./decompose.md#インターフェース確定の契機)と同じ扱いで、`src` を持たせずに登録し、合成の材料化でスタブが生成されたあと `dict-write.js update` で埋める。

### 9. 確認の拍と出口ゲート

[ツリー規範](../norms/tree.md)の**整形式チェック**を通してから、ツリーをユーザーに提示し、確認を得る。
提示と承認の作法は[対話規範](../norms/dialogue.md)に従う。
この確認は root を頂点として含む — 被覆確認（手順3）もここで完了する。

**承認と同時に `plans/<project>/test-tree.md` に追記する。**
書式と台帳の規約は[ツリー規範](../norms/tree.md)に従う。
このセクションの型は**再節合型**である — 見出しを `## <スコープ>（YYYY-MM-DD・再節合型）` とし、次の節を加える:

````markdown
## <スコープ>（YYYY-MM-DD・再節合型）

### できるのツリー

<root（固定点）と行為層（固定点）、その下の能力層。各装置ノードに移設元（ファイル・関数）を添える>

### 基盤節

- <基盤装置ノード> — 影響先: <上位ノードの列挙> / 移設元: <ファイル・関数>

### 残余

- <装置へ移設しない断片の宣言>

### 前提決定

- 採用: <採った構造> / 不採用: <案> — <理由一行>

### 挙動保存

- <回帰面の行為一覧（act id）と witness、特性テストの所在と被覆>

### 利用仮説

- 退行なし: <挙動保存の検証がすべて緑のまま>
- 構造の改善: <理解容易性・拡張容易性・頑健性について、こうなるはず>（検証は合成後のブラインドレビュー）
- こうなったら外れ: ...
````

利用仮説は**「退行なし＋構造の改善」の形**を取る。
構造の改善はこの工程では検証できない — 仮説としてコミットし、清算は合成後のブラインドレビュー（compose のレビュー手順）と、その後の実使用（feedback）が担う。

**出口ゲート:**

- 手順4の挙動保存の敷設（witness の緑の確認、台帳に目撃者がいない挙動への特性テスト・受け入れスケルトンの配置）が済んでいることを確認する
- 手順0の対応表で「扱えない」とした診断・申し送り項目が残っていれば、扱いをユーザーと確定する
- **再節合はツリー承認と上の確認が済んで終了する。**
  合成は同一セッションで続けてもよいし、セッションを改めてもよい（ルーターが `test-tree.md` を見て合成へ導く）。
  **どちらにするかをユーザーに確認する** — 「どちらでもよい」を暗黙の続行として扱わない

## 部分木再入口

feedback・レビュー等からの構造的修正の入り口。**全体のやり直しはしない。**

**契機:** ルーティング時に読まれた findings のうち、再節合型セクションのツリーに触る項目。
ユーザーが会話で直接構造的再入を指示した場合も同様にここから入る。

1. 影響を受けるノードを**すべて含む最小の部分木**を特定して開く
2. 手順5〜8を、その部分木のスコープで再実行する — 問いは発掘のまま。root・行為層は固定点であり、再入で動かさない。動かす必要に気づいた場合は挙動が変わっているということなので、中断して回帰面（台帳の該当行為一覧）と突合し、ユーザーに提示する
3. 手順9で差分を再確認し、`test-tree.md` を更新する

編集後は通常ルートで合成に合流する。
