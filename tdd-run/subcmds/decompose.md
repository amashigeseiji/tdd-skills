# /tdd-run 分解 — できるのツリーを立てる

要件を実現するための分解。作られるべきモジュールの**粒度**と**インターフェース**を決める。
成果物は `plans/<project>/test-tree.md`（確認済みのツリー）である。

## 入口条件

次のいずれかで入る。

- **新規実行** — `plans/<project>/test-tree.md` が存在しない。手順1から始める
- **新フェーズ** — `test-tree.md` が存在していても、新しいスコープ（次のユーザーストーリー等）の
  分解として入ってよい。手順1から始める。この場合、既存ツリーは前提知識として読む（既存装置の
  拡張の判断材料になる）が、編集対象ではない
- **部分木再入** — feedback 等からの構造的修正。末尾の「部分木再入口」から始める

冒頭で次を読む:

```bash
cat <plans_dir>/problem.md
cat <plans_dir>/user-story.md 2>/dev/null
```

`problem.md` がなければ、先に `/tdd-problem` で問題を定義する。
`plans/<project>/dictionary.json` がなければ、ツリーを構築する前に `/tdd-vocab plan` を呼ぶ
（[語彙規範](../norms/vocabulary.md)を参照）。

## できるのツリー

```
X は xxx ができる  ← root ノード（問題解決の仮説）
├── A は aaa ができる
│   ├── D は ddd ができる
│   └── E は eee ができる
└── B は bbb ができる
    └── C は ccc ができる
```

各ノードは「名前は〔挙動〕ができる」の形を取る。
**名前が先にあり、そのあとに何ができるかが続く。**
「X とは何か — xxx ができるもの」。ノードを置くとは、この問いに答えることである。

**ノード名は日本語で書く。**
日本語の概念名は、実装上の識別子（関数名・クラス名）がノード名に漏れ出すのを防ぐ。

**述語は挙動を述べるのであって、手段を述べるのではない。**

| NG | OK |
|----|-----|
| 展開状態マネージャーは localStorage でディレクトリの開閉を管理できる | 展開状態マネージャーはディレクトリの開閉状態を保持して管理できる |

述語に技術名（API、ライブラリ、ストレージ種別、プロトコル等）が現れたら、それは実装詳細が
ノードに漏れ出したシグナルである。

手段の選択はドライバー（テストコード）の責任である。
ノードが手段を先取りすると、ブラウザの外でインメモリに実装するという選択肢が消える。

> **前提:** この規則が成り立つのは、その行為が**可逆だと確認できている場合に限る**。
> 不可逆な行為では、どの手段を取ったかが系の状態の一部として残るため、手段と挙動を分離する
> 前提が崩れる。[語彙規範](../norms/vocabulary.md)の不可逆性チェックを参照。

**ツリーはテストファイルである。**
E のテストのコードを書いている間も、X の挙動を意識しているべきである —
これが近視眼的な実装を防ぐ。

ツリーは semi-lattice（複数の親を持つノードがある形）であってよい。
共有ノードは命名の機会である。

ツリーは理解が更新されるにつれて変わる。
ただし、**上位ノードの性質が変わったときは problem.md と突合する**
（合成側の「修繕がツリーに波及するとき」を参照）。

## 手順

### 1. 調査

既存システムを調査する。これは「最小限」で済ませる作業ではなく、**分解仮説の材料集め**として
積極的に行う。

対象は**辞書と実装の両方を並行して**調べる。辞書は改訂されながら運用されるため、
実装にのみ先例が残っていることがある。どちらか一方だけでは既存の解釈を取り逃す。

確認事項:

- **エントリーポイント** — この機能はどう到達されるか
- **既存の関連実装と、そこに現れている解釈 paradigm** — この領域を既存コードはどう解釈しているか
- **この問題は既存の配線済みモジュールの修正で解決できないか** — 新しいツリーを立てる前に問う
- **既存の型定義** — 重複と命名衝突を避けるため

### 2. root X を定義して名付ける

**スコープ:** 本スキルの一回の実行は**単一のエントリーポイント**を扱う。
`problem.md` が複数のエントリーポイントを要求している場合は、実行を分ける。

`problem.md` を読み、問う: **「この問題が解決されるためには、何ができるようになっている必要があるか」**

**`user-story.md` がある場合:** 各シナリオの Then 句（期待される結果）を並べる。
これらの Then がすべて成り立ったときに何が言えるか — その共通分母として root の「できる」が
浮かび上がる。Then 句から逆算して root を検証し、`problem.md` から出た答えと一致するか確認する。
一致しない場合、`problem.md` とユーザーストーリーのどちらかに見落としがないか検討する。

**まず既存の語彙で表現できないかを確認する**（[語彙規範](../norms/vocabulary.md)の
「既存語彙の確認」）。手順1の調査で**拡張可能な既存モジュールが見つかった場合、X はその既存概念とし、
新しい名前を作らない。**

新しい X を定義する場合:
「X は xxx ができるもの」という形で表現する。
名前は**日本語の概念名**にする（例: `フロントマターテンプレートローダー`）。
名付けたら、[語彙規範](../norms/vocabulary.md)の**語彙登録ルール**（表＋承認）に従って提示し、
`plans/<project>/dictionary.json` の entries 配列に追加する:

`{"name":"<概念名>","en":"EnglishName","context":"<context>","domain":"application","definition":"xxx ができるもの","relations":[],"src":null,"wip":{"status":"new","discovered":"tdd-run"}}`

root X が決まったら、手順1で特定したエントリーポイントと X の関係を宣言する:

```
Entry point: <entry-point-file> → X
```

エントリーポイントが決定できない場合、手順1に戻って調査を完了させる。

### 3. root テストを赤で置く

「X は xxx ができる」のテストを書く。
**このテストはツリーが完成するまで緑にしない。**

### 4. ツリーを分解する

「X が xxx できるためには何が必要か」を分解する。一行につき一ノード。
複数の挙動を「、」で連結して1ノードに詰め込まない — 分割できるなら子ノードに分ける
（詰め込むと挙動スロット自体が「〜できる」で終わり、テンプレートの「ができる」と衝突して
「〜できる ができる」のような冗語になる）。
直接実装できる粒度の葉に到達するまで続ける。

各ノードの命名と同時に、そのノードが属するコンテキスト（ドメイン境界）を `[context]` の形で宣言する:

```
X は xxx ができる [editor]
├── A は aaa ができる [editor]
└── B は bbb ができる [event]
```

コンテキストはそのノードが属するドメイン境界を表す — これはファイル組織の決定であると同時に、
「このモジュールの概念はどのドメインに属するか」という設計の宣言でもある。
コンテキストをまたぐ依存が生じたとき（親が `[editor]`、子が `[event]` 等）、その境界が
ドメイン理解の観点から適切かどうかを再検討する。

semi-lattice の共有ノード（複数のノードから参照されるもの）も独立したファイルとして扱う。
共有ノードのコンテキストが一つに定まらない場合 — 既存のどのコンテキストにも属さない場合 —
それは独自のドメイン境界の候補である。新しいコンテキストの定義を検討する。

分解の途中で、次の二つの契機が働く。

#### インターフェース確定の契機

分解の候補が複数あるとき、それが**同じサブ概念を異なるアルゴリズムで実現しているだけ**なのか、
**異なるドメインレベルのサブ概念そのものを要求している**のかを見分ける。

**判定:** 両方の候補について分解を一段だけ描き、**子ノードの集合が変わるか**を見る。
（ソートアルゴリズムの選択は子ノードの集合を変えない。開き戸か引き戸かは変える —
蝶番とラッチが要るか、レールと戸車が要るかが変わる。）

後者の場合、**決定しないまま分解を進めない。** 決定の順序は次のとおり:

1. 既存の解釈 paradigm の確認（辞書と実装を並行して調べる）
2. `problem.md` / `user-story.md`
3. 人間への確認

決定は**構造的仮登録**として辞書に記録する。`src: null`・wip ステータスのエントリに、
**インターフェースの形と関係のみ**を定義する（意匠 — 見た目、design-token、実装ファイル — は
ここでは書かない）:

```bash
node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/dict-write.js" add --to <plans_dir>/dictionary.json --discovered tdd-run <<'EOF'
{"name":"<概念名>","en":"<ConceptName>","context":"<dir>","domain":"ui","definition":"...",
 "relations":[{"type":"references","target":"<対象概念>","note":""}],"src":null}
EOF
```

登録は[語彙規範](../norms/vocabulary.md)の**語彙登録ルール**（表＋承認）に従う。
このエントリは合成の組み込み段階で `src` が充填され、design-token が適用されて完成する。
`test-tree.md` と並ぶ、分解から合成への第二の受け渡し成果物である。

**エントリの形:**
`relations: references` は概念への操作ハンドルとしての参照に使う（例: 削除ボタンが記事を参照す
る）。`relations: contains` はハンドルの合成に使う——複数の操作ハンドルが合成されてより大きな
操作ハンドルになる関係で（例: 入力ハンドルと送信ハンドルが合成されて投稿フォームになる）、器が
中身を保持する関係ではない。空間的な配置（左右・上下）は書かない。

**登録の基準**: エントリーポイントそのもの（画面・ページ等、合成の起点）は、できるツリーのroot X
と同じ理由——分解・合成の起点だから——で常に登録する。それ以外の中間の複合ハンドル（フォーム等）
は再利用可能性が基準になる。いまの文脈から切り離して他所でも使えるときに名付け、文脈固有で使い
回さないなら辞書には登録せず実装内の無名の構成のままでよい。

概念が特定の状態のときだけ意味をなす場合（例: 記事が公開中のときだけ表示される「非公開化」ボタ
ン）、その概念の辞書エントリに `states` フィールドがなければ状態の全集合を追加し、`relations[].note`
で該当状態を参照する（`ui`エントリ側に状態リストを複製しない）。

概念のどの操作を起動するかを明示したい場合（`references`だけでは「記事」を指すだけで、削除・編集
のどちらを起動するかが曖昧になる）、その概念の辞書エントリに `affordances` フィールドがなければ
操作の一覧を追加し、`relations[].note`で該当する操作を参照する（`ui`エントリ側に操作名を複製し
ない）。`affordances`はできるツリーの装置分割とは独立した、ドメイン言語としての操作一覧であり、
実際にどの装置が実現しているかは別途`src`/`@vocab`の機械チェックで追跡する（配線そのものの機械
チェックは合成の突合で行う）。

> 用語について: ここで扱っているのは**インターフェース確定**であって「UI」ではない。
> 「UI」というラベルは、UI → シグニファイア → 意匠 → 組み込み時、という連想の鎖によって
> 設計上の問題を組立工程に運んでしまう。辞書の `domain: "ui"` はツーリング上の語彙として
> そのまま使う。

#### パターン照合の契機

ツリーの形状を対象に、[構造パターン照合手続き](../norms/pattern-matching.md)を
domain=`pattern` で実行する。

### 5. 整形式チェック

ツリーを確定する前に、次の三つを通す。lint が存在する場合はそれを実行する。

#### 1. 技術語スキャン

すべてのノードの述語（「〜ができる」の部分）を走査し、次のカテゴリの語がないか確認する:

- URL、エンドポイント、HTTP メソッド
- ライブラリ名・フレームワーク名
- ストレージ種別（localStorage、DB、S3 等）
- 通信プロトコル、ファイル形式

見つかったら「この述語はどんな挙動を表しているのか」を問い直し、技術語を消してから
ツリーを確定する。

> **要件レベルの事実まで一緒に消さない。**
> 技術語をノードから除去するとき、その技術語に乗っていた要件レベルの事実まで道連れにしない。
> 「localStorage に保存できる」というノードから `localStorage` を消すとき、そこには
> 「リロードをまたいで状態が生き残る」という要件の事実が含まれていることがある。
> スキャンに従って技術語だけを消すと、この事実は行き場を失い、どこにも書かれないまま消滅する。
> その事実は**当該ノードの述語に残すか、別のノードに属させる**かであって、無に帰してはならない。
>
> なお、永続性の詳細を自由な手段として扱ってよいのは、**その行為が可逆だと確認できてから**である
> （[語彙規範](../norms/vocabulary.md)の不可逆性チェック）。

#### 2. scaffolding feasibility チェック

各ノードの主語が妥当な日本語の概念名になっているか確認する。
URL パス、技術的な操作の説明、camelCase の識別子が紛れ込んでいたら、名付けられる概念に
なるまで検討しなおす。

このチェックは、実装フェーズで起こる「テストが書けない」という判断の根本原因を、
起こる前に取り除く。

#### 3. loadability チェック

各ノードに割り当てられるモジュールが、テスト実行環境でロードできることを確認する。
次のものはロード不能とみなす:

- テスト環境で利用できないランタイム依存を直接参照している（ブラウザ API、GUI フレームワークの
  コンテキスト等）
- ロード時に副作用がある（イベントリスナーの登録、画面操作等）

ロード不能なノードがある場合、先へ進む前に次の2択を決める:

1. **ロジックを別モジュールに切り出す** — 純粋なロジックをテスト環境でロードできるモジュールへ移し、
   ツリーの context 宣言を変更する
2. **そのノードのユニットテストを書かない** — `it()` に「手動確認のみ」と明示してスキップする

「ロジックをテストファイルにコピーして検証する」は選択肢ではない。

### 6. 確認の拍 — ツリーを提示し、test-tree.md を書く

**ツリーをユーザーに提示し、確認を得てから先へ進む。**
提示と承認の作法は[対話規範](../norms/dialogue.md)に従う（提示はそのターンの最後のテキストであること）。

**承認と同時に `plans/<project>/test-tree.md` に追記する。**
draft 段階のツリーはファイルにしない — **`test-tree.md` の存在は常に「確認済み」を意味する。**

**`test-tree.md` は周回ごとにツリーを追記する台帳である。** 各ツリーセクションは作成日と
スコープの見出しを持つ（初回はファイル生成＝追記の初回）。「存在=確認済み」「部分木再入」の規約は
**最新のツリーセクション**に対して適用される。

ツリーの確定と同時に、このセッションが何を達成しようとしているのかの**利用仮説**を記録する。
利用仮説は「使ったらこうなるはず / こうなったら外れ」の形を取る — 実装の前にコミットする。

**`user-story.md` がある場合:** 各シナリオの Given/When/Then を材料にする。
一つのシナリオが「使ったらこうなるはず」の一項目に対応する。そのシナリオが失敗する条件が
「こうなったら外れ」になる。
**`user-story.md` がない場合:** `problem.md` の「解決されたと言える状態」を材料にする。

これはユーザーと共に書く。**新フェーズの場合、この節を既存ファイルの末尾に追記する**
（見出し以外の構成は初回と同じ）。

```markdown
# テストツリー: <プロジェクト名>

## <スコープ>（YYYY-MM-DD）

### できるのツリー

X は xxx ができる [context]
├── A は aaa ができる [context]
│   ├── D は ddd ができる [context]
│   └── E は eee ができる [context]
└── B は bbb ができる [context]

### 利用仮説

- 使ったらこうなるはず: ...
- こうなったら外れ: ...
```

**ここで分解は終了する。** 合成は同一セッションで続けてもよいし、セッションを改めてもよい
（ルーターが `test-tree.md` を見て合成へ導く）。

---

## 部分木再入口

feedback 等からの構造的修正の入り口。**全体のやり直しはしない。**

**契機:** ルーティング時に `findings.md` が読まれている場合、戻し先が `/tdd-run` の項目のうち
ツリーに触るものが再入の対象である（findings はルーティング時に読んでいるため、ここで再読は
しない）。ユーザーが会話で直接構造的再入を指示した場合も、同様にここから入る。

1. 影響を受けるノードを**すべて含む最小の部分木**を特定して開く
2. 上の手順4〜6を、その部分木のスコープで再実行する
3. 手順6では差分を再確認し、`test-tree.md` を更新する

編集後は通常ルートで合成に合流する。
