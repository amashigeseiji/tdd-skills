# 語彙規範

辞書（`plans/<project>/dictionary.json` および `docs/dictionary.json`）の読み書きに関する規範。
tdd-run の分解・合成の両方から参照される。

---

## 辞書の読み書き作法

辞書全体をロードしない。必要に応じて検索する:

```bash
# 概観スキャン（1エントリ1行 — トークンを節約する。キーワードは複数指定できる）
node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/dict-search.js" -s <keyword> [<keyword2> ...] <plans_dir>
# エントリ全文＋関連エントリ
node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/dict-search.js" -d1 <concept-name> <plans_dir>
```

`-s` は1行サマリーを返す。`-d1` は関連エントリも展開する。`plans/` 以下のエントリが `docs/` より優先される。
**`dictionary.json` を中身の確認のために `cat` しない。また直接編集しない** — 読みは `dict-search.js`
を、書きは `dict-write.js`（`add` / `update`）を通す。キーワード検索ではなく全件の概観が欲しいときは
`-a`（`--all`）を使う:

```bash
node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/dict-search.js" -a -s <plans_dir>
```

`dict-write.js` の使い方は各手順の書き込み箇所に示す。バリデーションエラーは書き込み全体を拒否する
— 入力を修正して再実行する。

## 作業仮説層としての plans/

**`plans/<project>/dictionary.json` が存在しない場合（新しい問題）:**
ツリーを構築する前に `/tdd-vocab plan` を呼ぶ。
この段階で定義される語彙は**作業仮説**である — `plans/<project>/dictionary.json` に書く
（`docs/dictionary.json` ではない）。
WIP の語彙は暫定的なガードレールとして働く。
実装と受け入れのあと、`/tdd-vocab promote` で安定層に昇格する。

**`docs/dictionary.json` を直接編集しない**（`/tdd-vocab promote` を通してのみ）。

## 既存語彙の確認

**新しい名前を作る前に、既存の語彙で表現できないかを必ず先に確認する。**

```bash
node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/dict-search.js" -s <keyword> [<keyword2> ...] <plans_dir>
```

既存の語彙で足りるなら、新しい名前を作らない。既存の概念を使う。

## 語彙登録ルール

**このスキルのすべての `dict-write.js add` に適用される。**

新しい概念を登録する前に、各概念の内容を表として**メッセージ本文に**提示し、ユーザーの承認を得る。
名前だけの列挙（「新規2件: 概念A, 概念B」）や、名前だけを選択肢にする形で承認を求めない:

```
| 概念名 | コンテキスト/ドメイン | 定義（案） | 関係 |
|--------|----------------------|------------|------|
| <name> | <context>/<domain> | <定義の案> | <他概念との関係> |
```

ユーザーが判断するのは名前の受け入れではなく、**定義の内容と語彙同士の関係**である。
この表を提示して承認を得たあとにのみ `dict-write.js` を実行する。

提示と承認のターンの取り方は[対話規範](./dialogue.md)に従う。

## 登録対象の基準

ユーザーがドメインについて語るときに使える概念 — root ノード、およびドメインの現実に接地している
と感じられる中間ノードが対象になる。
実装詳細の細分化（特定のアルゴリズム、一時的なヘルパー）は登録しない。

## 不可逆性チェック

概念の述語が**行為**であるとき、登録の前に問う:

**この行為を取り消したとき、系全体は取り消す前と区別不能な状態に戻るか。**

実用的な言い換え: この行為をイベントソーシングで実装したら、意味があるか。意味があるなら不可逆である。

不可逆な行為は、「何をしたか」の解釈が系に残り続ける。したがって述語をどう定義するかが後から
変更できない決定になる。**不可逆であると判定した場合、解釈を確定してから登録する。**
確定の順序は次のとおり:

1. 既存の解釈 paradigm（辞書と実装の先例）
2. `problem.md` / `user-story.md`
3. 人間への確認

**前提の明示:** [分解](../subcmds/decompose.md)の「述語は挙動を述べるのであって、手段を述べるのではない」が成り立つのは、
その行為が**可逆だと確認できている場合に限る**。不可逆な行為では、どの手段を取ったかが系の状態の
一部として残るため、手段と挙動を分離する前提が崩れる。上のチェックはこの前提を確認する手続きである。
