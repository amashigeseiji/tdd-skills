# ツリー規範 — できるのツリー

できるのツリーの記法・層の意味論・整形式チェック・`test-tree.md` の台帳規約。
tdd-run の分解（decompose）と再節合（refactor）の両方から参照される。
工程ごとに異なるもの — root の意味（仮説か固定点か）・分解の問い（導出か発掘か）・辺の意味（析出か遡及か）— はこの文書では定めず、各工程の文書が定める。

---

## 記法と層

```
X は xxx できる  ← root ノード
├── A は aaa できる
│   ├── D は ddd できる
│   └── E は eee できる
└── B は bbb できる
    └── C は ccc できる
```

各ノードは「<主語> は <可能形で終わる述語>」の形を取る。
**名前が先にあり、そのあとに何ができるかが続く。**
「X とは何か — xxx できるもの」。ノードを置くとは、この問いに答えることである。
ただし**この問いは装置主語ノードのものである。**
役割主語ノードは役割を定義しない — 登録済みの役割について、**何ができるべきかを主張する文**である。

**述語は可能形で終止する**（〜できる／〜られる／〜せる）。
受動形での終止（「〜表示される」）は取らない — 装置主語なら「〜示せる」のように直す。

**ノード名は日本語で書く。**
日本語の概念名は、実装上の識別子（関数名・クラス名）がノード名に漏れ出すのを防ぐ。

**ツリーは二つの層からなる。**
root は原則として**役割主語のユースケース**である（「作成者は xxx できる」）。
その下に役割主語の中間ノード（**行為層**）を立ててよい。
装置主語のノード（**能力層**）は行為層ノードの子として現れ、そこから下は装置のツリーである。

**層の意味論:** 役割主語の「できる」は**行為可能性**であり、受け入れテスト・手動確認で検証される。
装置主語の「できる」は**装置の能力**であり、ユニットテストで検証される。
親子関係は「**親は子の能力の使い手**」と読む。

**層の整合則:** 行為層ノード（役割主語）は、役割主語 root の下にのみ現れる。

行為層と能力層の**境界がインターフェースの線**である。

**述語は挙動を述べるのであって、手段を述べるのではない。**

| NG | OK |
|----|-----|
| 展開状態マネージャーは localStorage でディレクトリの開閉を管理できる | 展開状態マネージャーはディレクトリの開閉状態を保持して管理できる |

述語に技術名（API、ライブラリ、ストレージ種別、プロトコル等）が現れたら、それは実装詳細がノードに漏れ出したシグナルである。

手段の選択はドライバー（テストコード）の責任である。
ノードが手段を先取りすると、ブラウザの外でインメモリに実装するという選択肢が消える。

> **前提:** この規則が成り立つのは、その行為が**可逆だと確認できている場合に限る**。
> 不可逆な行為では、どの手段を取ったかが系の状態の一部として残るため、手段と挙動を分離する前提が崩れる。
> [語彙規範](./vocabulary.md)の不可逆性チェックを参照。

**ツリーはテストファイルである。**
E のテストのコードを書いている間も、X の挙動を意識しているべきである — これが近視眼的な実装を防ぐ。

ツリーは semi-lattice（複数の親を持つノードがある形）であってよい。
共有ノードは命名の機会である。

---

## コンテキスト宣言

各ノードの命名と同時に、そのノードが属するコンテキスト（ドメイン境界）を `[context]` の形で宣言する:

```
X は xxx できる [editor]
├── A は aaa できる [editor]
└── B は bbb できる [event]
```

コンテキストはそのノードが属するドメイン境界を表す — これはファイル組織の決定であると同時に、「このモジュールの概念はどのドメインに属するか」という設計の宣言でもある。
コンテキストをまたぐ依存が生じたとき（親が `[editor]`、子が `[event]` 等）、その境界がドメイン理解の観点から適切かどうかを再検討する。

semi-lattice の共有ノード（複数のノードから参照されるもの）も独立したファイルとして扱う。
共有ノードのコンテキストが一つに定まらない場合 — 既存のどのコンテキストにも属さない場合 — それは独自のドメイン境界の候補である。
新しいコンテキストの定義を検討する。

---

## ツリーは変わる

ツリーは理解が更新されるにつれて変わる。
ただし、**上位ノードの性質が変わったときは problem.md と突合する**（合成側の「修繕がツリーに波及するとき」を参照）。

## 整形式チェック

ツリーを確定する前に、次の三つを通す。lint が存在する場合はそれを実行する。

### 1. 技術語スキャン

すべてのノードの述語（主語の「は」に続く部分全体）を走査し、次のカテゴリの語がないか確認する:

- URL、エンドポイント、HTTP メソッド
- ライブラリ名・フレームワーク名
- ストレージ種別（localStorage、DB、S3 等）
- 通信プロトコル、ファイル形式

見つかったら「この述語はどんな挙動を表しているのか」を問い直し、技術語を消してからツリーを確定する。

> **要件レベルの事実まで一緒に消さない。**
> 技術語をノードから除去するとき、その技術語に乗っていた要件レベルの事実まで道連れにしない。
> 「localStorage に保存できる」というノードから `localStorage` を消すとき、そこには「リロードをまたいで状態が生き残る」という要件の事実が含まれていることがある。
> スキャンに従って技術語だけを消すと、この事実は行き場を失い、どこにも書かれないまま消滅する。
> その事実は**当該ノードの述語に残すか、別のノードに属させる**かであって、無に帰してはならない。
>
> なお、永続性の詳細を自由な手段として扱ってよいのは、**その行為が可逆だと確認できてから**である（[語彙規範](./vocabulary.md)の不可逆性チェック）。

### 2. scaffolding feasibility チェック

各ノードの主語が妥当な日本語の概念名になっているか確認する。
URL パス、技術的な操作の説明、camelCase の識別子が紛れ込んでいたら、名付けられる概念になるまで検討しなおす。

このチェックは、実装フェーズで起こる「テストが書けない」という判断の根本原因を、起こる前に取り除く。

### 3. loadability チェック

各ノードに割り当てられるモジュールが、テスト実行環境でロードできることを確認する。
次のものはロード不能とみなす:

- テスト環境で利用できないランタイム依存を直接参照している（ブラウザ API、GUI フレームワークのコンテキスト等）
- ロード時に副作用がある（イベントリスナーの登録、画面操作等）

ロード不能なノードがある場合、先へ進む前に次の2択を決める:

1. **ロジックを別モジュールに切り出す** — 純粋なロジックをテスト環境でロードできるモジュールへ移し、ツリーの context 宣言を変更する
2. **そのノードのユニットテストを書かない** — `it()` に「手動確認のみ」と明示してスキップする

「ロジックをテストファイルにコピーして検証する」は選択肢ではない。

## test-tree.md の台帳規約

`plans/<project>/test-tree.md` は**周回ごとにツリーを追記する台帳**である。
draft 段階のツリーはファイルにしない — **ファイルの存在は常に「確認済み」を意味する。**
「存在=確認済み」「部分木再入」の規約は**最新のツリーセクション**に対して適用される。

各ツリーセクションは、スコープ・作成日に加えて**工程の型**を見出しに持つ:

- `## <スコープ>（YYYY-MM-DD・新規型）` — decompose で作られたセクション（root は仮説）
- `## <スコープ>（YYYY-MM-DD・再節合型）` — refactor で作られたセクション（root は固定点）

型は、ルーティングの判定（提示 → 承認）で承認された結果の記録である。
合成・部分木再入・一周後の戻りは、この記録を読んで工程を選ぶ — **判定を再演しない。**

セクションの書式:

````markdown
## <スコープ>（YYYY-MM-DD・<型>）

### できるのツリー

X は xxx できる [context]
├── A は aaa できる [context]
│   ├── D は ddd できる [context]
│   └── E は eee できる [context]
└── B は bbb できる [context]

### 受け入れスケルトン

- 配置先: tests/acceptance/<project>.spec.ts

### 利用仮説

- 使ったらこうなるはず: ...
- こうなったら外れ: ...
````

利用仮説は「使ったらこうなるはず / こうなったら外れ」の形を取り、**実装の前にコミットする**。
ユーザーと共に書く。材料の取り方と型ごとの形は各工程の文書が定める。

再節合型のセクションは、これに**基盤節**・**残余**などの節を加える（形は再節合の文書が定める）。
