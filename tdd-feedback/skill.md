# /tdd-feedback - TDD利用フィードバックスキル

tdd-run が完了したら必ず起動する。**別セッションで動かす**（実装の文脈から離れるため）。

このセッションでは三つの役割を順に担い、最後にこのプランをクローズするか戻すかを判断する:

1. **利用インタビュー** — 実際に使ったユーザーから事実と印象を集める
2. **成果物レビュー** — 利用の事実に照らして語彙とソリューション構造を評価し、promote・行為の登記・spec への反映を行う
3. **クローズ判断** — findings をもとにプランを閉じるか、同一プランに戻すか、新規プランに移すかを決める

インタビューを最初に置くのは、先に成果物レビューをするとソリューションへの棲みつきを
再構築してしまい、「設計を擁護しない」「白紙で聞く」が守れなくなるため。
「使ったらどうだったか」が語彙昇格（promote）の入力になる。

ルーティング（どこに戻すか、どう閉じるか）はこのセッションで一本化する。tdd-run からは戻さない。

---

## 前提

1. **tdd-run が完了していること**（実装コード・テスト・observations.md が存在する）
2. **変更が利用可能な状態であること**（実アプリで動かせる）
3. 利用インタビューは**実際に使ってから**行う。未使用なら、インタビューを待つか「ウォークスルー」だと明示する

---

## 読み込み

まず3つのパス変数を1回で解決する:

```bash
bash "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/find-config.sh" <project>
```

出力の META が `<meta>`、WORK_REPO が `<work_repo_abs>`、PLANS_DIR が `<plans_dir>`。

- **WORK_REPO が `UNRESOLVED:<名前>` の場合**: 作業レポジトリが `<meta>` のサブディレクトリでも
  `.claude/tdd/config.local.json`（マシンごと・git 非追跡）の登録済みでもない。ユーザーに絶対パスを
  聞き、ディレクトリの存在を確認してから `<meta>/.claude/tdd/config.local.json` の `repos.<名前>` に
  保存し、find-config.sh を再実行する。**入口文書（problem.md・diagnosis.md）に絶対パスを書かない**（コミットされるため）
- **stderr に旧フィールド `**作業ディレクトリ:**` で解決した旨が出た場合**: 動作はするが、
  config.local.json への保存とフィールド削除（移行）を提案する

```bash
cat <plans_dir>/problem.md 2>/dev/null || cat <plans_dir>/diagnosis.md
cat <plans_dir>/test-tree.md 2>/dev/null
cat <plans_dir>/observations.md 2>/dev/null
```

入口文書はプランの型を示す — problem.md → 新規型、diagnosis.md → 再節合型（1プラン1入口文書）。

辞書は全量ロードせず、成果物レビュー中に必要な概念を検索する:

```bash
# 概観スキャン（1行サマリー、複数キーワード可）
node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/dict-search.js" -s <概念名> [<概念名2> ...] <plans_dir>
# 詳細確認（関連エントリも展開）
node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/dict-search.js" -d1 <概念名> <plans_dir>
```

plans/ 側のエントリが docs/ 側より優先される。

## 手順

### 1. 利用インタビュー

成果物レビューより先に行う。レビューを済ませてから聞くと、設計を擁護する立場で
インタビューに入ってしまう。

インタビュアーとしての立場（重要）:
- **設計を擁護しない** — 実装の文脈から離れ、白紙で聞く
- **誘導しない** —「良かったですか？」と聞かない。起きたことを聞く
- **ユーザーの代わりに解釈しない** — 印象をほどくのはユーザー本人。あなたは解像度を上げる質問をする

#### 1-1. 操作の事実を取る

印象の前に、何が行われたかを取る。
- どんな操作をしたか（入力・設定・出力の粒度で）
- 出力そのものを見せてもらう（可能なら）

利用仮説に「試してほしい操作」があれば、操作の事実は最初から分かっている。照合から入れる。

#### 1-2. 利用仮説を照合する

test-tree.md の利用仮説に対し、実際に起きたことはどちらだったか。
利用仮説が無い場合のフォールバックは入口文書のジャンルで分かれる: problem.md のプランでは problem.md の「解決したと言える状態」、diagnosis.md のプラン（再節合型）では test-tree.md の「退行なし＋構造の改善」の形の利用仮説（ツリー承認時に必ず書かれるため、無い場面は稀のはず）。
- 期待どおりか、外れ側か、どちらとも言えないか
- 利用仮説そのものが的外れだった（測る相手が違った）なら、それも記録

#### 1-3. 印象の解像度を上げる

粗い印象を、ユーザー自身の言葉でほどいてもらう。あなたは解釈せず、ほどけるように問う。

- **場所を特定**: 「全部？ 特定のもの？ 画面のどこを見てそう感じた？」
- **軸を複数差し出して選ばせる**: 「一個一個が大きい？ 詰まってる？ 大小がバラついてる？ どれが近い？（複数可）」
- **対比で引き出す**: 「どうなっていたら『ちょうどいい』だった？」
- **結果に接地**: 「その出力は、目的に使えそうだった？」

### 2. 成果物レビュー

利用インタビューで得た事実に照らして、語彙とソリューション構造をセットで評価し、
簡潔なレポートを作る。

**語彙の評価:**
- この概念群は問題に対するソリューションとして適切か。実際の利用で起きたこととずれていないか
- 概念間の関係は整合しているか。孤立した概念はないか
- ソリューションはもっと構造化できるか

**ソリューション構造の評価:**
- observations.md の気づきを確認する
- test-tree.md は**初期仮説の記録**として読む。現在のテストファイルの describe() 構造と
  比較し、差分（ツリーの組み換え）があればその原因を評価する。初期ツリーと最終ツリーの
  差分は「このプランで理解がどう動いたか」の記録になる

**レポート形式（簡潔に）:**

レポートを書く前に `${CLAUDE_SKILL_DIR}/../tdd-vocab/subcmds/promote.md` を Read し、手順1の機械的検証（`dict-write.js check`）を済ませておく。
語彙の欄には promote の表（手順1の形式）をそのまま入れる。

```
## 成果物レビュー

語彙（plans/<project>/dictionary.json）:
- （問題なし / 懸念点があれば記述）
<promote の表（概念名・区分・コンテキスト/ドメイン・定義・relations）。再定義は差分を添える>

ソリューション構造（test-tree.md と現在の describe() 構造の比較）:
- （問題なし / 差分とその原因、懸念点があれば記述）

観察メモ（observations.md）:
- （特記事項があれば記述）
```

**語彙の承認はこのレポートで一度だけ取る。** レポートは対話規範（`${CLAUDE_SKILL_DIR}/../tdd-run/norms/dialogue.md`）に従ってターンの最後のテキストとして出し、ユーザーのテキスト返答から昇格対象を確定する。
承認された概念は promote.md の手順2以降で昇格する。手順1の提示と承認はこのレポートで済んでいるので、重ねて提示しない。
問題があれば該当概念の promote を保留し、findings に記録する。

役割分担: このレビューは「昇格すべきか」の**判断**とその承認を担う。promote.md はこの経路では「機械的整合性」
（フォーマット・参照の整合・孤立リンクの検出、`dict-write.js check`）の**検証**と昇格の実行を担う。

**行為の登記（docs/acts.json）:**

promote の後に行う。台帳は「使用で清算された挙動主張の登記簿」であり、登記の拍は
**毎周の成果物レビュー**（クローズ時ではない）。B（同一プランへの戻し）に向かう周でも、
着地した行為は登記してよい。

先に `${CLAUDE_SKILL_DIR}/acts-format.json` を Read する（台帳の意味とエントリのフォーマット）。

登記する行為は**行為単位**で判定する。三つすべてを満たすものだけが候補になる:

- その周回の操作の事実（1-1）に現れている
- この周回の findings 素材（インタビュー・レビューで集めたもの）で、その行為に失敗・違和感が帰属されていない
- witness（受け入れテスト）が緑 — describe 内に実行されて pass するテストが1件以上あること。全テストが skip の describe は witness 無しとして扱う

利用仮説の照合（1-2）は変えない — 仮説は行為の集合より広く、照合結果は判断材料であって
登記の単位ではない。判定の確定は次の表＋承認が担う。claim の文言は承認で確定する。

新規の登記と既存の行為への witness 追加（下の「成立条件が広がっただけの周回」）は、**一つの表に区分の列で並べ、承認は表全体で一度取る**。
新規か witness 追加かは AI が判定して区分に書く（ユーザーに別の問いとして立てない）:

| 区分 | actor | claim | witness | settled |
|------|-------|-------|---------|---------|
| 新規 | <辞書の actor 名> | <述語（案）> | <テストファイルパス>#<describe表題> | date / project / devices / unitTests |
| witness 追加（act-NNNN） | <既存の actor> | <既存の claim（変えない）> | <足す witness（条件が読める表題）> | 広がった条件 / devices / unitTests |

この表は spec の差分と同じターンに出す（「spec への反映」参照）。

承認を得たら、書き込みはエントリごとにコマンドを一回ずつ実行する（承認を一件ずつ取り直すという意味ではない）。新規は次のとおり:

```bash
node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/acts-write.js" add <<'EOF'
{ "actor": "<辞書の actor 名>", "claim": "<述語>", "context": "<辞書の context.dir>",
  "witness": { "acceptance": ["<テストファイルパス>#<describe表題>"] },
  "settled": { "date": "<成果物レビューの日 YYYY-MM-DD>", "project": "<プラン名>",
               "devices": ["<装置概念名>"], "unitTests": ["<テストファイルパス>#<describe経路>"] } }
EOF
```

- **順序は promote の後。** actor が docs 側の辞書に昇格していない行為の登記は保留する
  （`acts-write.js check` の「actor が辞書に存在」と整合させるため）。保留は該当 actor の
  行為だけであり、周回全体の登記を止めるものではない。
- **既存の行為の成立条件（手段・環境）が広がっただけの周回では、新規に登記しない。**
  problem.md の「この問題で成立する行為」に「成立条件が広がる既存の行為」として挙がった行為（`test-tree.md` に `root の出自: act-NNNN …` がある維持型のプランを含む）は、行為を複製せず、既存エントリに新しい条件の witness を足す。
  判定は新規登記と同じ三条件（操作の事実に現れている／失敗・違和感が帰属されていない／witness が緑）を、**新しい条件で回した受け入れテスト**について見る。
  上の表に区分「witness 追加」の行として「対象 act の id・claim／足す witness／広がった条件」を載せ、新規の行と一緒に承認を取る。承認を得たものは次のコマンドで書く:

  ```bash
  node "$(realpath "${CLAUDE_SKILL_DIR}")/../bin/acts-write.js" witness-add <act-NNNN> <<'EOF'
  { "acceptance": ["<テストファイルパス>#<describe表題（条件が読める表題）>"],
    "date": "<成果物レビューの日 YYYY-MM-DD>", "project": "<プラン名>",
    "devices": ["<新しい条件を支えた装置概念名>"], "unitTests": ["<テストファイルパス>#<describe経路>"] }
  EOF
  ```

  claim を言い換えたくなる場合（条件を claim に書き込みたくなる場合を含む）は、それが新しい行為でないかを問い直す。
  新しい行為なら通常の登記、既存の行為の維持なら claim はそのままで witness だけ足す。
- **防衛線の停止**（同一 actor・近接 claim の既存エントリ）が出たら、まず「既存の行為の成立条件が広がっただけか」を疑い、そうなら witness-add に切り替える。
  claim そのものを書き換えたい場合は上書きせずユーザーに諮り、経緯を findings に記録する。この実例が supersede 本設計の材料になる。
- **再節合型プラン（diagnosis.md 入口）の周回では、新規の登記は原則発生しない。**
  root・行為層は台帳からの回収であり登記済みである — あらためて候補に挙げない（挙げれば防衛線が同一 claim で止まる）。
  扱うのは次項の「未登記挙動」だけである。
- refactor 由来の findings に「未登記挙動」の項があれば、この周回で扱ってよい。
  ただし判定は遡及の解釈規則（`/tdd-update acts` の登記判定）に従う。

**spec への反映（docs/spec.md または docs/spec/<context>.md）:**

書き込みは登記の後に行う。`${CLAUDE_SKILL_DIR}/subcmds/spec.md` を Read して従う。
**提示は登記の表と同じターンにまとめ、承認は一度で取る。** 差分は表の claim（案）で書いておき、承認で claim が直されたら spec 側も同じ文言に揃えてから書く。
spec は使用で清算された振る舞いと機構の現在形の説明であり、`docs/` の分担では「名前は辞書、証拠は台帳、依存は接続マップ、説明は spec」にあたる。
書き先は入口文書 problem.md の `**関連設計資料:**` が指す節（無ければ昇格した概念の context の節）。
節の単位は「全体としての振る舞い」（機能）で、要素がどう噛み合って成り立つかを辞書の語で書く（装置ごとの節は作らない）。この周に登記した行為・昇格した装置がその中で読めるように、節の追記・改訂・削除を差分で提示し、承認を得て書く。
context 末尾の行為一覧は登記の claim をそのまま写したものなので、承認の対象にしない（差分には写した結果として示す）。
未清算の振る舞い（外れ側・findings が帰属したもの）は書かない。
再節合型の周は原則触らない（改名の波及と未登記挙動の登記分のみ）。
過去のアーカイブ分をまとめて起こすのは `/tdd-update spec` の仕事で、ここではやらない。

### 3. 前周 findings の棚卸し

`plans/<project>/findings.md` が既にあれば、一周後の戻りである。ここで読む。

**インタビューより前には読まない。** 前周の解釈を頭に入れた状態で聞くと、白紙で聞けなくなる。
成果物レビューと同じ位置に置くのはそのため。

既存の各項目を、今回の利用の事実に照らして判定し、`**状態:**` を更新する:

| 判定 | 状態 |
|---|---|
| 今回の利用で再現しなかった | 解消 |
| 戻し先のフェーズで扱われたが、まだ利用で確かめられていない | 対応済み（戻し先・日付を明記） |
| 扱われたのに、また同じことが起きた | 再発 |
| まだ手がついていない | 未処理（据え置き） |

**再発は最も重い信号**として扱う。対応したのに同じ発見が出るなら、解法ではなく問題定義か、
発見の解釈そのものがずれている可能性が高い。今回の発見として書き直し、戻し先を見直す。

### 4. findings.md の更新

1〜3 で集めた素材をまとめ、findings.md を更新する。**事実の節と解釈の節を必ず分ける。**

**戻し先は三系統に整理する:**

- **問題の発見** → `/tdd-problem`。
  既存問題の未達・定義の誤りなら同一 plan の再定義、新しい問題意識なら新プランに problem.md。
- **構造・品質への懸念**（ブラインドレビューの劣化指摘、利用仮説「構造の改善」の外れ等） → `/tdd-refactor`。
  これは**診断の依頼**であり、同一プランへの再入ではない。
  tdd-refactor が診断し、構造的な作業が要るなら新しいプランを立てて diagnosis.md を置く。
  項目の状態は診断の結果が出た時点で更新する — プラン化: `対応済み（/tdd-refactor, plans/<新プラン>/diagnosis.md, YYYY-MM-DD）`／その場修正: `対応済み（/tdd-refactor, その場修正, YYYY-MM-DD）`／見送り: `対応済み（/tdd-refactor, 見送り, YYYY-MM-DD）`（理由は診断の提示に残る）。
- **ツリー・実装の修正**（既存スコープ内で済むもの） → `/tdd-run`。
  部分木再入・次サイクル。入口文書は変わらないので同居は生じない。

スキルとの摩擦（想定した使い方とのズレ）は上のどれでもなく、tdd-skills リポジトリの更新へ。

**既存の findings.md は退避せず、同じファイルを更新する。** ファイルの存在が /tdd-run の
ルーティング信号であり、周回をまたいだ照合（再発の検出）もこの一枚で行う。過去の版は git にある。

- 前周の項目は、状態を更新した上で残す
- 今回の発見を `F-nn` の続き番号で追記する
- 「解消」の項目が増えて見通しが悪くなったら、解消済みをまとめて畳んでよい（判断はユーザーに諮る）

### 5. クローズ判断

findings.md の内容とユーザーの状態をもとに、以下の三択から選ぶ。

A の条件のうち、promote・spec への反映・findings の内容は、ここまでの承認で既に確かめている。重ねて「満足しているか」を聞かない。
条件をすべて満たしていれば、推奨する選択肢（A/B/C）とその理由を示し、ユーザーの返答で確定する。
満たしていない条件（保留した promote、未処理の findings など）があるときだけ、その条件を挙げて聞く。

#### A. クローズ（アーカイブ）

条件:
- findings に満足している
- 辞書マッピングが完了している（promote 済み）
- spec への反映が済んでいる（テストを畳み、入口文書をアーカイブしたあとに残る振る舞いの説明は台帳と spec になる）
- この問題に対して特に不満がない

アクション:

**テストを畳む（ライフサイクルの二層化）:** 辞書の安定層に昇格した概念に対応する
describe() ブロックだけを残し、それ以外は畳む（削除する）。`tests/acceptance/` は常に残す。
プランと共に生まれたテストはプランと共に畳んでよい足場であり、生き残るのは
辞書概念に索引された昇格テストと受け入れテストの二本立て。

**プランディレクトリをアーカイブする:** `<meta>` と `<work_repo_abs>` が同じか異なるかで処理を分岐する。

**単一レポ構成（`<meta>` == `<work_repo_abs>`）:**

```bash
mkdir -p <work_repo_abs>/plans/archives
mv <work_repo_abs>/plans/<project>/ <work_repo_abs>/plans/archives/<project>/
```

**サブレポ構成（`<meta>` != `<work_repo_abs>`）:**

```bash
mkdir -p <meta>/plans/archives
mv <meta>/plans/<project>/ <meta>/plans/archives/<project>/
```

ユーザーへ報告する:

```
プラン `<project>` をアーカイブしました。
```

#### B. 同一プランへの戻し

条件: 既存の problem が明らかに未達（problem の定義に問題があるか、解法に問題がある）

| 原因 | 戻し先 |
|------|--------|
| 問題定義の見落とし・条件の誤り | /tdd-problem（同一 plan） |
| ツリーの分解・合成の見直し | /tdd-run（同一 plan、次サイクル） |
| スキルとの摩擦（想定した使い方とのズレ） | tdd-skills リポジトリの更新 |

#### C. クローズ + 新規プランへの移行

条件: 問題自体は達成されているが、フィードバックを通じて**新しい問題意識**が生まれた、または**構造・品質への懸念**（リファクタリングの相談）がある

- この plan 自体は A と同様にアーカイブする
- 新しい問題意識については、別の plan として `/tdd-problem` を起動するよう促す
- 構造・品質への懸念については、`/tdd-refactor` に診断を依頼するよう促す（診断の結果プラン化するなら、新プランに diagnosis.md が置かれる）

---

## findings.md のフォーマット

```markdown
# Findings: <project>

**日時:** YYYY-MM-DD
**対象:** plans/<project>/

## 操作の事実
- 何をしたか（入力・設定・出力）。再現できる粒度で

## 利用仮説の照合
- 利用仮説: 使ったらこうなるはず／こうなったら外れ
- 実際: 期待側 / 外れ側 / どちらとも言えない

## 印象（ユーザーの言葉）
- 粗い印象 → 解像度を上げた言い直し（本人の言葉のまま）

## 発見（解釈・原因の仮説、戻し先つき）

### F-01: <タイトル>
**状態:** 未処理 | 対応済み（<戻し先>, <反映先>, YYYY-MM-DD） | 解消 | 再発
**戻し先:** /tdd-problem（同一 plan | 新規 plan） | /tdd-refactor（診断の依頼） | /tdd-run（同一 plan） | tdd-skills
**出どころ:** 成果物レビュー / 利用インタビュー / observations.md
**解釈・原因の仮説:** ...（事実ではなく仮説として）
**推奨される対応:** ...
```

**`状態:` は周回をまたぐ台帳。** 新規の項目は「未処理」で書く。戻し先のフェーズがその項目を
扱ったら、扱った側がここを「対応済み」に更新する（例: `対応済み（/tdd-problem, problem.md v2, 2026-08-02）`）。
どこまで反映済みかはこの欄が唯一の記録であり、problem.md 側には書かない。

/tdd-run が拾うのは **未処理・再発** の項目だけ。

---

## 制約

- **設計を擁護しない／誘導しない**（インタビュー中）
- **ユーザーの代わりに解釈しない**（解像度を上げる質問に徹する）
- **事実の節と解釈の節を混ぜない**
- **未使用の状態で想像を聞かない**（接地しない）
- **コードを書かない**（直しは戻し先のフェーズで）
- **時間見積もりはしない**

## 成果物

1. **plans/<project>/findings.md** — 利用インタビュー・成果物レビューの統合結果（状態・戻し先つき）。
   周回をまたいで同じ一枚を更新する（退避も別ファイル化もしない）
2. **docs/dictionary.json** への昇格（レビューが通った場合）
3. **docs/acts.json** への登記（判定規則を満たし、表＋承認を経た行為）
4. **docs/spec.md または docs/spec/<context>.md** への反映（清算済みの振る舞いと機構の現在形の説明。差分＋承認を経た節）
5. **plans/archives/<project>/** — クローズ時にプランディレクトリごとアーカイブ。
   あわせてテストを二層化する（昇格概念の describe() と tests/acceptance/ だけ残す）
