# /tdd-feedback — spec への反映

成果物レビューの promote → 行為の登記のあとに読み、実行する。
`docs/spec.md`（または `docs/spec/<context>.md`）は **使用で清算された振る舞いと機構の、現在形の説明**である。
読者は開発者と AI エージェント。外から見える振る舞いだけでなく、内部の機構も書く。

`docs/` の分担: 名前と関係は辞書、行為の証拠は台帳（acts.json）、依存の網羅は接続マップ、**説明は spec**。
重複は構わないが、正は各台帳であり spec は説明。食い違ったら spec を直す。

## 前提

- promote と行為の登記が済んでいる（spec は昇格した語で書く。claim の文言は登記の承認で確定している）
- 手元に次がある: 操作の事実（1-1）、利用仮説の照合（1-2）、印象の言い直し（1-3）、test-tree.md、observations.md、入口文書、この周に登記した行為、昇格した語彙
- 対話規範（`${CLAUDE_SKILL_DIR}/../tdd-run/norms/dialogue.md`）に従って提示 → 承認で書く。案は差分（追記・改訂・削除）の形で提示する

## 何を書くか

### 粒度の原則

1. **節の単位は「全体としての振る舞い」（機能）。** テストツリーで言えば root の行為（誰が何をできる）か、複数の行為をまとめる機能の名前（context がそれにあたることが多い）。書くのは、要素がどう組み合わさって相互作用し、その全体が成り立っているか — 合成の記述であって、要素の一覧ではない。装置は節を持たず、全体の説明の中に登場する。個々の要素の定義は辞書が、所在は接続マップが持つ。装置に独自の設定面（キーの表など）があるときだけ、節の中に小見出しを持つ。
2. **語は辞書の語。** 説明に使う名前は辞書に載った概念（行為・装置・data）に揃える。名前の無いものは書かない — 書きたければ語彙登録ルールで名付けるか、書かないかの二択。葉（個々の関数の入出力）はこの規則で自然に落ちる。
3. **spec が変わるのは、辞書が変わるか振る舞いが変わるときだけ。** それ以外の変更で書き換えが要る記述は細かすぎる。逆に、辞書か振る舞いが変わったのに書き換え箇所が無ければ書き漏れ。
4. **後から読む人が「知らなければ壊す」もの、コードから安く復元できない・誤って復元しやすいものを書く。** 関数のシグネチャやファイル一覧は書かない。複数ファイルにまたがる規約、暗黙の前提、失敗時の挙動、永続化されるものの意味、既定値、装置どうしの相互作用は書く。

### 一節の要素（目安。見出しとして固定しない。要素の有無は提示時の点検に使う）

| 要素 | 何を | 素材 |
|---|---|---|
| 説明 | その機能が全体として何をするか、要素がどう噛み合ってそれが成り立つか | test-tree の root と中間ノードの連なり、辞書の definition と relations |
| インターフェース | 入力（設定キー・既定値・記法）、出力、永続化するもの（ファイルと形式） | 昇格した data 概念、接続マップ、コード |
| 規約・不変量 | 変えてはいけない関係 | 入口文書の問題記述、ツリー承認時の判断 |
| 前提 | 暗黙の前提を明示する — 環境、順序、他装置の状態、消してはいけないもの | 入口文書の「障害・制約」「範囲外」、observations.md の詰まった点、インタビューで出た「〜だと思っていた」 |
| 制約・失敗時の挙動 | 意図的に「できない」こと、失敗したときどう見えるか | test-tree の外れ側、異常系のテスト、清算済みだが仕様上の限界として残った findings |
| 具体例 | 最小の一つ（設定例、入出力の対） | 利用仮説の「試してほしい操作」、操作の事実 |

インターフェース（キー・フィールド・ディレクティブ）は全部列挙する。振る舞いの事例は網羅しない — 事例はテストが持ち、spec は規則と最小の一例を持つ。

### 書かないもの

- 未清算の振る舞い — 利用仮説の外れ側に落ちたもの、findings で失敗・違和感が帰属したもの。次の周で清算されてから書く
- 経緯・理由（入口文書とアーカイブが持つ）、プラン名・findings 番号・テストパス（台帳が持つ）、履歴（git が持つ）
- ソースファイルのパス。spec が辞書の語で書かれていれば、読み手は語 → `dict-search.js`（`src`）／接続マップ（`implements`）→ src と辿れる。spec に書いたパスはコードに追随せず腐る。契約の一部であるパス（設定ファイル・永続化ファイル・キャッシュディレクトリ等）は内容なので書く
- 葉の詳細 — 呼び出す外部 API のエンドポイント、エンコードの分割、関数名、リトライ回数など。ただしそこから漏れる制約（上限によるサイズ制限等）は制約として書く

## 構成

- **context 単位。** 単一ファイルなら `docs/spec.md` の `##` が context、小分けなら `docs/spec/<context.dir>.md`（context.dir は `dict-search.js -a -s` のコンテキスト一覧の `[context: <dir>]`）
- **context の冒頭に行為の一覧**（actor 視点で何ができるか）を一行ずつ置く。台帳の散文要約であり、読み手の入口
- **機能ごとの節**がそれに続く。一つの節が一つの「全体としての振る舞い」を、要素の相互作用として説明する。装置ごとの節は作らない

```markdown
## <context 名>

<この context が担うことの一文>

<actor> は … できる。
<actor> は … できる。

### <機能名（辞書の語）>

<全体として何をするか、要素がどう噛み合って成り立つか。以下、要素の目安に沿って必要なものだけ>

#### <装置名>（独自の設定面がある装置だけ）

<キーの表、記法など>
```

## 手順

**1. 書き先の特定**

- 入口文書 problem.md の `**関連設計資料:**` が spec の節を指していれば、そこが書き先（problem が「適切さの出発点」とした節に書き戻す）
- 指していない・新機能で該当節が無い → この周に昇格した概念の context から節を決める。`docs/spec/` があれば小分け、`docs/spec.md` があれば単一。どちらも無ければ単一か小分けかを一度だけユーザーに聞き、作る
- 変更が複数 context に及ぶなら、context ごとに分ける

**2. 対象節だけ読む**

spec 全体をロードしない。書き先の節（と、その context の行為一覧）だけを読む。
既存の記述と今回の変更の関係（追記か、既存の振る舞いの改訂か、消える振る舞いか）をここで見る。

**3. 素材を並べる**

この周の素材から、書く候補を要素ごとに拾う:

- 登記した行為 → 行為一覧の行、機能の節の説明（何ができるか）
- 昇格した装置・data 概念 → 機能の節の中での相互作用の記述、インターフェース（設定面があれば小見出し）
- 入口文書の「障害・制約」「範囲外」「問題」 → 前提・不変量・制約（**なぜを落として、何が成り立っていなければならないかだけを写す**）
- 操作の事実・利用仮説の期待側 → 具体例
- 外れ側・異常系 → 制約・失敗時の挙動（清算済みのものに限る）
- observations.md の詰まった点、インタビューの「〜だと思っていた」 → 前提

未清算のもの（外れ側、findings が帰属したもの）はここで外す。

**4. 案を差分で提示する**

追記・改訂・削除を、節ごとの差分として提示する。あわせて次を点検し、欠けがあれば示す:

- この周に登記した行為が spec のどこかで読めるか
- この周に昇格した装置が、機能の節の中で相互作用として登場しているか（装置ごとの段落になっていないか）
- 改名・統合された概念があれば、spec の語が追従しているか
- 書いた記述に葉の詳細・ソースパス・経緯が混ざっていないか

提示はターンの最後のテキストで行い、承認はユーザーのテキスト返答から取る（対話規範）。

**5. 承認を得た差分だけを書く**

承認されなかった箇所は書かず、理由が findings に載るべきものなら findings に記録する。

## 例外

- **B（同一プランへの戻し）に向かう周**でも、着地した行為・装置の分は書く（台帳と同じ）
- **再節合型（diagnosis.md 入口）の周**は振る舞い不変なので原則触らない。扱うのは、辞書の改名・統合が spec の語に波及する分と、findings の「未登記挙動」が台帳に登記された分だけ
- **spec が無いリポジトリで初回**は、この周の分だけ書く。過去のアーカイブ分をまとめて起こすのは `/tdd-update spec`（遡及）の仕事であり、ここではやらない
