## 1. 再現可能性の検討と方向転換

センサー差し込み型の対応(「同じ反論を二度したら前提を明示」等)は、効果を確かめる手段がないまま蓄積し、旧 tdd-run の保守不能化と同型になる懸念があった。当初「事例をフィクスチャ化して回帰テストにする」路線を検討したが、これは棄却した。

- 目的は事例を「起きなかったことにする」ことではない。対話が理想的・完璧であることは求めていない。
- 検出は人間がやる。人間は摩擦の違和感に気づけるし、「いったんリセットしよう」と言える。センサーは手順として意味がない。
- 欠けているのは、**対話が失敗に終わったとき(AIと人間が別の理解を持ってしまったとき)、その原因を分解して修繕するワークフロー**。

形としては事故調査に近い。入力は失敗したセッションの記録と周辺成果物。作業は、分岐点の特定 → 原因の帰属(概念の混線か、記録されなかった望みか、聞き落としか) → 既存の修繕経路への振り分け。「その要件は誰が置いたか」という問いは、混線と判明した後の道具ではなく、この帰属の前段に属する。

概念の診断(model-rearrangement.md)は修繕先の一つとして生きるが、帰属が済んだ後の手続きとして位置づけ直す。成立の前提は記録の保全(セッションログ・findings・archives)であり、ワークフロー本体より先に確かめる。

## 2. 外部設計の欠落

(a) 人手で確かめる拍の欠如は、(b)(c) と独立ではなく、その必然的な帰結である。より一般化すると:

- この体系にはユースケースを検討する場がない。「人間はこのシステムをどう使うか」を検討するフェーズがない。
- 問題定義(「できない」の定義)から直接 decompose に行き、decompose が行うのは内部設計である。**外部設計——システムとユーザーがどうインタラクションして「ユーザーは…できる」を実現するか——が存在しない。**
- V字モデルとの対応で言えば、現行の V は古典的な V の内側半分しか持たない。左脚に外部設計がないから、右脚にその対応物(人手による受け入れ確認 = (a))も現れない。左右の欠落は対称である。
- インタラクションだけが、最初の検証が実地投入(feedback)であるような層になっている。コードにはテスト、辞書には承認という「安く失敗する機会」があるのに、この層にだけ無い。

## 3. BDUF 懸念の解体

外部設計の導入は BDUF ではない。判定基準は**時期ではなく、撤回可能性とフィードバック経路の有無**である。

- ペーパープロトタイプやワイヤーフレームは、撤回が安いからこそ存在する事前シミュレーション技法。ユースケース記述も同種のシミュレーションである。
- アジャイル/TDD/DDD の根本はフィードバックサイクルであり、実装を投機的行動と捉えるからフィードバックが要る。アジャイルが批判したのは、設計が解釈の余地なき権威として置かれ、実装が逐語変換にすぎず、フィードバックもユーザーも要らない世界。
- 左脚の成果物が BDUF になるのは、右脚に対応物(戻り経路)が無いときだけ。V が対称である限り、事前の検討は権威ではなく仮説でいられる。

原則が禁じるのは内部構造の事前固定であって、界面の検討はユーザーの日常語の側に属し、原則に触れない。むしろ「できる」を操作可能な形まで具体化する作業として、問題定義の完結に必要である。

## 4. rationale.md の診断

AI(Claude Code / Claude)が外部設計に BDUF 様の反射を示すのは偶然ではなく、文書に実体がある。

**(i) 原則が機構のレベルで成文化されている。** セクション1「設計フェーズと実装フェーズを分離すると…」は、本来の基準(発見が設計を更新する場所を失うな = 戻り経路の喪失禁止)を「分離するな」という形式面の禁止として書いており、字義通り読む AI が時期・配置のレベルで発火する。

**(ii) インタラクションの言葉が全域から追放されている。** problem は「解決手段を持ち込まない」で追放し、できるツリーは「手段を述語に持ち込まない」で追放し、UI 層は「命名は合成の最終段階」で最後まで留め置く。三つの規律は局所的に正当だが、合わせるとインタラクションの言葉に住む場所がない。「手動で確かめるやり方が分からない」事例は、この教義上の帰結である。

**(iii) 原則とプラクティスの混入。** rationale は原則を書く文書だが、現行実装の機構が原則の顔で混じっている(二層管理のパス、スキーマ欄名、describe/it の手順等)。これは辞書における「実現の逆流」と同型で、「その記述は誰が置いたか(原則か、現行実装か)」で仕分けられる。害も同じ——再設計時に読まれる文書に現行機構が原則として書かれていると、再設計が現行実装にアンカリングされる。

改訂の編集規則は一つ: **各記述を、実装を入れ替えても真であるレベルまで持ち上げる**。(i) と (iii) は同じ誤りの裏表なので、同じ規則で直る。インタラクションの居場所は Jackson の machine / world の界面として理論的に確保できる(problem が追放すべきは machine 内部の語彙であって界面の語彙ではない)。

## 5. 理論的統合の方針(ポランニーと投機・フィードバック)

現行 rationale はポランニーの静的な構造論(近位項・遠位項・包括・棲みつき)のみを使っており、**発見の理論**(理解はどう前進するか)が空席のまま、投機とフィードバックの話が実務の言葉でそこを埋めている。統合は接木ではなく、ポランニーのもう半分を迎え入れる形でできる。

- **メノンのパラドックスへの回答**(『暗黙知の次元』): 問題を見るとは、まだ言明できない一貫性を予感すること。暗黙の予知が探索を導く。→ 望みの一覧 (c) は予感の外部化として理論的地位を得る。優先度・見積の欄を作らない判断も「予感はまだ分節されていない」から導き直せる。
- **コミットメント**: 予感に基づく行為は個人の賭けであり、実在からの応答が審判する。実在の定義=「まだ予期しない仕方で自らを顕わにしうるもの」。→ フィードバックは投機に対して実在が予期しない仕方で応答する経路であり、省略できない。
- **探針(盲人の杖)**: 投機的な実装・ハリボテ・プロトタイプは世界を探る杖。杖に要るのは精巧さではなく、手応えが伝わることと持ち替えられること。→ 撤回可能性の基準は探針の経済学として理論の内側に入る。
- **創発と二重統御**(第二章「創発」): 上位は下位の法則を破らず、下位が開いたまま残す境界条件を統御する。創発は包括の存在論的対応物。→ 指示の連鎖(現実←辞書←ツリー←実装)は二重統御の積層として読み直せる。
- セクション6の翻訳の連鎖は、一方向の変換列から**予感 → コミットメント(投機的成果物) → 実在の応答 → 予感の更新**という円環に組み替わる。外部設計はこの円環の中に自然な席を持つ(インタラクションの筋書き=ユーザーにおける包括の予期、(a)=その最初の確認)。

**AI と暗黙知について。** LLM の確率的生成は「まだ書かれていないものの一貫性への感度」を機構として持ち、瞬間的な暗黙知・予感は機能的に存在すると言える(リファクタリングはメノン構造を最も純粋に持つ設計行為)。ただし三つの留保がある: 予感が乱交的(訓練分布を反映し、このプロジェクトの現実を反映しない)、所有されない(賭け金がない)、持続しない(内面化の基体がない)。体系の成果物群はこの欠落への応答として読める——継承の経路を身体から環境へ振り替えた設計(ニッチ構築型)。人間は意味の固定点であるだけでなく、予感の選別者・賭け金の持ち主として席を持つ。

**書き方の注意二点。** 発見論の転用は科学的発見からのずれを明記する(dwell in の註記と同じ流儀)。人間の役割は「AI の記憶を補う」(消えうる技術的制約)ではなく「賭け金の持ち主」(記憶の問題ではない)を土台に書く。「AI を主体として扱う」は反テイラー主義の原則(構想と実行を AI において分離しない)として定義し、コミットメントの次元は別立てで書く——手続的責任は成果物の層へ外部化でき(acts.json は清算済みの約束の登記簿)、実存的責任は人間に留まる。

## 6. 当面の対応(決定)

rationale.md の見直しは別途。インタラクションの居場所には、**新しいフェーズもスキルも作らず**、最小の器で始める。

1. **tdd-problem に境界語彙の区別を一行入れる**: 禁じられるのは機械内部の語彙。界面の語彙(ユーザーが何をして、何を見て、どう確かめるか)は problem の完結に必要。
2. **problem.md に「操作の筋書き」の節を設ける**: 「できるようになったとき、ユーザーはこう操作し、これが見えたら確かめられたことにする」。数行の散文。仕様ではなく予期(claim)であり、書き直し自由・撤回は安い。
3. **tdd-run の統合ステップの最後に、筋書きを人手で再演する拍を足す**((a) の実装): 通れば記録、通らなければ何が阻んだかを findings へ。再演できない理由が「後回し」なら、それが (b) の明言の自然な発生場所——(b) 用の独立した仕組みは今は作らない。
4. (c) 望みの一覧はメモの設計のまま別トラック。
5. **昇格基準を先に決めておく**: 2〜3プロジェクト回して、筋書きの節が数行で安定するなら現状維持。節を書くために毎回まとまった対話が必要になる、または筋書きが decompose の形を実際に変える(ルートノードの吊り元になる)ことが確認されたら、独立したフェーズ/対話の型に昇格。

失敗した対話の修繕ワークフロー(§1)は、記録の保全状況の確認が先行タスク。
