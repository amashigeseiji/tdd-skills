# problem 段階で「新しく成立する行為」を台帳と照合する（2026-08-17）

## 起点

利用プロジェクトの feedback から、tdd-skills 宛ての二つの発見が戻ってきた。

一つは problem → run の流れが「行為が増える」ことを暗黙に仮定していたこと。
そのプランは、既存の同期操作（公開・非公開・取り込み）を、これまでとは別の手段でも行えるようにするものだった。
ツリーの root は「作成者は〜が無くても同期操作の一式を行える」と立ち、受け入れシナリオが 16 本新規に書かれ、利用仮説の照準は「混在」「取り込み」「別マシン」に寄った。
feedback で登記しようとして防衛線が止まった — 候補はすべて台帳の既存の行為（公開できる・非公開に戻せる・取り込める）と近接していた。
作者の判断は「これらは新しい行為ではなく、既存の行為が別の手段でも維持されただけ。claim に『〜が無くても』と書くと任意の手段と読め、検証内容も特定できない」。
一方で作者にとって本当に新しかった行為（手段を選択できる／選んだ手段で運用を始められる）は、problem で「初回セットアップ・範囲外」に切り出されていた。
problem 作成時に作者が「認証が先ではないか」と言った直感は、この新しい行為の所在を指していたが、問いの形を持たなかったので消えた。

もう一つは、既存の行為に witness を足す操作が `acts-write.js` に無かったこと（`add` / `check` のみ）。
台帳に必要だったのは「既存の行為に新しい手段の目撃者を足す」ことであって、行為を手段ごとに複製することではなかった。

## 診断 — 台帳の非対称

台帳（`docs/acts.json`）を引いていたのは `/tdd-refactor` と `tdd-run/subcmds/refactor.md`（再節合型）だけで、`/tdd-problem` と `decompose.md`（新規型）は台帳を参照していなかった。
台帳は再節合の固定点としてしか働いておらず、新規型の入口では既存の行為が見えない。

`/tdd-problem` の手順3には「問題を既存の辞書語彙で語れるか試みる — 語れる概念はそのまま使い、語れない概念は語彙の種として申し送る」がある。
欠けていたのは、この辞書照合の**行為版**である。
「やりたいことは既存の行為で語れるか。語れるなら維持、語れないものが新しい行為」。
rationale の「problem における翻訳」は辞書を翻訳の媒介と位置づけている。台帳も同じ位置に立つ媒介であり、これは孤立した追加ではなく体系の対称性を埋める変更である。
（rationale への追記は差分が溜まっているため今回はせず、まとめて行う。）

## 判定のヒューリスティック — 条件節を外す

root「作成者は〜が無くても同期操作の一式を行える」は `<役割> は … できる` の形をしているが、**条件節（〜が無くても）を外すと残るのは既存の claim** である。
条件節（「〜が無くても」「〜の環境で」「〜経由で」「〜のときも」）を外して台帳と突き合わせ、一致すれば「成立条件が広がる既存の行為」、一致しなければ「新しく成立する行為」。
条件節を外して「やりたいこと」が空になるなら、この問題で新しく成立する行為は別の場所にある — 今回なら「手段を選べる」「新しい環境で運用を始められる」。
feedback の防衛線がクローズ時に捕まえていた判別を、problem の時点に前倒しする。

## 変更の形

1. `/tdd-problem` 手順3に台帳照合を足し（候補まで）、手順4の対話で行為を確定して problem.md の必須節「この問題で成立する行為」（新しく成立する行為／成立条件が広がる既存の行為の id）に書く。手順4の分割の確認に、両方が同居する場合を候補として足す。
2. `/tdd-userstory create` はこの節で分岐する。既存の行為の維持には新規シナリオを書かず「維持される既存の行為」節に列挙し、`run` は既存 witness のシナリオを新しい条件で回す describe（表題に条件を含める）を置く。シナリオを生む場所は userstory なので、受け入れ重複の抑止はここが実体。
3. `decompose.md` の root は problem.md の行為の言明を受け取り、再導出しない（設計側のチェックは残す。後述）。維持型では root は台帳の既存の行為（claim は言い換えない）で、仮説なのは成立条件の拡張。利用仮説は「退行なし＋新しい条件で同じ読み」。
4. `/tdd-feedback` の登記規則に維持型（既存エントリに witness を足す）を足す。`acts-write.js witness-add` がその操作。

## root の文が problem に移ることについて — 設計の先取りか

変更 1 は、`<役割> は … できる` の形の文を problem.md に書かせる。
これまで root の文は decompose が立てていた（problem.md と Then 句からの導出、調査・辞書・エントリーポイントを伴う設計案の提示）。
問題側にこの文を置くことが設計を先取りしないか、という問いが実装後の対話で出た。

decompose の root 手順に含まれている設計側の要素を分けると、次のとおり。

- 手順1の調査（エントリーポイント・既存実装の解釈 paradigm・辞書）を経て立てる
- 主語の役割を辞書に actor として登録する
- `Entry point: <file> → <root の行為>` — この行為が系に入る場所の宣言
- フェーズの束ね方（1回の実行は単一エントリーポイント）
- 「root は問題解決の仮説」— どの行為を立てるかの選択で、下の分解の形が決まる

root の文そのものに含まれていないもの: 概念の定義（ツリー規範: root は概念ではなく文。辞書に触るのは actor の登録だけ）、装置・手段（能力層）。
つまり `<役割> は … できる` の文自体は行為層＝行為可能性の言明で、問題領域の言葉である。
設計に触れるのは、その文にエントリーポイントを結びつけ、フェーズに束ね、仮説として採用するところ。

problem に移したのは文だけで、エントリーポイント・actor の登録・束ね方は decompose のまま。
ただし「どの行為を立てるかの選択」は事実上 problem 側に一部移る。
これについては、F-13 の実例が逆方向の漏れを示している — decompose で台帳なしに選ばれた root「〜が無くても一式を行える」の条件節は解決側の環境の言葉で、root に手段が漏れた形だった。
台帳と比べる作業（既存の行為を除いたら利用者にとって何が新しいか）の答えは問題側の事実であり、照合を problem に置くことは root の選択から手段の漏れを抜く方向に働く。

残る懸念は「problem.md に答が書いてあると、decompose がそれを批判なしに受け取り、思考が省かれる」こと。
二つの取り方があった。(a) decompose が再導出して批判する、(b) problem で本人と対話を重ねて行為を確定し、decompose は再導出しない。
(b) を採った。理由:

- 行為（利用者にとって何が新しいか）の接地は人間から取るもので、decompose の導出は文書（problem.md と Then 句）からの共通分母の抽出である。文書からの導出は本人と対話して確定した言明より弱い。F-13 の実例はまさに導出が本人の直感を拾えなかった件。
- decompose でも root は単独承認していなかった（承認は手順6のツリー確認が root を含めて行う）。decompose 側の root の「批判」は Then 句との突合・エントリーポイント・束ね方という設計側のチェックであって、行為の是非を問う対話ではない。行為の対話が problem に移っても、設計側のチェックは残る。
- 8/14 にルーティングから解釈を外したのと同じ向き。下流に「これは本当に新しい行為か」を再解釈させず、上流で確定した事実として受け取る。

したがって線引きは次のとおり。
スキップしてよいのは行為の再導出、スキップしてはいけないのは設計側のチェック（エントリーポイントの結びつけ、束ね方、Then 句との整合、actor の登録、技術語スキャン）。
チェックで行為そのものが動く（条件節を外して問題側の言明と一致しなくなる言い換え、Then 句との食い違い）なら decompose で直さず problem に戻す。
単一エントリーポイントに収まらないための分割は行為の変更ではないので decompose で決めてよい。

problem 側の「ちゃんと対話を重ねる」の実体は手順4に置いた。
照合の結果を提示し、「既存の行為を除いたら、やりたいことに何が残るか」を本人に問い、残ったものを `<役割> は … できる` の形で確認する。何も残らない場合も本人に確認して「無し」。
確定するのは行為の言明であり、エントリーポイント・フェーズの束ね方は決めない。
だからこそ AI が候補を確定させず、本人の言葉で行う。

## 維持型を独立した工程型にしなかった理由

維持型は root が固定点（既存の行為）で問いは導出、という新規型と再節合型の中間である。
しかし工程型は入口文書のジャンルで機械的に決まる（problem.md → 新規型、diagnosis.md → 再節合型）ので、維持型を型にすると判定が文書の存在から節の内容へ戻る。
実例がまだ一つなので、新規型の変種として `test-tree.md` に root の出自（`root の出自: act-NNNN（<claim>）の成立条件の拡張 — <条件>`）を記録するに留めた。
実例が溜まってから型に昇格するかを判断する。

## witness 追加の形 — settled は不変、resettled に積む

`settled` は「清算時の証拠スナップショット。不変」という契約を持つ。
witness を足すたびに `settled` を書き換えると、初回清算の歴史的事実が消える。
そこで `witness.acceptance`（生きた参照、既に配列）にアンカーを足し、追加分の清算スナップショット `{ date, project, acceptance, devices?, unitTests? }` を `resettled` 配列に積む形にした。
`resettled.acceptance` は「そのとき足した witness」の記録であり、生きた参照は `witness.acceptance` が担うので `check` ではリンクを追わない。
claim の置き換え（supersede）は引き続き未設計。防衛線が止まったとき、まず「成立条件が広がっただけか」を疑い、そうなら witness-add に切り替える。
