# spec を清算済みの説明として docs/ に置く（2026-08-16）

## 起点

スキルを導入して開発を続けているプロジェクトで、`docs/spec.md` がほとんど更新されなくなっていた。
20 以上のプランがアーカイブされているのに、それらが加えた機能の記述が spec に無い。
一方で、プロジェクト側の作業手順に「ドキュメント更新」が残っていると、tdd-run の途中で spec が書かれる。
つまり「使う前に仕様が書かれ、次のプランでは書かれない」の両方が同時に起きていた。
ループの中に spec を書く拍が無いことが原因である。

## 位置づけ — docs/ の四つ目の清算済み成果物

`docs/` にいま残る清算済みのものは、辞書（名前と関係）と台帳 acts.json（actor の行為主張と witness）の二つ。
クローズ時にテストは畳まれ、problem.md はアーカイブされるので、現在の姿として生き残るのは辞書＋台帳＋コード＋接続マップである。
このどれも、開発者や AI エージェントが読んで「システムがいまどうなっているか」を一続きの話として掴める形を持っていない。

acts-format には「装置（能力層）は載せない — 名前は辞書、構造は依存グラフ、証拠はテストファイルが持つ」とある。
装置がどう組み合わさって一つの機能として動いているか — 合成 — を散文で説明する場所がこれまで無かった。spec がそれである。

| 名前・関係 | 行為の証拠 | 依存の網羅 | 説明（散文） |
|---|---|---|---|
| dictionary.json | acts.json | depgraph / 接続マップ | spec |

重複は構わない（読者が違う）。ただし正は各台帳、spec は説明。食い違ったら spec を直す。

読者は開発者と AI エージェントであり、エンドユーザーではない。
したがって外から見える振る舞いだけでなく、内部の機構も書く。
線引きは「外/内」ではなく「現在の姿の記述か、それ以外か」。

problem.md の `**関連設計資料:**` は既に spec の節を「適切さの出発点」として指している。
problem が指した節に feedback が書き戻す、という閉ループが既存フィールドだけで作れる。

## 書き手と拍 — feedback の成果物レビュー、promote → 登記 → spec

- `docs/` は使用で清算されたものだけを持つ、という規則が辞書・台帳で既に取られている。spec も同じ拍に置けば規則が一本になる。run で書くと仮説段階の仕様が書かれ、B（同一プランへの戻し）のたびに書き直しになる。
- 語が確定してから書ける。辞書は promote で、claim の文言は登記の承認で確定する。spec はその語で書く。
- インタビューの言葉が素材になる。「認証が通らないとステータスが不明になる」のような記述は、使ったあとに確定する種類の文。
- クローズ A でテストを畳む前に写す。テストが消えたあとの振る舞いの記録は台帳＋spec になる。
- run 側に spec が無くてもインタビューは回る。利用者への操作説明は test-tree.md の利用仮説（試してほしい操作）が担っている。

例外は台帳の規則に揃う。B に向かう周でも着地した分は書く。再節合型（diagnosis.md 入口）は振る舞い不変なので原則触らない（辞書の改名・統合の波及と「未登記挙動」だけ）。tdd-refactor のその場修正は触らない。

書き手は tdd-feedback の subcmd とする。独立スキルにするのは feedback 以外の呼び出し口が本当に要ると分かってから。
遡及（拍が無かった間のアーカイブ分を起こす）は `/tdd-update spec` に置く。台帳の遡及登記が tdd-update に置かれた前例に揃える。

## 粒度 — 四つの原則

1. **節の単位は「全体としての振る舞い」（機能）。** テストツリーで言えば root の行為か、複数の行為をまとめる機能の名前（context がそれにあたることが多い）。書くのは、要素がどう組み合わさって相互作用し、その全体が成り立っているか — 合成の記述であって、要素の一覧ではない。装置は節を持たず、全体の説明の中に登場する。個々の要素の定義は辞書が、所在は接続マップが持つ。装置に独自の設定面（キーの表など）があるときだけ節の中に小見出しを持つ。
   当初は「単位は辞書の概念」と言っていたが、それでは装置ごとの段落が並ぶ用語集になる。読み手が欲しいのは「なんとか機能」と名指される全体がどう成り立っているかであり、その合成の記述こそ辞書にも台帳にも接続マップにも無いものだった。
2. **語は辞書の語。** 説明に使う名前は辞書に載った概念に揃える。名前の無いものは書かない — 書きたければ語彙登録ルールで名付けるか、書かないかの二択。既存の語彙登録ルールが粒度の番人を兼ね、葉（個々の関数の入出力）は自然に落ちる。
3. **リトマス: spec が変わるのは、辞書が変わるか振る舞いが変わるときだけ。** それ以外の変更（葉の実装差し替え、再節合型プランの内部整理）で書き換えが要る記述は細かすぎる。逆に、辞書や振る舞いが変わったのに書き換え箇所が無ければ書き漏れ。
4. **選別: 後から読む人が「知らなければ壊す」もの、または「コードから安く復元できない・誤って復元しやすい」もの。** 関数のシグネチャやファイル一覧は書かない。複数ファイルにまたがる規約、暗黙の前提、失敗時の挙動、永続化されるものの意味、既定値、装置どうしの相互作用は書く。

## 一節の中身 — 六要素（目安であり、見出しとして固定しない）

| 要素 | 何を | 素材（feedback 時点で手元にあるもの） |
|---|---|---|
| 説明 | その機能が全体として何をするか、要素がどう噛み合ってそれが成り立つか | test-tree の root と中間ノードの連なり、辞書の definition と relations |
| インターフェース | 入力（設定キー・既定値・記法）、出力、永続化するもの（ファイルと形式） | 昇格した data 概念、接続マップ、コード |
| 規約・不変量 | 変えてはいけない関係 | problem.md の問題記述（不変量はここにある）、ツリー承認時の判断 |
| 前提 | 暗黙の前提を明示（環境、順序、他装置の状態、消してはいけないもの） | problem.md の「障害・制約」「範囲外」、observations.md の詰まった点、インタビューで出た「〜だと思っていた」 |
| 制約・失敗時の挙動 | 意図的に「できない」こと、失敗したときどう見えるか | test-tree の外れ側、異常系の葉テスト、清算済みだが仕様上の限界として残った findings |
| 具体例 | 最小の一つ（設定例、入出力の対） | 利用仮説の「試してほしい操作」、操作の事実 |

前提・不変量・制約の素材の多くが problem.md にある。
problem.md はクローズでアーカイブされるので、「なぜ」を落として「何が成り立っていなければならないか」だけを spec に写す拍がクローズ前の feedback にあるのは筋が通る。

列挙の粒度は分ける。インターフェース（キー・フィールド・ディレクティブ）は全部列挙する（それが契約だから）。振る舞いの事例は網羅しない（事例はテストが持つ。spec は規則と最小の一例）。

書きすぎの例: どの外部 API のエンドポイントを叩くか、エンコードの分割方法、関数名、リトライ回数。いずれも葉で、名前を持たず、変えても辞書も振る舞いも変わらない。ただしそこから制約が漏れる場合（上限によるサイズ制限等）は制約として書く。

## 構成

- context 単位。単一ファイルなら `docs/spec.md` の `##` が context、小分けなら `docs/spec/<context>.md`。どちらにするかはリポジトリの現状に従い、新規なら初回に一度だけ聞く。
- context の冒頭に行為の一覧（actor 視点で何ができるか）を一行ずつ置く。台帳の散文要約になり重複するが、読み手の入口として要る。
- 機能ごとの節がそれに続く。一つの節が一つの全体としての振る舞いを、要素の相互作用として説明する。装置ごとの節は作らない。

## ソースパスを書かない

spec が辞書の語で書かれていれば、読み手は語 → `dict-search.js`（`src` フィールド）／接続マップ（`implements`）→ src と辿れる。
接続マップはコードの `@vocab` アノテーションから生成されるのでコードに追随するが、spec に書いたパスは追随せず腐る。
だから spec は「入口を見つけるための言及」に留め、依存の網羅は接続マップに委ねる。
契約の一部であるパス（設定ファイル、永続化ファイル、キャッシュディレクトリ）は「参照」ではなく「内容」なので書く。
`implements` が空の語があるのは接続マップの欠けであり、spec 側で救う理由にはならない。

## 書かないもの

未清算の振る舞い（外れ側・findings が帰属したもの）、経緯・理由（problem.md／アーカイブ）、プラン名・findings 番号・テストパス（台帳が持つ）、履歴（git）、葉の詳細。

## 読む側

- tdd-problem 手順3: spec を「適切さの出発点」の第一候補として読み、`**関連設計資料:**` に節見出しまで書く（feedback の書き先になる）。
- tdd-run decompose: 既存の振る舞いを変えるプランでは、関連設計資料の節を「現在の契約」として読む。書かない。
- tdd-refactor: 入れない。診断は圧縮された自己記述（辞書・台帳・依存グラフ）だけで理解が復元できるかを見る設計で、spec を渡すと復元テストの意味が変わる。spec が充実しても診断は素通し。
- tdd-vocab init: 既に読む。

## 保留

- rationale.md への追記（`docs/` の四つ組、spec の位置づけ）。このメモを見てもらってから諮る。
- 六要素をテンプレートに固定するかどうかは、何周か回してから判断する。いまは目安。
- 独立スキル化（`/tdd-spec`）は feedback 以外の呼び出し口が要ると分かってから。
