# 望みの一覧（prospective な行為）・後回しの明言・人手で確かめられる状態 — 欠落の認識と原案

**日付:** 2026-08-20
**性格:** 欠落の認識と、補い方の原案。まだ skill ではない。
**発端:** `docs/notes/2026-08-17-model-rearrangement.md` と同じ事例（概念の混線の手前で起きていたこと）。概念の混線とは別の欠落なので別ノートにする。
**状態（2026-08-28）:** (a) 人手で確かめられる状態は、[2026-08-21 の検討](./2026-08-21-interaction-place-and-integration.md) §6 の形で実装した（problem の「操作の筋書き」と、合成の組み込みでの人手の再演）。(b) 後回しの明言は、その再演の findings に書く形で暫定的に受け止める。(c) 望みの一覧は未着手・別トラック。

## 1. 発端（時系列）

事例で兆候が現れた順序は次のとおりだった（概念の混線はこの後に見えた）。

1. 既存の行為（公開・非公開・取り込み）を新しい手段でも維持する、というプランを実装し、feedback に入った。
   利用仮説は期待側だったが、作者が本来やりたかったこと（git の無いコンピュータで運用を始める）には手が届かなかった。
   入口がひとつも用意されておらず、「手動で検査できる」が自明でなかった。
   技術手段の追加が先に来ていたが、それは明言された選択ではなかった。
2. 作者の望む入口（認証情報をどこで取得しどこに置くか）を problem で検討し始めると、綻びが次々に見つかった。
   problem.md は書かずに中断した。
3. 中断して分かったこと——「未検討事項によって設計の全体が崩れることがありうるのだから、手段の置き換えより先に未検討事項を潰すのが妥当だった」。
   新しいユースケースを検討するときに、未検討のユースケース群をまるで検討しなかったことが問題だった。
   うまくいけば手戻りは無いが、悪い場合は再設計を含む大きな手戻りになる。
4. その後で、概念の再配置の必要性が見えた（→ `model-rearrangement.md`）。

作者の振り返り:
- 最初に problem を組み立てるとき、AI は既存の辞書・システムを踏襲する側に誘導した。
- 作者には「今回の事案は現在の設計では足りないだろう」という予感があり、設計を先にやった方がよさそうだと思っていた。
  その設計行為には概念の再検討も含まれるはずだが、現状のワークフローで設計を担う tdd-run/decompose はそこまで担わず、problem は「できない」を定義する場で設計案を考える場ではない。
- つまり「未検討のユースケース群を見渡し、概念の再配置を含む設計案を練る場」が存在していない。

## 2. 欠落の認識

事例から三つの別の欠落が読める。

### (a) 人手で確かめられる状態が作られる拍が無い

feedback は人間の実使用を前提にしている（「緑 ≠ 完了」「run は利用可能な状態まで持っていき、feedback が実使用と照合する」）。
しかし体系のどこにも「利用仮説の操作を人間が実環境で行える——接続先・認証情報・設定・入口が用意されている、または手順が書かれている」を確かめる拍が無い。

- 利用仮説はツリー承認時に「使ったらこうなるはず／こうなったら外れ」の形でユーザーと書く（`tdd-run/subcmds/decompose.md` 手順 6）。操作に要る前提は書かない。
- compose の統合は「ユーザーが触れるエントリーポイントに統合する」「情報が足りなければ合理的なデフォルトで統合し findings に記録」まで（`compose.md` の統合）。
- feedback は「利用仮説に『試してほしい操作』があれば照合から入れる」（`tdd-feedback/skill.md` 1-1）。
- 受け入れテストは操作手順を記述するが、外部接続はフィクスチャで代替されるので、緑でも人手で試せるとは限らない。

緑と「人手で試せる」は別のことなのに、体系はそれを区別していない。
事例では、手段を追加したプランが緑で終わり、いざ使おうとすると確認用の手順がどこにも考慮されておらず、利用できなかった。
「人手での確認の仕方が分からない」ことによって、大量の見落としが事後的に発見された。

### (b) 後回しを明言する拍が無い

技術手段を先にやること自体は構わない。
問題は、それが「技術手段の実現をまず優先する」と明言されての活動ではなかったこと、後回しにされたユースケースの中に設計の形を変えうるものがあったのに、誰もそれを問わなかったことである。

problem 手順 4 の「新しい行為と既存の行為の維持を分ける」（2026-08-17 追加）は、この事例の直接の帰結として「維持に寄って新しい行為が範囲外に落ちる」を防ぐ手当てになっている。
残っているのは「後回しにしたものが今回の設計の形を変えうるか」を問う拍である。
これは problem には判断できない（設計の形を知らない）。設計の場である decompose なら判断できる。

### (c) まだ問題にしていない望みを置く場所が無い——回顧の地図しか無い

この体系が持つ地図は全部、済んだもの・立ったもののものである。

- 辞書 — 承認された概念
- 台帳（acts.json）— 使用で清算された行為
- spec — 清算された振る舞いの説明
- problem 手順 5「他の問題との関係」— 既に立っている problem.md

まだ問題にしていない望み（prospective な行為の候補）を置く場所が無い。
problem は一度に一つの問題を立てる設計なので、隣は見えない構造になっている。
事例で欠けていたのは、設計でも分解でもなく、「git 無しマシンで運用を始める」「認証情報をどこで取得しどこに置くか」という望みが作者の頭の中にだけあって、どこにも書かれていなかったことである。
書かれていれば、手段の追加を先にやるという決定は「これらを後回しにする」という明言を伴えた。
**望みの一覧が無ければ「後回しにする」と言えない。** (b) は (c) に依存する。

UI・UX の検討でも同じ理由で困る。
rationale §5 の UI 層は「UI はできるツリーの分解ではなく合成の最終段階で命名する」——UI は能力の下流に置かれ、入口は統合時に登録される。
これも回顧的である。
画面や導線は複数のユースケースを一枚に合成するもので、一つずつ足していくと導線が継ぎ足しになる。
rationale 自身がこの節を「開いたままの課題」と書いている。

## 3. 原則との両立——禁じられているのは「AI が埋める・先に切る・固定する」であって「見渡す」ではない

「分解は実装者の責務、事前フェーズに固定しない」は**解決側の構造**（能力ツリーの装置層、合成の形）の話である。
ユースケース＝行為層（「<役割> は … できる」）はその上にあり、分解の対象ではなく分解の起点。行為の言明を先に持っていても装置の分解は固定されない。
だから「ユースケースを並べること」はこの原則に反しない（初稿では粗く「衝突する」と書いたが、言い過ぎ）。

この体系が「一度に一つの問題」の形になっていて隣を見渡す場が無かったのは、別々の三つの原則による。それぞれ何を禁じているかを分ける:

1. **AI は差異の源ではなく引き出し役。** AI が候補を出して本人の望みを引き出すのは、引き出し役の仕事そのもの。AI による洗い出し自体はよい。一覧に入るかは本人が決め、由来（本人が言った／AI の候補を本人が採った）を残す——それっぽい候補が増えても見分けがつくように
2. **観察をまず分節せずに受け取る**（problem の鉄則 2）。ユーザーのまとまった望みを AI が複数のユースケースに切り分けるのは、それ自体が構造化の行為。切るなら候補として出し、本人に確かめる
3. **深いモデルは再編成から生まれる。** ユースケースの意味は概念が組み替わると読み替わる（事例の「公開する」）。今日の言葉で書いた一覧は仮のもので、仕様として固定して構造を導出する元にはできない。**禁じられているのはこれ——一覧を固定した仕様として、事前に構造を導出すること。** 早すぎる最適化と同じ問題で、形は使用と再編成の中で見えてくるのに、先に決めてしまう

したがって「全ユースケースを事前に洗い出して設計する」が原則と衝突するのは、洗い出しではなく、**それを固定した仕様として事前に構造を導出する**からである（肝は 3）。
望みを並べ、問題を立てるときに隣を見て、後回しを意識的に決め、概念が組み替われば読み直す——これはどの原則にも反しない。
3 の「読み直す」ができるように、一覧は清算された台帳とは別に、仮のものとして置く（概念の診断の申し送りが一覧に行く、という接続がその例）。
一覧は地図であって約束ではない。設計しない、分解しない。

UI・UX についても同じ言い直しになる——「洗い出せない」のではなく、「洗い出しは仮で、人間の言葉でしかできず、形は後で変わる」という制約の下で行う。展望の地図はあってよい。約束ではないだけ。

## 4. 望みの一覧（原案）

### 性格

- **ユーザーの言葉で書かれた「<役割> は … できる」の一覧。** フィーチャーの一覧、ロードマップに近い。
- tdd-problem の「できない」の定義は、この一覧のフィーチャーを実現するにあたって取り除くべき障害を特定する作業、と読める。
- **台帳（acts.json）の展望側。** 台帳が「使用で清算された行為」なら、こちらは「まだ清算されていない・問題にもしていない望み」。claim の形を揃えておくと、一覧 → problem の「この問題で成立する行為」→ root → 登記、という流れが一本になる。
- **入るかどうかは本人が決める。** AI が候補を出すのはよい（引き出し役）。一覧に書くのは本人が望みとして認めたものだけで、claim は本人の言葉。由来（ヒアリング・feedback・概念の診断の申し送り・AI の候補を本人が採った）を残す。
- **設計しない・分解しない・優先順位を付けない。** 書くのは望みと、後回しにしたならその理由と日付まで。

### 形（案。2026-08-20 に構造化へ改訂）

これは backlog である。作者が欲しかったのはまさに backlog であり、この体系の地図がすべて回顧的だという §2 (c) の裏返しとして正しい欲求である。

**構造化する。acts.json と同じ claim の形で、別ファイルに置く。フィールドは最小に。**

- `id`（例: `wish-NNNN`）— problem.md の「この問題で成立する行為」がこの行を指せる。望み → 問題化 → root → act-NNNN の流れを辿れる
- `actor`・`claim` — 台帳と同じ形。claim はユーザーの言葉のまま
- `origin` — 由来（feedback の F-nn／problem のヒアリング日付／概念の診断の申し送り）
- `deferred` — 後回しの履歴 `[{ date, reason, plan }]`。消さずに積む
- `status` — open ／ problemized（plan 名）／ settled（act id）／ dropped（ユーザーが「もう望んでいない」と言った日）
- `context`・入口 — 分かるときだけ。decompose が「同じ入口・装置に触る望み」を引くための手がかり

**作らない欄: 優先度・見積もり・担当・期限。** 欄があると埋めたくなり、そこから backlog の腐敗が始まる。形式の側でできる防止策はこれだけである。

初稿では「Markdown 一枚、スキーマにしない（backlog の問題——AI が量産し、陳腐化し、誰も読まない——を呼び込む）」としたが、撤回した。
腐る原因は形式ではなく、誰が書くか・いつ読むか・いつ消すかである。
Markdown でも AI が埋めれば量産され、JSON でも「ユーザーの言葉だけ・承認を得て・problem 手順 5 と decompose 手順 2 で必ず読む」が守られれば腐らない。腐敗防止は統治の仕事で、形式に託すものではない。
「機械チェックのためだけに形式化しない」という指針はここには当てはまらない——構造には機能的な用がある（id での参照、ライフサイクル、context・入口での絞り込み、台帳との対称性。この repo では dictionary.json・acts.json が構造化されていて、Markdown 一枚はむしろ例外）。
Markdown の利点は「ユーザーが自分の手で直接書ける」こと一つで、書き込みツールを薄く用意すれば構造化でも同じことができる。

置き場所は `docs/` 側（辞書・台帳・spec と同じ層）。ファイル名・id の接頭辞・ツール（`acts-write`／`acts-search` の流儀を踏襲するか）は開いた問い。

### 誰がいつ書くか

- **problem のヒアリング**: 「やりたいこと」のうち今回の問題にしないものが出たら、ユーザーの言葉で一覧に足す（承認を得て）。今回の問題にするものは一覧から「問題化」に進む
- **feedback**: 発見のうち「新しい問題意識」に分類されるものを、problem を立てる前の段階で一覧に置ける（すぐ問題化しないものの置き場ができる）
- **概念の診断（`model-rearrangement.md` §8 の diagnosis.md の申し送り）**: 再配置の後に新しく成立しうる行為は、ここに置く。再節合と feedback を経て辞書が直ったら、ここから problem を立てる
- **UI・導線の検討**: 一覧を横断して見られる（入口・導線は複数の望みを一枚に合成する）

### ライフサイクル

- 望み → 問題化（plans/<project>/problem.md の「この問題で成立する行為」に移る）→ 清算（台帳に登記）。一覧の行はチェックされ、行き先（プラン名・act id）が残る
- 後回しにした望みは消えない。理由と日付が積まれる。同じ望みが何度も後回しになっているのは信号
- 消すのはユーザーが「もう望んでいない」と言ったときだけ

## 5. 後回しの明言（(b) の原案）

- **tdd-problem 手順 5（他の問題との関係）**: 既に立っている problem.md に加えて望みの一覧を見る。「隣にこれがあるが、今回は後回しでよいか。理由は」を本人に問い、後回しにするものは一覧に理由と日付を書く。problem.md のスコープ外にも「後回し（理由）」として書く
- **tdd-run decompose 手順 2（エントリーポイントの宣言）**: 望みの一覧のうち、今回と同じ入口・装置・環境に触るものを挙げ、「これを後で入れると今回の形が変わりうる」をユーザーに見せる。形だけ先に検討するか、手戻りを承知で進むかはユーザーが決める。決めたことは test-tree.md に一行残す
- 分解は設計の場なのでこの判断ができる。problem は設計の形を知らないので、problem では「後回しにする」の明言まで

## 6. 人手で確かめられる状態（(a) の原案）

**利用仮説の形に「人手で確かめる操作と、その操作に要る前提」を持たせる。**
利用仮説は run と feedback の間の契約として既にあるので、ここに列を足すのは体系的な変更になる。

- **decompose 手順 6（利用仮説）**: 「使ったらこうなるはず／こうなったら外れ」に加えて、「人手で確かめる操作」と「その操作に要るもの（実環境の接続先・認証情報・設定・入口・ガイド）」を書く。要るものが今回のプランの中で用意されないなら、その時点（実装前）で表に出る——用意するか、後回しにするか（→ §5 の明言）をユーザーが決める
- **compose の統合**: 利用仮説の前提が揃っているか（用意された／手順が書かれた）を出口で確かめる。揃っていなければ「人手で確かめられない」ことを findings に書いて終える（緑でも利用可能な状態ではない）
- **feedback 1-1**: 利用仮説の「人手で確かめる操作」から入る。操作ができなかった（前提が無い）なら、それ自体を発見として書く——戻し先は tdd-run（統合）。仮説の外れ側とは区別する
- **problem（「解決したと言える状態」）**: 「それが解決したと、あなたはどう確かめますか」を添える。問題の言葉の範囲で、確認の前提が早く出る

受け入れテストがフィクスチャで外部接続を代替しているプランでは、この前提が必ず要る。

## 7. 「設計案を練る場」との関係

作者の振り返りにある「未検討のユースケース群を見渡し、概念の再配置を含む設計案を練る場」は、まだどこにも無い。
`model-rearrangement.md` の概念の診断は辞書の側だけを扱う。
その場が要るとしたら、望みの一覧と辞書を一緒に眺める場になるはずである（Evans の exploration に近い）。
ただし、場より先に一覧が無いと眺めるものが無い。
§4〜§6 を入れて一度回してから、その場が本当に要るかを見る。

## 8. 開いた問い

- **一覧の名前と置き場所**: 「望みの一覧」「フィーチャー一覧」「ロードマップ」「prospective acts」「backlog」。`docs/` 直下の JSON（acts.json と同じ claim の形）。acts.json の中に status で混ぜない（台帳は「清算済み」の意味を保つ）でよいか。書き込み・検索のツールを `acts-write`／`acts-search` の流儀で用意するか、最初はユーザーが手で書くか
- **tdd-userstory との関係**: ユーザーストーリーはプラン単位で書かれる。一覧の一行がストーリーの種になる、でよいか
- **AI の候補の扱い**（2026-08-20 に決着）: AI が候補を出すのはよい。一覧に入るかは本人が決め、由来に「AI の候補を本人が採った」を残す。禁じるのは一覧を固定した仕様として事前に構造を導出すること（§3 の 3）
- **後回しの繰り返しの扱い**: 同じ望みが何度も後回しになるとき、feedback の「再発」と同じ重さで扱うか
- **利用仮説の前提と受け入れテストの関係**: 前提（実環境接続）が受け入れテストでは代替されるとき、人手の確認手順を test-tree.md に書くか、別の場所（README・ガイド）に書くか
- **rationale への追記**: 「回顧の地図と展望の地図」「禁じられているのは固定であって見渡しではない」は rationale §1 か §6 に置くべき内容かもしれない。運用後に諮る
