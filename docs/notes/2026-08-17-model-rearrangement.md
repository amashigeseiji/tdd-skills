## 1. 発端

利用プロジェクトの公開まわりのコンテキストで、あるプランの /tdd-feedback → 三分割の /tdd-problem と進める途中、ヒアリングで「問題定義の手前にもっと基礎的な結び目がある」ことが見えた。辞書の `リモート` が三役（原稿の共有場所／配信経路の入口／「公開済み」の完了点）を一人で演じ、記事ごとの公開／未公開が「場所（リモートにあるか）」で実現されているため、**原稿を共有する操作と記事を公開する操作が同じ一手に潰れていた**。作者の日常語では「公開する＝配信する。それ以外の読みはない」のに、辞書と二つの実現はどちらも「原稿を共有リポジトリに置く」を公開と呼んでいた。

この混線が、直前のプランで「取り違えた問題」を定義する原因にもなっていた（findings に「解いた問題は成立したが、作者の主要ユースケースは範囲外に置かれていた」が上がっていた）。problem.md は書かずに中断し、tdd-* を前提にせず別セッションで概念の配置を議論した。結果は発端事例のメモの §10〜§14（混線の核・新しい配置と旧→新の対応・決まったこと・開いた分岐・次の一手）。

作者の所感: **「現状の tdd-* で、こうした概念の再配置・再設計を議論する場がなく、混線したままの概念で問題定義を行い、あとから問題定義が正しくできていないことがわかる、あるいは誤解があるまま進んでいく、などがたまにある」。**

## 2. 欠落の認識

現行の体系は、翻訳の連鎖（rationale §6）のうち

- problem: 人間の経験 → 問題の言葉
- tdd-run: 辞書を媒介に、問題 → テストツリー → 実装
- feedback: 使用経験 → 問題理解
- refactor: コードの診断（problem の鏡像。「現状のコードの何に問題があるか」をコードの言葉で）

を持ち、辞書は「人間が保持する固定点」として最も安定な遠位項に置かれている（rationale §5「安定性の非対称」）。**その固定点自身が間違っているとき——一つの語が複数の役割を兼ねている、定義同士に緊張がある、実現の姿が定義に逆流している——の手続きが無い。**

- `/tdd-vocab check` が見るのは孤立・リンク切れ・矛盾で、「網の張り方が違う」は検出しないし、直す場でもない。「再定義は check を経る」は個別エントリの手続きであり、複数エントリの役割分割・新設・移し替えを一体で扱う場ではない
- `/tdd-problem` は「やりたいこと／阻むもの」を問題の言葉で立てる場。既存語彙で「語れない概念」は種として申し送るが、既存語彙が「間違っている」（語ろうとするとユーザーが違うと言う）ケースの出口が無い。混線したまま problem.md を書くと、混線が問題定義に刻まれる
- `/tdd-refactor` はコードの診断で、鉄則は「再設計案を書かない」。概念の再配置は人間の承認で固定点を動かす作業であり、tdd-run の再節合（AI がコードに棲みつく場）に委ねる性質のものではない
- `/tdd-feedback` は混線の**兆候**を最初に見る場（解いた問題と実際の用が食い違う型）だが、実装への棲みつきから距離を置くための別セッションであり、そこで再配置まで行うのは役割の混在

DDD の言葉ではこれは *Refactoring Toward Deeper Insight*（Evans, Part III）——「暗黙の概念を明示化する（Making Implicit Concepts Explicit）」「一つの語が複数の役割を兼ねていることに気づく」——で、コードのリファクタリングでも問題定義でもない。rationale §5 の注「ローン出資は銀行用語ですらなかった」の瞬間と同型で、**アンカリングは対話によるギャップの発見でのみ解除される**。今回それが起きたのは、スキルの外だった。

## 3. 位置づけ（既存フェーズとの違い）

| 場 | 主語 | 何を語るか | 出力 |
|---|---|---|---|
| tdd-problem | ユーザー | 何ができない・何が阻む（問題の言葉） | problem.md |
| tdd-refactor | コード | 現状のコードの何に問題があるか（コードの言葉） | diagnosis.md |
| **モデルの再配置（tdd-refactor の概念の診断ジャンル）** | **辞書（概念の網）** | **どの語がどの役割を兼ね／欠き、どこで溶接されたか。役割で分け直した配置** | **概念の診断ジャンルの diagnosis.md（辞書には書かない）** |
| tdd-run | ツリー・実装 | 分解・合成・再節合 | test-tree / 実装 / plans 辞書 |

（2026-08-19 改訂）出力は新プランの diagnosis.md で、出口は tdd-run 再節合の一本。辞書の redefine・新設はその再節合プランの中で行い、そこで波及範囲を見る。新しく成立する行為は再配置の**後**に、直った辞書で /tdd-problem を立てる（追記 §19）。
初稿は「再配置メモを出し、problem か refactor に手渡す」の二出口だったが、tdd-refactor の出口は tdd-run であること、再配置自体は挙動保存（名前・境界・claim の意味が変わるだけ）であることから一本にした。

## 4. 配置（入口・出口・セッション）

```
feedback ──(問題の発見)──────▶ tdd-problem
   │  ──(ツリー・実装の修正)──▶ tdd-run
   │  ──(構造・品質の懸念)───▶ tdd-refactor（コードの診断）
   └──(概念の混線)─────────▶ tdd-refactor（概念の診断）──▶ 新プラン diagnosis.md ──▶ tdd-run 再節合 ──▶ feedback ──▶ （必要なら）tdd-problem
                                    ▲                          （辞書を wip で直し、波及を見る）    （promote・supersede・spec）  （直った辞書で新しい行為を立てる）
tdd-problem ──(ヒアリングで既存語彙が「間違っている」と分かる)─┘
```

（図は 2026-08-19 に一本の出口へ改訂。初稿は「【モデルの再配置】→ tdd-problem または tdd-refactor」の二出口）

- **入口は三つ。** feedback の戻し先の四つ目「概念の混線」。tdd-problem のガード（既存の語彙で語ろうとするとユーザーが違うと言う＝語彙が足りないのではなく間違っている、と分かったら problem.md を書かずに中断してこちらへ）。tdd-refactor 自身（ユーザー起点のヒアリングで「言葉が違う」と分かる、トリアージで辞書内部の兆候が重なる）。→ 追記 §17
- **出口は一つ。** 辞書には書かない。合意した配置を新プランの diagnosis.md に書き、tdd-run 再節合へ渡す。辞書の redefine はその再節合プランの中で行う——波及範囲（辞書・台帳・実装・受け入れテスト）はプランでしか見えないから。新しい行為はその後に /tdd-problem で
- **別セッションで行う。** feedback・refactor と同じ論理。実装文脈が残っていると、定義を読み直さず実装の姿から語り、溶接を無批判に引き継ぐ（発端事例の §3.4 で Claude に実際に起きた失敗）
- **AI が勝手に入らない。** AI は概念を並べ替えたがる。入口は上の二つのトリガーに限り、人間の承認で開く

## 5. トリガー（兆候）

どれか一つでは開かない。複数重なる、または人間が「言葉が違う」と申告したときに開く。

- feedback で「解いた問題は成立したが、ユーザーの実際の用と食い違っていた」が出る。とくにそれが同じ context で繰り返す
- problem のヒアリングで、既存の辞書の語で「やりたいこと」を書くとユーザーが訂正する。訂正が「その語の意味が違う」の形をとる
- 一つの語が、複数の problem の「阻むもの」側に繰り返し現れる
- 辞書の定義文同士に緊張がある（例: `成果物`「最終的に公開されるのは常にこれ」vs `リモート`「ここに反映された状態が公開済みの実体」）
- 一つのエントリを references する側の理由句が、互いに異なる役割を指している（例: `リモート` が「反映先」「取り込み元」「実反映の起点」と三通りに呼ばれる）
- 定義が抽象のまま、実現がすべて一方の形に寄っている（定義にある道が一つも動いていない）
- ユーザーの日常語とシステムの語の意味がずれていることを、ユーザーが繰り返し言い直している

## 6. 鉄則

tdd-refactor の「再設計案を書かない」の鏡像として、この場には別の鉄則が要る。

1. **定義文から始める。実装から語らない。** 辞書のエントリを引用して読み、それが何を言っているか・言っていないかを確定してから、実現の姿を見る。混線は定義文そのものより「その周りの取り決め」に宿ることが多い（発端事例では `公開する` の定義文は抽象的で正しく、完了点の置き方・sync 操作の溶接・実現の偏りの三つが混線の出どころだった）
2. **ユーザーの日常語をアンカーにする。**「公開する＝配信する。それ以外の読みはない」がすべての出発点。エヴァンスの「エキスパートが理解できないと言い続けていた語」と同じ扱い。システムの語がそれとずれていたら、ずれているのはシステムの語
3. **物と役割を分ける。** 中心概念ごとに「どの役を演じているか」を列挙する。一つの物が複数の役を兼ねている／ある役を演じる物が無い（暗黙）が混線の典型。役割で分け直し、「一つの物が両役を兼ねる」場合はそれを明示できる形にする（分けた効用）
4. **どのプランで溶接されたかを辿る。** archives の problem.md は決定の履歴。「なぜそう決めたか」が読めるので、単純な誤りか、当時は正しく今は前提が変わったのかを区別できる
5. **先取りしない。** 配置の中でしか決められない問い（例:「公開済みは配信の実反映まで含むか」）は分岐点として残し、推しは書くが決めない。決めるのはユーザー
6. **辞書に書かない。台帳にも触らない。** 出力は論点メモと diagnosis.md。波及の見立ては書くが、redefine・supersede は再節合プランの中で
7. **新設は役割の欠けを埋めるものに限る。** 命名のための命名をしない。新しい語は「これまで暗黙だった役割に名を与える」か「兼任を分ける」のどちらかであること

## 7. 手順の原案

1. **起点の確認**: feedback からの依頼か、problem からの中断か、ユーザーの申告か。発端の findings／メモを読む
2. **定義の引用**: 当該 context の辞書エントリを `dict-search.js -f context=<ctx>` で全件、周辺 context の関連エントリを `-d1` で引き、中心概念の定義文をそのまま引用する（要約しない）
3. **役割の列挙**: 中心概念ごとに、(a) 定義文が言っている役割、(b) references している側が理由句で呼んでいる役割、(c) 実現（実装・受け入れテスト・台帳の claim）が事実上担わせている役割、を並べる。兼任と暗黙（役はあるが名が無い）を洗い出す
4. **溶接の出どころ**: archives の problem.md・findings.md から、その配置を決めたプランと理由を辿る。定義文そのものか、周りの取り決めか、実現の偏りか、AI の引き継ぎか、を区別する
5. **ユーザーの言葉の要点**: 日常語での意味、維持すべき制約、いま答えないと決めたこと、責務の外に置くこと、を作者の言葉のまま列挙する
6. **暗黙の前提の棚卸し**: いまその context の中心的な行為を行うとき、暗黙に満たされている前提を表にする（何が・現状どう満たされているか）。ユーザーに「別でよい」「これが混線の現れ」を仕分けてもらう
7. **症状の帰属**: 実利用で観察された症状（findings）のうち、この混線に帰属しうるものを列挙する。帰属が誤っていた項目は訂正する（発端事例では、ある症状の帰属を第2回で取り下げた）
8. **配置の提案**: 役割で分け直した配置を図＋表で示す。旧概念→新概念の対応表を付ける。ユーザーの言葉との突き合わせを一行ずつ行う
9. **決まったこと／開いた分岐**: ユーザーとの対話で確定したものと、残ったものを分けて書く。分岐には推しと理由を添える
10. **波及の見立て**: 辞書（redefine・新設・context のスコープ文）、台帳（claim の意味が変わる登記＝supersede 候補）、実装（抽象・装置）、受け入れテスト、保留中の他プラン、を列挙する。数量感の目安まで。実行はしない
11. **申し送り**: 再配置の後に新しく成立しうる行為（ユーザーが「阻まれている」と言ったこと）を、決めずに列挙する。再節合の後の /tdd-problem の材料になる（§9）
12. **記録**: 新プランのディレクトリを切り、第2回の結果（合意した配置・決まったこと・開いた分岐・波及の見立て・申し送り）を diagnosis.md に、第1回の論点（§8 の §1〜§9）を作業ノートとして同じディレクトリに置く。feedback の findings 側の状態を「対応済み（/tdd-refactor, plans/<新プラン>/diagnosis.md, 日付）」に更新する

## 8. 出力テンプレート（第1回の論点メモと、第2回の diagnosis.md）

発端事例の §10〜§14 を汎化したもの。
書くのは tdd-refactor（概念の診断）のセッションである（追記 §14・§19）。feedback の出力は findings.md の項目までで、feedback ではこれを書かない。
（2026-08-19 改訂）第1回（§1〜§9）は論点の書き出しで、新プランのディレクトリに作業ノートとして置く。第2回（§10〜§14）は配置の合意で、これが**概念の診断ジャンルの diagnosis.md** になり、tdd-run 再節合の入口文書になる。初稿では両方を一枚の「再配置メモ」として `plans/` 直下に置き、problem か refactor に手渡す形だった。

```
# <context> の概念の混線をほどく — 論点（第1回、作業ノート）

**日時:** 第1回 YYYY-MM-DD
**性格:** 入口文書ではない。第2回（diagnosis.md）を書くための論点・懸念の書き出し。
**起点:** feedback（plans/<plan>/findings.md F-nn）｜problem の中断｜ユーザーの申告

## 1. どこから来た議論か        — 経緯（どのプラン・どの findings・なぜ中断したか）
## 2. 作者の言葉（要点）        — 日常語の意味・維持する制約・答えないと決めたこと・責務の外
## 3. 辞書の現状と混線の出どころ — 定義文の引用、兼任・暗黙、溶接したプランと理由
## 4. 暗黙の前提の棚卸し        — 表: 前提｜現状どう満たされているか｜仕分け
## 5. 症状の帰属                — findings のうちこの混線に帰属しうるもの（訂正含む）
## 6. 開いている問い            — 先取りしないと決めたもの
## 7. 懸念                      — 波及・台帳の扱い・どのフェーズに載せるか
## 8. 保留・未着手の一覧
## 9. 参照
```

```
# Diagnosis: <plan>（概念の診断）— <context> の概念配置

**日時:** 第2回 YYYY-MM-DD（第1回の論点: <作業ノートのファイル名>）
**性格:** 再節合型プランの入口文書。診断の主語は辞書。物差しはユーザーの日常語。
**起点:** feedback（plans/<plan>/findings.md F-nn）｜problem の中断｜ユーザーの申告

## 10. 混線の核（一文で）
## 11. 合意した配置             — 図、概念表（役割・候補定義・引き受けた役割 ← 旧概念）、旧→新の対応、ユーザーの言葉との突き合わせ
## 12. 決まったこと
## 13. 開いたままの分岐点        — 各分岐に: 候補、ユーザーの懸念、対話での整理、現時点の推し（決めるのはユーザー）
## 14. 波及の見立て             — 辞書（redefine・新設・context のスコープ文）、台帳（supersede 候補）、実装（抽象・装置）、受け入れテスト、保留中の他プラン
## 15. 申し送り                 — 再配置の後に新しく成立しうる行為（決めない。望みの一覧に置き、再節合の後に /tdd-problem で立てる → prospective-acts-and-usable-state.md §4）
```

## 9. 出口（2026-08-19 改訂: 一本）

- **出口は tdd-run 再節合。** 概念の診断ジャンルの diagnosis.md を入口文書とする新プランで、辞書の redefine・新設を wip に持ち、装置・`@vocab`・テストを新しい配置に沿って引き直す。台帳の行為は維持し、claim の意味が変わるものは supersede 候補として feedback へ申し送る。
  再配置そのものは挙動保存である——現状の振る舞いは変わらず、変わるのは名前・境界・claim の意味。だから再節合の仕事に収まる
- **新しく成立する行為は再配置の後に。** 混線の帰結としてユーザーが「阻まれていること」（発端事例: 下書きを別マシンに持っていけない／資材が手段から届かない／本番構成の差し替えがシステム外）は、diagnosis.md の申し送りに列挙するだけにして、再節合と feedback（promote・supersede・spec）を経て辞書が直ってから、新しい語で /tdd-problem を立てる。先に言葉を直してから問題を立てる——発端の不満（問題定義の時点で言葉が間違っている）への答えはこの順序にある
- **diagnosis.md から直接 `/tdd-vocab promote` で redefine しない**——波及はプランでしか見えず、行為の登記との整合（supersede）もそこで判断する
- 初稿は「problem か refactor か」の二出口だった。tdd-refactor の出口が tdd-run であること、再配置が挙動保存であることから一本にした

## 10. 既存スキルへの変更（提案。追記 §14〜§19 を反映して 2026-08-19 に書き直し）

新スキルは作らない。手続きは tdd-refactor のジャンルとして置く（追記 §14）。フェーズ分け: 1 センサー（feedback・problem・dict-search）→ 2 tdd-refactor のジャンル → 3 tdd-run refactor.md → 4 試走（発端事例を diagnosis.md に起こして再節合）。

- **tdd-feedback**（フェーズ 1。2026-08-19 実装済み）:

# 追記（2026-08-17〜19 の検討）— 置き場所と feedback 側の観察

§1〜§12 を書いたあと、tdd-skills 側で内容を検討した結果。決めたことは §10・§11 に反映済み。ここにはその理由と、feedback 側の観察の言語化を残す。

## 13. 名前の三層

一語で呼ぶと症状・状態・手続きが混ざるので分ける。

- **対話者間の概念の食い違い** — feedback で観察される**症状**。同じ語（例: 公開）で、ユーザーと AI が別のものを指している。findings の項目に書くのはこれ
- **概念の混線** — 症状の背後にある辞書側の**状態**。一つの語が複数の役割を兼ねている、定義同士に緊張がある、実現の姿が定義に逆流している。戻し先の名前はこちら
- **概念の診断（モデルの再配置）** — その状態を扱う**手続き**。tdd-refactor 側のジャンル名

症状と状態を分ける理由: feedback の時点では「食い違いはある。だが混線かどうかはまだ分からない（単なる見落としかもしれない）」が正直な位置。feedback は症状の名で書き、混線と判定するのは診断の側。「観察までが feedback、帰属は戻し先」という既存の分業と揃う。

混線の状態そのものは、ユーザーとの対話を伴わなくても辞書から兆候を拾える（§5 の「定義文同士の緊張」「理由句が三通り」「実現が一方に寄る」）。対話の失敗はその症状として起こる。ただし辞書から見えるのは候補までで、「間違った兼任」か「意図した兼任」かはユーザーの日常語を物差しにしないと決まらない（§17）。

## 14. 置き場所は tdd-refactor（概念の診断ジャンル）

新スキルは作らない。tdd-refactor に「概念の診断」ジャンルを足す。

**なぜ refactor か。**
DDD の *Refactoring Toward Deeper Insight* は主語がモデルで、コードの気持ち悪さ（Scrutinize Awkwardness）とエキスパートの言葉とのずれ（Listen to Language）を同格の兆候として並べ、その先にモデルの組み替えを置く。
2026-08-09 のノートは欠落を「コード品質の評価 → 悪い部分 → 改善案 → 影響範囲」という Fowler 側の操作列で言語化し、その言語化が主語をコードに決めた。
一週間使って、理解の混乱の源はその手前の概念にあると分かった。「refactor という語を Fowler 側に使い切っていた」ので、DDD の語感をこちらに戻す。
実務上も、tdd-refactor は既にユーザー起点のヒアリング・findings 起点・「観察であって再設計案ではない」の鉄則を持ち、再配置メモの第1回（§1〜§9）はまさに辞書の診断でこの鉄則と同型。

**変わるのは物差し。**
現行の tdd-refactor は辞書・台帳を物差しにしてコードを測る（skill.md「診断の軸は、この体系——人間の承認・辞書・台帳・テスト——がコードに接続し続けられるか」）。
復元テストは辞書と台帳からコードを想像しギャップを測るが、ギャップの解釈は「辞書の陳腐化／記述の不足／匿名の処理／未登記挙動／語彙の穴」の五つで、「辞書の網の張り方が違う（兼任・溶接）」は無い。
辞書が混線していてコードがそれを忠実に実装しているとき、復元テストのギャップはゼロになる。**コードの診断は構造的に混線を検出できない。**
検出できるのはユーザーの日常語を物差しにしたときだけ（鉄則 2）。

| 場 | 物差し（アンカー） | 測られる側 |
|---|---|---|
| tdd-problem | ユーザーの経験 | （辞書を使って）問題の言葉を立てる |
| tdd-refactor（コードの診断） | 辞書・台帳 | コード |
| tdd-refactor（概念の診断） | ユーザーの日常語 | **辞書そのもの** |

概念の診断は、この体系で唯一「辞書が測られる側に回る」場。Evans にこの区別が要らなかったのは、モデルがコードと会話の中に生きていて、人間承認つきの独立した固定点（rationale §5）を持たなかったから。この体系は辞書を明示的な固定点にしたので、固定点を動かす手続きも明示的に要る。

**skill 側の帰結。**
skill 名は据え置き、主語が「コード」から「体系（辞書・台帳・コード）」へ広がる。コードの診断ジャンルは既存のまま。
概念の診断ジャンルは、第2回（配置の合意）が「観察まで」を越えるので、鉄則を一つ足す——AI は候補と推しまで、配置を決めるのはユーザー（§6 の鉄則 5 と同じ内容を refactor の言葉で）。
出口は概念の診断ジャンルの diagnosis.md → tdd-run 再節合の一本（§9。初稿は再配置メモを problem か refactor に手渡す二出口だったが、tdd-refactor の出口が tdd-run であることに合わせた）。
復元テストはそのまま残す。辞書からシステムを想起できるかを測る装置としては正しく、そのギャップがコード側にしか出ないというだけ。ユーザー理解とのギャップは運用の軋みからしか出ないので、それを拾う場は feedback（§16）。

## 15. 発掘との関係

Evans の Making Implicit Concepts Explicit のうち、**ボトムアップの半分**（コードの中に名前の無い概念がいる → 名を与える）は既に体系にある。tdd-refactor の「発見」ジャンル → tdd-run 再節合の発掘・語彙作業（wip → promote）。AI がコードに棲みついて見つける方向。
概念の診断は**トップダウンの半分**——既に stable にある概念が、ユーザーの言葉と照らすと間違っている——で、人間が固定点を動かす方向。
新設は「役割の欠けを埋める」に限る（鉄則 7）のはこの区別のため。コードから見つかる新概念は発掘に任せる。

## 16. feedback 側の観察（症状の捕捉）

**症状の形（発端事例を一般化）:**

1. ユーザーが「やりたいこと」を述べる（一台で、git 以外の手段で公開する）
2. AI が**ユーザーが置いていない要件**を根拠に、それを塞ぐ（「それでは複数台での原稿の共有ができない」）
3. ユーザーには根拠が分からない。説明しても繰り返される
4. 優先順位が反転している。ユーザーの主要ユースケースを AI は応用問題か範囲外に置き、ユーザーが応用だと思うものを AI は必須と言う
5. 争点になっている語は双方が日常的に使う語で、定義文だけ見ると異論が無い

AI の反論は**辞書の配置の内側では正しい**（原稿の共有 = 公開が体系に埋まっていれば、共有を前提としない公開は体系内で矛盾）。だから AI は退かず、ユーザーは要件の出所を見つけられない。公理が違うまま議論している。rationale §5 の注の構図で、チーム側に立っているのが AI、エキスパートがユーザー。

**なぜ problem・run では見えず feedback で見えるか。**
problem.md・ツリー・行為層は辞書の語で書かれ、AI の読みはその内側で一貫している。ユーザーはそれを自分のイメージで読むので、同じ語が別の束を担いでいることに気づかない。双方が合意していると思っている——「それっぽい」の正体。
ズレが見えるのは合意の不一致としてではなく**衝突**として。AI がユーザーの望むことを塞いだとき（対話の中）、実使用でユーザーが「できない」に当たったとき（使用の中）。feedback は使用の後に対話を振り返る場なので拾える。

**（2026-08-19 改訂）ズレは聞いても出ない。見えるのは摩擦だけ。**
初稿ではここに「問題定義をユーザーに読み返してもらう三つの問い」（やりたいことは problem.md のどこにあるか／言った覚えのない要件はあるか／納得しなかった反論はあるか）を置いたが、撤回した。
双方が自明と仮定していることは、どちらにも見えていない（近位項に棲みついている）。ズレの内容を後から聞いても出ない。見えるのは、それが衝突したときの摩擦だけ——同じ反論が繰り返される、当たり前の語を言い直させられる、相手が言っていない要件が根拠に出てくる、「あれ？」という感じ。発端事例で気づきが起きたのも、「複数台の共有ができない」を何度も言われて「なぜそれを言い続けるのか」と問い返した瞬間だった。
「気付く」こと自体は手続きにできない。rationale の「深いモデルは再編成から生まれ、手続き化できない。できるのは再編成を試みる契機を用意すること」と同じ位置。気付くのがユーザーか AI かは問わない。できるのは三つ:

1. **摩擦の場面で、AI に自分の前提を明示させる。** AI は自分の暗黙の前提を見られないが、「同じ反論を二度した」ことは検知できる。そのとき再説明せず、根拠を辞書のエントリ・関係や既存実装に遡って言葉にし、ユーザーの前提と同じかを確かめる。ズレを見せるのではなく、片方の前提を表に出して衝突させる。対話の主戦場はヒアリングなので tdd-problem に置く（本来は横断的な規律だが、この体系に横断規範の置き場が無いので、まず problem と feedback に）
2. **気付いた側の申告を一級の入力にする。** ユーザーの「話が通じていない感じ」は根拠を言えないことが多い。説明で押し返さず、そのまま受け取って記録する。AI が気付いた場合も同じ扱い。feedback のインタビューには一問だけ「このプランの対話で、話が通じていないと感じた場面はありましたか」を置く——ずれの内容ではなく摩擦の経験を聞く契機。出るとは限らない
3. **置き場所を用意する。** 気付いたときに行く先（戻し先「概念の混線」）が無いと、問題定義の見落としとして処理されて消える

**規律: 辞書を擁護しない。** ユーザーの発言が辞書の配置と矛盾しても、feedback の AI は訂正せず矛盾をそのまま記録する。feedback の AI も辞書を読んで入るので、放っておくと同じ反論を再生産する。「設計を擁護しない」の辞書版（2 の AI 側）。

**見落としとの区別（同一 plan の再定義に戻すものとの境界）:**

- 見落とし: ユーザーが「X を言い忘れた／条件が違った」と言い、言えば双方が合意する。条件を足せば解ける
- 混線: ユーザーが X と言い、AI（または成果物）が「X はできない、Y だから」と言い、ユーザーは Y を要件と認めない。争点が語の意味にあるので条件を足しても解けない
- 判定の一言: **その要件は誰が置いたか**。ユーザーでなく辞書・実装なら混線の側

**findings に書くもの:** 争点の語、ユーザーの意味（本人の言葉のまま）、AI・辞書側の意味、AI の反論がどのエントリ・関係から来たか、優先順位の反転。`戻し先: /tdd-refactor（概念の診断）`、状態は未処理。これがそのまま第1回の論点メモの §2（作者の言葉）と §3（役割の列挙）の入力になる。

## 17. 入口は三つ、開くのは人間

- feedback の症状（§16）——実際上の主要な入口。ユーザー理解とのギャップは運用の軋みからしか出ない
- problem のガード（§10）——ヒアリングで「語ると違うと言われる」
- tdd-refactor 自身——ユーザー起点のヒアリングで違和感の正体が「言葉が違う」だと分かった、またはトリアージで辞書内部の兆候（§5、`--referrers`）が重なった。現行のままだとこのケースは「辞書の陳腐化」に誤帰属される

どの入口からでも、診断を開くのは人間。辞書内部の兆候は候補を出すだけで、AI がそれを根拠に勝手に始めない（§4「AI が勝手に入らない」）。

## 18. 注記 — Evans との違い

「問題定義の時点で使っている言葉が間違っているから正しく問題を定義できない」を、Evans なら会話の中で連続的に直す（ユビキタス言語はヒアリングの中で研がれる）。
このメモはそれを別セッションの別フェーズに切り出した。「フェーズの責務を混ぜない」というこの体系の側の選択で、代償として「小さな混線でもいちいち中断する」コストが乗る。
体系の哲学から来る選択であって Evans の処方そのものではない、と記録しておく。

## 19. 具体的な流れ（feedback → refactor → tdd-run 再節合 → feedback → problem）

（2026-08-19 改訂: 出口を一本にした。初稿の 4 は「problem か refactor へ手渡す」だった）

1. **feedback**: 利用の中で軋みが出る（1-2 の照合で「成立したが用に届かない」、または印象）。印象の節にユーザーの言葉のまま残す。発見の項目を立て `戻し先: /tdd-refactor（概念の診断）`。**再配置は feedback ではやらない**。クローズ判断は C が既定（このプランはアーカイブし、概念の診断を依頼するよう促す）
2. **別セッションで /tdd-refactor（第1回）**: 起点は findings 起点。戻し先が概念の診断ならコードの診断（4軸・トリアージ・復元テスト）には入らず、概念の診断ジャンルへ。§7 の 1〜7、出力は論点メモ §1〜§9（新プランのディレクトリに作業ノートとして）。辞書・台帳・コードには触らない
3. **第2回**（別セッション既定）: §7 の 8〜12。配置の提案・決まったこと／開いた分岐（推しつき、決めるのはユーザー）・波及の見立て・申し送り（新しく成立しうる行為、決めない）を **diagnosis.md** に書く。findings の状態を `対応済み（/tdd-refactor, plans/<新プラン>/diagnosis.md, YYYY-MM-DD）` に更新
4. **tdd-run 再節合**: diagnosis.md を入口に、語彙作業で redefine・新設を wip に持ち（`/tdd-vocab plan`）、装置・`@vocab`・テストを新しい配置に沿って引き直す。台帳の行為は維持し、claim の意味が変わるものは supersede 候補として申し送る。diagnosis.md から直接 promote はしない
5. **feedback**: promote・supersede の確定・spec の該当節の書き換え。「言葉が違う」が再発しないかを見る（同じ context で再び出れば再発として重く扱う）
6. **必要なら /tdd-problem で新プラン**: 直った辞書で、申し送りにあった「阻まれていること」を新しい語で問題として立てる。先に言葉を直してから問題を立てる
