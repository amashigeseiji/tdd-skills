# 既存実装調査とインターフェース解釈確定についての対話記録

**日付:** 2026-07-18

tdd-run の手順並び替え（`2026-07-18-tdd-run-step-reorder.md` 参照）に続く対話。当初の目的からは
逸れたが、良い方向の議論になったため記録する。

---

## 当初の目的とのずれ

当初考えていたのは、tdd-run の手続きを意味のあるブロックに切り出して名前を与え、**スキル文書自体を
構造的に拡張可能な形にする**ことだった。現状の改訂の仕方は累積的で、チェック項目をアドホックに
追加しがちという問題意識があった。

実際に議論が向かった先は、tdd-run が支援する**対象システムのアーキテクチャ**、特に「概念設計は
どこから始まるべきか」という問題だった。スキル文書の構造化そのものにはまだ着手していない。ただし
今回の議論は、その前提となるアーキテクチャ上の欠落を明らかにするものであり、無駄ではないと判断した。

## 議論の流れ

1. ブロック分けの再検討: 1 / [2,3,4]（テスト・語彙設計）/ [5,6,7]（実装）/ 8（統合）/ 9（チェック）/ 10。
2. 8の統合内のUI語彙設計と、9のユーザーストーリーからの受け入れテスト具体化を、[2,3,4]に
   移すべきではという疑問が出た。
3. これを検討する前段として、「手順2は既存実装を調査しているか」を確認した。結果: していない。
   手順2は既存**語彙**（辞書の概念名）しか確認せず、既存**実装・配線**の調査には接続されていない。
   `tdd-problem` の技術的背景調査（現状実装がなぜ問題を生むか）は診断目的に限定されており
   （`tdd-problem/skill.md:79`「調査は問題を理解するために限る。解決策の探索はしない」）、
   tdd-run側の設計判断には使われていない。
4. rationale.md 3節の診断（AIはコードの中に棲みつく）との緊張関係を指摘した。名前を先に立てる
   設計は、この棲みつき問題への処方だが、既存実装を調べずに毎回新しい「機械」を組み立てることが、
   既存モジュールの修正で済む問題まで純粋モジュールの新規作成に導いている可能性がある。
5. 「UI語彙設計を手順8から手順2に移すべきでは」という提案の根拠を深掘りした。「電灯をオフに
   できる」という例を使ったが、rationale.md 内にこの例は実在しない（検索したが見つからず、出典
   不明のまま議論を継続した）。
6. rationale.md の該当箇所（232-234行目、「UIは機械が埋め込むアフォーダンスを人間に開く
   シグニファイアである（Jacksonのmachine/Normanのsignifier）」）への疑義として、ドアの例
   （取っ手のないドア、開き戸 vs 引き戸）で精緻化した。結論: これは「アフォーダンスの選択」という
   より、「開く」「閉じる」という**語彙の解釈確定はインターフェース確定と相互依存する**、という
   定式化が適切。語彙定義とは曖昧語の解釈体系を確定することであり、インターフェースが決まらないと
   解釈も決まらない。
7. 「記事を削除できる」に適用: ソフト削除/ハード削除という解釈の選択が、`states`フィールドの
   要否を含めツリーの形そのものを左右する。この解釈確定を怠ったまま分解すると、「装置はfooが
   できる」という記述に感じる違和感（言語化未了だったもの）の正体になる。
8. 既存実装調査の役割を確認: 先例に通用しているparadigmがあり、変える必要がなければ新しい解釈は
   不要。辞書と実装は**並行して**調べる必要がある——辞書は改訂されながら運用されているため、実装
   にのみ先例が残っていて辞書に反映されていないケースが十分ありうる。
9. トリガーの粒度について、当初「状態変化を意味する動詞であれば」という目印で合意したが、後で
   これは不十分と判明した（11参照）。
10. 「既存実装調査をしていない」問題と「既存解釈paradigmを確認していない」問題は、同じ一つの
    欠落——手順1/2での既存システム（辞書＋実装）調査の不在——の2つの現れである、という統合に至った。
11. トリガーの再検討。「並び替えできる」を境界事例として試したところ、「状態変化動詞かどうか」
    という見た目の判定では境界が曖昧だとわかった（並び替えは見た目は状態変化っぽくないが、
    ドラッグで永続順序を確定する解釈なら削除と同型の曖昧さを持つ）。REST の resource state /
    application state の区別を経由して、最終的に**不可逆性**が正しい判定軸だと合意した:
    「取り消す操作をしても、系全体が取り消す前と区別不能な状態に戻らない（系の外に取り消せない
    痕跡が残る）か」。ドア・ディレクトリの開閉は取り消せば区別不能な元の状態に戻るので可逆
    （= application state、手段は自由でよい）。記事の削除・公開/非公開は、たとえば一度公開した
    事実が検索エンジンのインデックス等を通じて系の外に漏れ出し、取り消しても消えないため不可逆
    （= resource state、解釈確定が必要）。「ドラッグでの並び替え」も、この基準では実は**可逆**
    （戻せば区別不能）であり、状態変化動詞に見えても解釈確定は不要という結論になった——動詞の
    見た目と実際の要否が一致しない例。
    実用的な言い換え: 「これを（実際に使うかは別として）イベントソーシングで実装したら意味が
    あるか」。ディレクトリの開閉をイベントソーシングするのはほぼ無駄（開いた・閉じたの履歴を
    ユーザーが気にする理由がない）。記事の削除・公開はドメインイベントとして履歴に意味があり、
    監査ログの対象になりうる（実装するかは別問題）。ログファイル等あらゆる操作が何らかの痕跡を
    残るという際限のない話には踏み込まず、実用的な線で運用する。
12. 副作用の有無を技術語彙なしにどう表現するか、という問いが出た。答え: **ドメインイベント**が
    まさにそれ——技術基盤に触れずに「取り消せない事実」を名指す、ドメイン言語側の語彙。これにより
    不可逆性チェックは技術語彙なしで運用できる。副次的な発見として、辞書の`states`フィールドは
    「ドメインイベントによる不可逆な状態遷移」を指すのであって、ディレクトリの開閉のような一時的な
    application stateとは区別すべき、という整理も得た。
13. ここで「手順8のUI語彙設計を手順2に」という当初の提案に立ち返り、ドアの例で再テストした。
    開き戸/引き戸の選択は**可逆**（不可逆性チェックには引っかからない）にもかかわらず、選択した
    瞬間にツリーの内部分解がほぼ確定する（蝶番・かんぬきノード vs レール・戸車ノード）。つまり
    不可逆性とは独立したもう一つの現象がある。
14. この現象の一般性を「記事削除」（ソフト/ハード削除の選択も分解の形を決める）と「リストの
    ソート」（アルゴリズムの選択は分解の形を変えない）で比較検討し、判定軸を特定した:
    **分解の候補同士が異なるアルゴリズムで同じサブ概念を実現しているだけか、それとも異なる
    ドメインレベルのサブ概念そのものを要求しているか**。後者なら、決定しない限り分解を始められない。
    不可逆性はこの現象が起きる理由の一つ（結果が変わるケース）にすぎず、蝶番/レールは別の理由
    （結果は同じだが構造が変わるケース）だが、どちらも同じ軸に収束する。
15. 手順2/4の境界を再検討した。手順2のルート定義（「ドアは開くことができる」）は
    インターフェース非依存のままでよい。問題が起きるのは手順4——分解を進めるとき、対象の意味
    （「開く」とは何をすることか）を確定させる行為と、最初の分解（ドアノブ→ラッチという関係を
    特定すること）が**同一の行為**になる、という点。CLAUDE.mdの「深いモデルは再編成から生まれ、
    手続き化できない。できるのは再編成を試みる契機を用意すること」という原則に照らし、これは
    手順2への事前ゲートではなく、**手順4の分解作業中に、分解候補が異なるドメインレベルの
    サブ概念を要求していないかに気づく契機**として埋め込むべき、と合意した。既存の「構造パターン
    照合手続き」や手順5の命名機会の一時停止と同じ位置づけ。
16. 具体的な組み込み方法として、既存の`wip`/`src`機構を再利用する案に至った。手順4の分解中に
    この決定が必要になった時点で、`domain: "ui"`エントリーを**構造的な仮登録**として書く
    （具体的な画面ファイルがまだないため`src: null`、`wip`ステータス、インターフェースの形
    （例: ドアノブ→ラッチの関係）だけを定義・関係として確定させる）。手順8では、このWIPエントリー
    に`src`を埋め、design-tokenを適用し、実際のエントリーポイントに組み込んで完成させる。
    `domain: "ui"`の定義から空間的配置・見た目を排除し「pageの要素（コンポーネント）である」
    という定義に留めているのは、この構造的側面（インターフェースがどの概念をどう操作するか）と
    意匠的側面（design-token、手順8）を意図的に分離しているためだと確認した。
17. 締めの比喩: ハンドルのない車を考えると、タイヤはあっても「曲がる」ができない。後から
    「右折ボタン」「左折ボタン」を付け足すような設計は破綻する。ハンドルが「タイヤの向きを
    操作するものである」という定義は、システム要件として最初の設計段階に組み込まれていなければ
    ならず、後付けでは部品が足りないという結果にしかならない。
