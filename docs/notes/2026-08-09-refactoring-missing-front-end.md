# リファクタリング工程の前段（診断と改善案の提示）の不在

**日付:** 2026-08-09

行為の登記簿の実装指示 05（refactor.md の典拠差し替え）の先行論点「台帳のスコープ絞り込み」を設計する過程で、より手前の欠落が見つかった。
05 は中断し、この論点を記録する。

---

## 発見の経緯

先行論点は「触る範囲に支えを持つ行為の一覧（回帰面）を台帳からどう引くか」だった。
しかし refactor.md（再節合）の手順を見直すと、そもそも「システムのどこからどこを触るのか」を決める前提が体系のどこにも無い。

一般的に言って、リファクタリングは次の操作の列である:

1. コード品質の評価
2. 悪い部分の発見
3. 改善案の提示
4. 影響範囲調査（= 回帰面の確認）

リファクタリングとは「既存コードに何かネガティブなものがあるから、よりよいコード構造を作る」ことであり、改善したいコードのピックアップと改善案の提示が先に立つ。
現行の体系では、この列の前半三つがどの工程にも正式な居場所を持たない。

## 各候補がなぜ受け皿にならないか

**problem.md — 様式上受け取れない。**
problem は「ユーザーは何ができないか」を問題領域の言葉で語る場であり、コードの不都合を語る場ではない。
コード品質の評価は解決領域の人工物への評価なので、これを problem.md に書くことは体系自身の problem/solution 分離の原則に反する。
無理矢理書かせることはできるが、それはジャンル違反の文書になる。
一方で tdd-run のルーティングは「problem.md に挙動保存が掲げられているか」で再節合型を判定しており、入口が要求する文書を、その文書の様式が書かせないという不整合がある。
手順としてもコードの調査は「何ができないか」を語る範囲に限定されており（調査は問題を理解するために限る）、コード品質の良し悪しの評価はしない。

**findings.md — 拍が遅い。**
findings は診断が入りうる場だが、手順上は通常の compose 実行と feedback を経た後にしか生まれない。
大規模リファクタリングの動機は通常この周回の外から来る。

**観察スキル（tdd-refactor）— 大物を受け流す。**
評価 → 発見 → 改善案の操作列自体は観察スキルにほぼ存在する（観察の視点 (a)〜(f) → 報告と実施計画の提示）。
しかしこれは小さい修正をその場で実施するために作られており、コンテキスト切り出し級の大きい再構成は「/tdd-problem の候補」として一言添えるにとどめる。
つまり受け皿として、様式上受け取れない problem.md を指している。
診断の成果物も残らない（報告はセッションの対話で消える）。

## refactor.md 内の順序の問題

現行の再節合は、回帰面の確定（手順2の回収・手順3の挙動保存の敷設）を設計案の提示（手順4の前提決定・手順5の発掘）より先に置く。
スコープが外から与えられている前提では、この順序は内部的に整合する — 行為層はスコープの既存挙動であり、能力層の設計案に依存しないため。
しかし上で見たとおりその外部が存在しないので、工程全体が浮く。
改善案の提示が触る範囲を決めるのだから、一般的な操作の列としては、評価・発見・改善案が影響範囲調査より先に立つ。

## 開いた論点

- コードを対象とする問題（品質の評価・悪い部分・改善案）を語る場をどこに立てるか。
  新しい工程か、既存工程の拡張かは未設計。
- その場が立った後、refactor.md 内の順序（回帰面確定と設計案提示の前後関係）を見直すか。
- 05 の先行論点（台帳のスコープ絞り込み）は、この論点の解決に依存するため保留。
  典拠差し替え自体（台帳を固定点の典拠にすること）は、前段がどう設計されようと有効な変更として残る。
