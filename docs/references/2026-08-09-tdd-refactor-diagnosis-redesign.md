# tdd-refactor 再設計の骨格案: コードの診断スキル

**日付:** 2026-08-09

## 全体像: 二本の軌道

体系は入口の違う二本の軌道を持つ。

- **挙動が変わる軌道:** tdd-problem（問題の言語化）→ tdd-run decompose → compose → feedback
- **挙動を保存する軌道:** tdd-refactor（診断の言語化）→ tdd-run refactor（再設計）→ compose → feedback

tdd-refactor は**コードにとっての tdd-problem** になる。
problem.md が「ユーザーは何ができないか」を問題領域の言葉で語るのと対称に、診断は「現状のコードの何が悪いか」をコードの言葉で語る。
どちらも次工程（設計）に踏み込まない。

スキル名は tdd-refactor のまま変えない。
tdd-problem が問題を解決しないのと同じ命名法 — スキル名は軌道の入口を指し、セッション内で行う操作を指さない。

## 自己定義の書き換え

現行の「リファクタラー。理解とコードのズレを見つけてコードに転写する」（発見と実施の一体）を、「**コードの診断者**」に改める。

- 診断の対象はコード（解決領域の人工物）。problem.md はこれを様式上受け取れない — コード品質の評価を problem.md に書くことは problem/solution 分離の原則に反する。診断の場はこのスキルである。
- 鉄則: **再設計案を書かない。** どう作り直すかの考察は tdd-run refactor（再節合）の仕事。tdd-problem の「解決手段を持ち込まない」の鏡像であり、「診断を診断のまま捉える」。

## 診断の二ジャンル

診断には性格の違う二つのジャンルがある。

### 1. 評価軸による診断（悪さの検出）

軸は4つ。
人間の動機（理解にコストがかかる・コードの臭い）をそのまま持ち込まず、**この体系 — 人間の承認・辞書・台帳・テスト — がコードに接続し続けられるか**から立てる。
AI はコンテキストが広く、乱雑なコードへの耐性が人間より高い。だから軸の主語をそれぞれ明示する。

- **理解容易性** — 主語は人間。接地は人間から取るという原則の帰結で、人間が読めないコードは承認も接地もできない。
- **拡張容易性** — 主語は変更操作。次の変更がどこに入るかが見えるか、一つの変更が触る面がどれだけ広いか。同じ処理の散在はコピー同士の乖離と見落としを生み、変更の触面を広げる — 散在の負の面はこの軸に吸収する（独立軸「処理の散在」は立てない。理由は後述の発見ジャンル）。
- **頑健性** — 誤用・境界・失敗に対する壊れにくさに加えて、**テストの張りづらさ**を含む。witness が張れない構造は挙動保存が観測できず、リファクタリング自体を不可能にする（台帳の witness 必須の規約と直結）。
- **匿名の処理** — 主語は体系。名前を持たない処理は辞書から指せず、台帳の witness からも辿れない。AI にとっての問題は「読めない」ではなく「**指せない**」— 語彙が定義する行動可能空間の外にコードが漏れていること。

この軸の体系はループを貫通する:

> 診断「この範囲は軸Xが悪い」（tdd-refactor）→ 利用仮説「軸Xが改善するはず」（tdd-run refactor の「構造の改善」）→ 清算（compose のブラインドレビュー＋実使用の feedback）

診断がそのまま検証可能な約束になる。
tdd-run/subcmds/review.md の現行軸（5軸、「処理の散在」を含む）との整合は実装時に調整する。

### 2. パターンの発見（潜在的な概念の検出）

共通化は欠陥の検出ではなく、**積極的な発見**である。
繰り返し現れる形を見つけて名前を与え、処理の再配置を検討する行為であり、「散らばりを直す」こととは性格が違う。
この体系は plans ごとに実装を積み重ねるので、同じような処理が別々のプランから独立に生まれるのは体系の正常な帰結であって、誰かの過失ではない。

- 現行の観察の視点 (e)（コンテキスト横断の構造パターン、B の同一性）と (f)（共通型の抽出）は、このジャンルの手続きとして再配置する。インフラ的な横断関心事とサブドメインの萌芽の区別（現行 (e) の区別）はここで生きる。
- **観察までが診断。** 「同じ形が複数箇所に現れている」という事実の報告までを行い、名前を与えて括り出すのは設計側（tdd-run refactor の語彙作業・発掘）の仕事。
- 将来の拡張: UI パターンの発見（同じような手順を踏むユーザー操作は同じような UI で処理できたほうがよいのではないか、という診断。design token への括り出し等）。v1 には入れないが、ジャンル構成はこのまま受けられる（発見ジャンルの手続きを一つ足すだけ）。docs/notes/2026-07-17-ui-vocab-domains.md と接続する。

現行の (a)〜(f) の再配置先:

| 現行視点 | 再配置先 |
|---|---|
| (a) 意味的な整合 | 評価軸（理解容易性・匿名の処理）の手続き |
| (b) 構造的な正確さ | 衛生（その場修正・ツールの check） |
| (c) 理解可能性 | 評価軸（理解容易性）の手続き |
| (d) 未使用コードの削除 | 衛生（その場修正） |
| (e) コンテキスト横断の構造パターン | 発見ジャンルの手続き |
| (f) 型の欠如と共通型の抽出 | 発見ジャンルの手続き |

## 三層のスコープ構造

二つのジャンルは自然なスコープが違う。
評価軸は狭く・深く、発見は広く・浅く。

1. **全体・浅い（トリアージ＋発見）** — 入力は圧縮された自己記述のみ: 辞書・acts.json・依存グラフ・接続マップ・git の変更頻度・findings の履歴。コードは開かない。出力は (a) context ごとの症状の目星（どの context を深く診るべきか）、(b) 発見の候補（複数 context に現れる似た形、複数の枝から出ている共有断片）。
2. **context 単位・深い（評価軸）** — 選ばれた context に対して4軸の評価と復元テストを実行する。絞る単位が context なのは、それが体系自身の境界概念だから（辞書の context、acts.json の context フィールド、context.dir とコードディレクトリの対応）。
3. **候補単位・確認（発見の深掘り）** — 発見候補ごとに、関係する断片だけを横断して開き、同一性を確認する。

どの context を深く診るかは、ユーザー指定でもトリアージの提案でもよい。

**境界の辺の診断**を context 単位の診断の必須の下位手順にする。
この context のディレクトリから外へ出る依存と、外から入ってくる依存を依存グラフで列挙する。
境界を越える辺は共有基盤・概念の漏れ・横断機能の候補がいる場所であり、スコープを絞っていても横断の徴候はスコープの内側から見える。

## 診断の手続き（道具）

### ブラインド復元テスト

コードを一切読まずに、辞書と acts.json だけからシステム（context）を想像させ、想像された像とコードのギャップを測る。
辞書と台帳はシステムの地図であり、これは「地図だけから土地を復元できるか」という生成的なテスト。
語彙が良く連結されていれば正しい像が生成でき、孤立したアドホックな概念の集まりからは貧しい像しか生成できない — 生成の質そのものが語彙の質の診断になる。

規律:

- **反証可能な形式でコミットさせる。** actor ごとに「何が実行できるか」、行為ごとに「エントリーポイントはどこにあるはずか」「どんな装置・データ概念が支えているはずか」。曖昧な像は何とでも一致してしまう。
- **由来の刻印。** 像の各主張に「どの辞書エントリ・どの登記から導いたか」を付けさせ、資料が沈黙していて推測で埋めた箇所には「仮定」の印を付けさせる。ギャップの帰属（資料が誤導したのか、沈黙していたのか）に必要。
- **サブエージェントでブラインドを構造的に保証する**（review.md と同じ手法）。想像者には辞書と acts.json のパスだけを渡す。
- 挙動の側のギャップは witness の実行で機械的に測る。想像者には外部依存の仮定（この context は外部に何を頼っているはずか）も述べさせ、境界の辺の実測と突き合わせる。

ギャップは二方向で、別の診断に落ちる:

- **想像にあってコードに無い・違う** → 辞書・台帳の陳腐化、または記述の不足（沈黙を仮定で埋めた箇所）
- **コードにあって想像に無い** → 匿名の処理（全体版）、未登記挙動、語彙の穴

このテストは compose のブラインドレビュー（review.md）と**対称**をなす:

| | 渡すもの | 測るもの |
|---|---|---|
| ブラインドレビュー（review.md） | コードだけ、資料なし | コードが自己説明的か |
| ブラインド復元テスト（本スキル） | 資料だけ、コードなし | 記述が生成的・忠実か |

併用すると切り分けができる: コードだけの読解が失敗し資料からの復元が成功するならコードの問題、逆なら資料の陳腐化。
台帳・辞書との被覆（台帳にあるのにコードから読めない／コードにあるのに台帳に無い）は独立軸にせず、このテストが吸収する。

### 既知の失敗モード

AI は尤もらしい生成が得意なので、資料からの導出ではなく事前知識で像を埋めるリスクがある。由来の刻印がその対策だが完全ではない。
辞書が薄いレポジトリでは診断の大半が「記述の不足」になる — それ自体は正しいシグナルだが、初回はそうなると予期しておく。

## 出力と行き先

診断の提示 → ユーザーと項目ごとの行き先を確定する。行き先は三種:

1. **その場修正** — ツリーに触らず、挙動保存の敷設が要らない機械的修正（リネームの追従、リンク切れ、未使用コードの削除）。現行スキルの実施経路を軽微な項目に限って残す。
2. **プラン化** — 構造的な項目。plans/<project>/ を作り、**診断文書**（名前は仮に diagnosis.md）を置く。problem.md は置かない。ジャンル規律: 何が悪いか（軸の言葉で）と発見の観察のみを書き、再設計案を書かない。
3. **見送り** — 記録して閉じる。

プランの入口文書のジャンルが tdd-run のルーティング情報になる:

- problem.md がある → 新規型（decompose）
- 診断文書がある → 再節合型（refactor）

現行の「工程の判定」（problem.md から挙動保存の掲出を読み取る解釈作業）は廃止され、判定は文書の存在という機械的な事実になる。

### 同居の禁止（1プラン1入口文書）

problem.md と diagnosis.md は同一プランに同居させない。規約として排除する。

- **スコープの不一致** — 診断のスコープは context 単位であり、プランは一つの問題の単位。構造の悪さは複数プランの積み重ねから生まれるのが普通で、元プランの枠に診断を合わせる理由がない。
- **ライフサイクルの独立** — プランは feedback のクローズでアーカイブされる単位。問題の解決と構造の改善を一つのプランに同居させると、どちらの完了がクローズなのかが曖昧になる。
- **ルーティングの機械性** — 「両方あったらどちらか」という解釈が入った瞬間、廃止した工程の判定が別の形で戻る。

feedback からの構造・品質への懸念（ブラインドレビューの劣化指摘、構造の改善仮説の外れ等）は、**同一プランへの再入ではなく /tdd-refactor への診断の依頼**として扱う。
tdd-refactor が findings の項目を受けて診断し、構造的な作業が要るなら新しいプランを立てて diagnosis.md を置く。
元プランの findings 項目は「対応済み（/tdd-refactor, plans/<新プラン>/diagnosis.md, 日付）」に更新する — tdd-problem が「問題の発見」の findings を problem.md に統合して対応済みにするのと同じ作法。

これで feedback の差し戻し先は三系統に整理され、二軌道の対称が差し戻しにも延長される:

- 問題の発見 → /tdd-problem（新プランに problem.md）
- 構造・品質への懸念 → /tdd-refactor（診断を経て、必要なら新プランに diagnosis.md）
- ツリー・実装の修正（既存スコープ内） → /tdd-run（部分木再入。入口文書は変わらないので同居は生じない）

副産物として、準備的リファクタリング（これから作る機能のために先に構造を整える）は、diagnosis プランを problem プランが「前提とする」関係で結ぶことで表現できる。

## 周辺への波及（実装時に必要な変更）

- **tdd-run skill.md（ルーティング）** — 工程の判定を、入口文書のジャンル判定に置き換える。
- **tdd-run/subcmds/refactor.md** — 入口を problem.md から診断文書に変える。手順の順序を修正する: 診断の対応表 → 再設計案の考察 → 触る範囲の確定 → 回帰面の確定（台帳のスコープ絞り込み。redesign/acts-ledger/05 の先行論点はここに納まる — 再設計案が触る範囲を与え、台帳＋依存グラフが回帰面を返す）→ 挙動保存の敷設 → 発掘・ツリー。
- **compose.md** — user-story.md の無い再節合型プランでは、root の最終検証を witness（＋特性テスト）の緑が担うことを一文明記する。
- **tdd-feedback** — 冒頭の `cat <plans_dir>/problem.md` が無条件（skill.md:45）。入口文書のジャンルに応じて診断文書を読む分岐を足す。利用仮説照合のフォールバック（skill.md:85）も同様。差し戻し先に /tdd-refactor（構造・品質への懸念）を加え、三系統に整理する。
- **user-story.md** — refactor プランでは作らない。台帳の該当行為一覧（claim ＋ witness）が相当物。台帳が空・未整備なら従来のやり方（コードと UI からの回収＋特性テスト）に従う。
- **既存レポジトリの移行** — test-tree.md に残る再節合型セクションと、findings からの部分木再入経路の行き先を確認する。
- **redesign/acts-ledger/05** — 典拠差し替えの実装先は新体制の refactor.md になる。中断中の先行論点は上記の位置で解消する。
