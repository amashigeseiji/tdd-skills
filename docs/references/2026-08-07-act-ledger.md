# 構想: 清算済み挙動主張の登記簿（docs/test-tree.json）

**日付:** 2026-08-07
**出どころ:** 「plans 以下の状態管理ファイルを JSON 化できないか」という問いから始まった対話。
test-tree.md の JSON 化の検討を経て、リファクタリング工程（refactor）の「引用」に引用先が実在しないという欠陥の発見に至り、それを埋める装置として収束した。
**状態:** 構想の合意まで。スキーマ設計・実装は未着手。

## 出発点: refactor の引用には引用先がない

refactor の回収（手順2）が接地しているのは現在のコードと UI である。
過去の test-tree への参照はどこにも指示されておらず、過去のツリーは feedback のクローズで `plans/archives/<project>/` に移り、そこを引く仕組みもない。
テストファイル自体は作業リポジトリに生き残るが、残るのは describe のネストだけで、周回の型・利用仮説・移設元・前提決定は plans と一緒に閉じる。
つまり refactor の「引用」にはアドレス可能な引用先がない。
コードを読んで回収する行為はもっともらしさを保証するが、過去の主張との同一性は保証しない。
引用先の住所がなければ、引用は構造的に生成になる。
これは個々のセッションの怠慢ではなく仕組みの帰結である。

## 台帳の意味論

**docs/test-tree.json は「使用で清算された挙動主張の登記簿」である。**

背景にある観察: ユーザーの行為可能性とシステム内の装置群の間には必然的な繋がりがない。
装置群の協調がユーザーの行為を支えるのは、テスト（とくに受け入れテスト）だけが目撃している偶然の成立である。
台帳とはこの偶然の繋がりの登記簿であり、「この行為はこの検証手段によって成立が目撃されている」という結線が、辞書にも依存グラフにもテストファイルにも書かれていない台帳の固有領域になる。

- **昇格の拍は feedback のクローズ時**（dictionary の promote と同じ拍）。
  plans のツリーは仮説であり、compose の緑では清算されない（緑 ≠ 完了）。
  feedback が実使用と照合してループを閉じた時点で、主張は「成立した挙動」に変わる。
  台帳に載っていること自体が「清算済み」を意味し、refactor の固定点の定義そのものになる。
- **台帳に緑/赤は持たせない。**
  通っているかどうかは常にテスト実行から導出する。
  台帳が持つのは主張・構造・テストへの結線のみ（リンク切れは lint で検出）。

## 行為層のみを載せる

台帳に登記するのは **actor の行為（行為層）のみ**。能力層はグローバルに持たない。

理由: 能力層のグローバル表現はすでに三つ揃っている。
名前は辞書（`src` 付き）、構造は依存グラフ、証拠はテストファイル。
docs 側に能力層ツリーを置くのは第二の依存グラフを手で維持することであり、能力層は再節合のたびに入れ替わることが目的の層なので確実に古びる。

安定性の非対称がツリーの中にもある: 行為層（固定点）は蓄積に値する安定な資産で回帰面そのもの、能力層は入れ替わる層。
辞書の二層管理（問題ドメイン語彙は安定、solution は入れ替わる）と同じ非対称である。

「plans のツリーをそのまま持ってくる」案は採らない。
plans のツリーは把持の過程の記録（どういう問いでどう分解したか、採らなかった案）であり、アーカイブがすでに保存している。
過程の記録と清算済みの主張を混ぜるのはフェーズの責務を混ぜる形である。

**装置主語 root のフェーズは昇格するものを持たない。**
装置の主張は plans のアーカイブ・辞書・テストファイルで足りる。
帰結: 純粋に基盤的なコードのリファクタリングでは台帳に固定点が見つからず、そのときの固定点は既存のユニットテストと辞書から取る（現行 refactor.md の姿勢のまま）。
「台帳に目撃者がいない挙動には特性テストを書く」という規則が装置についても一貫して効く。

## 結線: witness と settled の分離

- **witness** — 生きた参照。主たる結線は受け入れテスト（役割主語の「できる」の検証者は受け入れテスト・手動確認だとツリー規範が既に定めており、`tests/acceptance/` はアーカイブされず生き残る）。
  リンク切れは lint で検出、緑/赤は実行から導出。
- **settled** — 清算時の証拠スナップショット。不変。
  「清算時点でこの行為はこの受け入れテストと、これらの装置・ユニットテストに支えられていた」は歴史的事実であり古びない。
  生きた「いま何が支えているか」は refactor セッションが依存グラフから導出し、記録された当時の支えとの差分が被覆のドリフトを教える。

ユニットテストの ID リストを「生きた索引」として持つ案は却下した。
再節合が UT を入れ替えるたびに台帳更新が要り、その内容は依存グラフから導出可能 — 導出できるものを手で写経し続ける形になる。
同じ情報をスナップショットとして持つ形に変えて残した。

「現在の支えの導出」は `depgraph.regen` に依存する（オプトイン）。
無いプロジェクトでは settled スナップショットが唯一の地図になるが、compose の既存の姿勢（depgraph が無ければ検査をスキップして findings に記録）と同じ扱いで許容する。

イメージ（スキーマは未設計、一行の例）:

```json
{ "id": "act-0042", "actor": "作成者", "claim": "記事を下書きとして保存できる",
  "parent": "act-0040", "context": "editor",
  "witness": { "acceptance": "tests/acceptance/<project>.spec.ts#US-2" },
  "settled": { "date": "2026-08-07", "project": "<project>",
               "devices": ["<装置概念名>", "..."],
               "unitTests": ["tests/<dir>/<file>.spec.js#<describe経路>"] } }
```

## ID とツリー性

- **ID は台帳の行為エントリにのみ発行する。**
  述語の文言は再清算で変わりうるので、文字列一致を引用の同一性にできない。
  テスト側に新しい ID 空間（UT01 等）は作らない — describe 経路（日本語ノード名のネスト）とファイルパスという自然キーが既にあり、名前空間を増やすと突合対象が増えるだけ。
- **ツリー性は層で答えが分かれる。**
  行為層の中の浅い親子（root 行為とその下の中間行為、「この行為はこの行為の一部として現れる」）は保持する。
  台帳は actor ごとの浅い森になり、昇格の蓄積で「このシステムでこの actor は何ができるか」が actor 別に一覧化される。
  能力層のツリー性（親は子の能力の使い手）は把持の足場であり、清算後の構造的事実は依存グラフが持つ。
  semi-lattice と基盤節を入れた時点でもともと厳密な木ではなかった。

## refactor がどう変わるか

- 回収（手順2）: 「コードと UI を読んで列挙」から「台帳の該当 actor の行為一覧を引き、コードと突き合わせる」へ。
- 被覆確認の問い: 「この列挙は既存の振る舞いを被覆しているか」から「台帳との差分は何か — 台帳にあるのにコードから読めない行為、コードにあるのに台帳にない行為」へ。
- 引用: ノード ID の参照として実体を持つ。
- 挙動保存の敷設（手順3): witness のテストを走らせることが第一手になり、特性テストは台帳に目撃者がいない挙動にだけ書く。

## 副次的な使い道: 類似ノードの発見

ノードの主語と context は辞書で正規化されているので、ツリーの合成は文字列マッチではなく概念キーでの結合になる。

- 同一主語・異述語のノード群 = その装置が歴代主張してきたことの集積（実効的なインターフェース履歴）。
- 複数プロジェクトから同じ装置が出てくる = 基盤節の発見基準（同じ断片が複数の枝から出たら基盤候補）のプロジェクト横断版。
- 主語が辞書で解決できないノード = それ自体が lint（主語の未登録）。

述語どうしの曖昧な類似は、スクリプトが主語・context・src で候補を絞り、絞られた一覧の類似判断は AI がやる（dict-search.js と同じ分業）。
埋め込みや類似度スコアを最初から持ち込まない。

## 追記（2026-08-08）: 昇格の拍の訂正

本文の「昇格の拍は feedback のクローズ時（dictionary の promote と同じ拍）」は、
promote の実態の誤認である。promote は現行 tdd-feedback で**毎周の成果物レビュー**に走り、
クローズ時に限らない。登記の拍もこれに合わせて毎周の成果物レビューとする
（同一プランへの戻しに向かう周でも、着地した行為は登記してよい）。
「feedback が実使用と照合してループを閉じた時点で清算される」という意味論は変わらない —
変わるのは、その照合が毎周行われているという事実の認識である。

## 追記（2026-08-17）: witness の複数化と追加操作

未決点の「witness の複数化」は `witness.acceptance` を配列にして解決済み。
既存の行為に witness を足す操作（`acts-write.js witness-add`）と、その清算スナップショットを `resettled` 配列に積む形を追加した。
`settled` は不変のまま。claim の置き換え（supersede）は引き続き未設計。
