# リファクタリング問題の受け皿 — decompose の再配置類型

**日付:** 2026-08-06
**出典:** スキル利用プロジェクトでのリファクタリング実践のフィードバック（2026-08-05 の利用インタビュー・観察記録）
**状態:** 検討中（未着手）

## 背景 — 何が起きたか

利用プロジェクトで、大きなエントリーポイントファイルに畳み込まれた実装をモジュール化する
リファクタリングを /tdd-problem → /tdd-run で実施した。

problem.md は最初から良い形で書かれていた:

- 問題の本質を「機能実体が名前をつけられないまま匿名的に埋もれている」
  「辞書の概念が実装の実体を表現できていない（概念の劣化）」として記述
- 「解決したと言える状態」に挙動保存（既存の挙動が保たれたことを確認できる）を含む
- 「/tdd-run への申し送り」に、想定する進めかた
  （概念の再定義から入り、そのためのテストを考案し、既存実装を再配置する）と語彙の種まで記載

それにもかかわらず、tdd-run の decompose が迷走した。事実経過:

1. **概念提示の段階** — 新規に作る機構の概念は提示されたが、既存コードの問いなおし
   （既存概念の再定義・再配線）がなかった。ユーザーがその欠落を指摘したが、無視して先へ進んだ
2. **ツリー提示の段階** — 「コード保守者」のような開発者を指す actor を立て、それを主語とした
   ツリーを提示した。ユーザーが指摘して修正させた
3. **再提示のツリー** — ユースケース（行為層）の記述のみで、装置群への分解がなかった。
   装置ノードがなければ作業対象コードを特定できないはずだが、ユーザーが
   「分解しないと駄目では」と問いかけて、ようやく分解した

このほか、同セッションで観察された周辺の問題:

- /tdd-vocab plan の概念候補が「状態管理の外部化」などのメタ概念
  （リファクタリング作業自体を語る概念）に流れ、ユーザー指摘で修正した
- 「リファクタリングをやってほしい」という曖昧な軌道修正を工程スキップと誤読し、
  ツリー承認前に実装へ着手した（聞き直すべきだった）
- decompose 終了後、セッションを切るか確認せず compose へ直進した
- 能力ノードのスケルトン `it('TODO', () => {})` が自明に pass し、実装漏れが
  「全緑」の報告に紛れた
- /tdd-refactor が受け皿の候補に見えたが、概念の再定義を含む場合の扱いが不明だった

## 診断 — decompose.md のどの記述が迷走を生んだか

迷走はモデルの能力ではなく decompose.md の記述に帰着する。3 つの迷走はそれぞれ
具体的な記述に対応する。

### (1) 開発者 actor の捏造 ← root 原則

decompose.md は「root は原則として役割主語のユースケースである」（手順2）と定める。
リファクタリング問題ではアプリ利用者の行為は何も変わらないため、この原則に従おうとすると
主語にできる actor がいない。すると problem.md の「名前を通じて発見・操作できない」の主体である
開発者を actor に仕立てるのが、規則に忠実な帰結になる。

例外枝（装置主語 root）は存在するが、「配線済み装置の能力改善
（共有中間ノードの取り出し＝セミラティスの探求）に限る」と狭く限定されており、
「匿名実装の再配置」はどちらの枝にも乗れない。

なお装置主語 root の例外枝は、利用仮説を「退行なし＋クライアント側の改善」と定めており、
これはリファクタリングの形（挙動保存＋構造の改善）にすでに近い。
類型の不足であって、思想の不足ではない。

### (2) 行為層止まりで装置分解がない ← 分解の問い

手順4の分解の問いは「X が xxx できるためには何が必要か」。これは**導出**の問い——
まだ存在しない機械に必要な部品を導く問いである。再配置に必要なのは逆の**発掘**の問い——
「既存実装のどの断片が、どの名前の装置に属するか」。
導出の問いを既存挙動に当てると「すでに全部できている」ため分解が進まず、行為層で止まる。
装置ノードが出ないので、作業対象コードの特定もツリーから読めない。

### (3) 既存概念の問い直しの素通り ← 調査の姿勢と申し送りの不使用

手順1調査の姿勢は「既存の解釈 paradigm の確認」、すなわち既存を**従う対象**として読む指示であり、
**疑う対象**（再定義・再配線の候補）として読む指示がない。

さらに、problem.md の「/tdd-run への申し送り」を分解の入力として使えという指示が
decompose.md のどこにもない。冒頭で problem.md を読みはするが、
手順の側（root 原則・導出の問い）が申し送りの内容を上書きした。

## 設計原理

利用プロジェクトで最終的に機能した形（軌道修正後）から、線の引き方が一つ抽出できる:

**メタな解決条件（開発者が名前で発見できる・辞書↔実装の対応）は受け入れ層に置き、
できるツリーには入れない。ツリーは装置の再節合を書く。**

実際に機能した構成は、受け入れテスト＝「辞書↔実装の対応」というメタな Then（ユニットテスト
ランナー側）＋挙動保存（E2E 側）、ツリー＝装置群の再配置、だった。
迷走とは、このメタがツリーに漏れて「保守者は〜できる」ノードになったことである。

これは rationale.md の「分解は実装者の責務——分解を事前フェーズに固定しない」とも整合する。
「再設計案の提示→承認→実行」という独立フェーズを持つ新スキルを立てる必要はない。
リファクタリング問題においては **decompose の出力（既存概念の再定義案＋装置ツリー）が
そのまま再設計案**であり、ユーザーの期待（現状の問題＋再設計後の姿）は
problem.md ＋ ツリー承認時の提示に対応する。欠けているのは能力ではなく、この対応の明示である。

## 提案

### 本丸: decompose.md に第三の root 類型「再配置（リファクタリング）」を追加する

- **判定:** problem.md が挙動保存を制約・解決条件に掲げている
  （挙動を変えないことがゴールの一部である）
- **root は装置主語。** 既存エントリーポイントの機械が root。行為層は立てない
  （アプリ利用者の行為は変わらない）
- **挙動保存の検証:** 既存の受け入れテスト・E2E が担う。なければ特性テストのスケルトンを
  ここで置く。利用仮説は「退行なし＋構造の改善」の形（装置主語例外の形を継承・一般化）
- **メタな解決条件はノードにしない。** 辞書↔実装の突合を主張する受け入れテストとして置く
- **分解の問いを差し替える:** 「できるためには何が必要か」ではなく
  「既存実装のどの断片が、どの名前の装置に属するか」。
  各装置ノードに移設元（ファイル・関数）を添える——ツリーがそのまま作業対象の特定になる
- **語彙作業に既存概念の問い直しを含める:** 新規登録だけでなく、実装と対応しない・
  対応が薄い既存エントリの再定義・再配線を、語彙登録ルールと同じ表＋承認の作法で提示する

### 共通の小修正（類型追加とは独立に効く）

- decompose.md 冒頭の読み込みに「problem.md の『/tdd-run への申し送り』は分解の入力である」を明記
- compose.md の能力ノードスケルトン `it('TODO', () => {})` を `it.todo()`（または pending）に変更
  （全緑偽装の直接原因）
- decompose の出口ゲートに「セッションを切るか続けるかをユーザーに確認する」を追加
  （現状は「どちらでもよい」とだけ書かれ、確認を求めていない）
- 工程スキップを含意する曖昧な指示は、スキップしてよいかを聞き直す
  （置き場は対話規範 norms/dialogue.md か tdd-run 本体の制約か、要検討）

### 周辺スキルの修正

- **tdd-vocab plan:** 「ソフトウェアを語る概念のみを登録する。リファクタリング作業自体を語る
  メタ概念（外部化・移設・正規化など）は登録しない」の規律を追加
- **tdd-refactor:** 位置づけの明確化とルーティング。ここは「理解とコードの小さなズレの転写」
  （辞書の概念定義は動かさない・振る舞い保存・problem.md 不要）。観察の結果、概念の再定義・
  再配線が必要と分かったら「リファクタリング問題として /tdd-problem へ」と明示的に送る。
  境界の判定基準は「辞書の概念の定義自体を動かす必要があるか」

## 未決点

- **類型の置き場:** decompose.md 内の分岐（読み替え節）にするか、独立した subcmd にするか。
  差分は root の立て方・分解の問い・受け入れの形に集中しており、語彙規範・整形式チェック・
  確認の拍は共通なので、decompose.md 内の分岐が第一候補。
  なお tdd-run の分解/合成サブコマンド化（フィードバック対応 D の 7-1）は 2026-07-30 に実施済みで、
  decompose.md 約 450 行は分割後のサイズ。類型追加によるさらなる肥大が気になる場合のみ
  独立 subcmd を検討する
- **判定の明示性:** 「挙動保存が制約」という暗黙の判定で足りるか、problem.md 側に問題類型の
  宣言を持たせるか（tdd-problem への追記が必要になる）
- **user-story.md との関係:** リファクタリング問題でのユーザーストーリーは開発者主語の
  メタな Then になりうる（実例では機能した）。受け入れ層にメタを置くことの明文化を
  tdd-userstory 側にも入れるか
