# tdd-refactor 再定義の検討記録 — リファクタリング問題の受け皿

**日付:** 2026-08-06
**性格:** 指示書ではない。ここまでの議論・そう考える理由・概念・現在のアイデアの記録。
具体化(ファイル構成・文面・既存規範との整合)は、実際の decompose.md / norms /

## 1. 出発点 — 何が起きて、何が分かったか

経緯の詳細は refactoring-decompose.md にある。要点だけ再掲する。

リファクタリング問題(main.js の匿名実装のモジュール化)を /tdd-problem → /tdd-run で
実施したところ、decompose が迷走した。①開発者を指す actor(「コード保守者」)を捏造した、
②行為層止まりで装置分解が出なかった、③既存概念の問い直しと problem.md の申し送りを
素通りした。強い軌道修正の末にできた test-tree.md は悪くないツリーだった。

診断: 迷走はモデルの能力ではなく decompose.md の記述に帰着する。root 原則(役割主語)が
actor 捏造を規則に忠実な帰結として誘導し、分解の問い(「できるためには何が必要か」)が
既存挙動に対して空転し、調査の姿勢(既存 paradigm の確認=従う対象としての読み)が
問い直しを妨げた。

ここから得た最初の教訓は refactoring-decompose.md の「設計原理」にある:
**メタな解決条件(開発者が名前で発見できる・辞書↔実装の対応)は受け入れ層に置き、
できるツリーには入れない。ツリーは装置の再節合を書く。** 迷走①とは、このメタが
ツリーに漏れて「保守者は〜できる」ノードになったことだった。

## 2. 概念の中核 — 類型を分ける軸は「rootの主語型」ではなく「どの層が固定点か」

当初の提案(refactoring-decompose.md)は「装置主語 root の第三類型」だったが、
検討の結果これは採らない。理由: 実走の test-tree.md は行為層の記述から入っており、
それがむしろ良かった。冒頭にこうある——「root は既存ユースケースそのもので、
リファクタリングの前後で不変。変わるのは能力層(装置)だけで、root と行為層が
緑のままであることが挙動保存の確認になる」。

ここから、類型を分ける軸の再定義に至った:

- **新規型(decompose):** root は**仮説**であり、利用仮説によって検証される。
  下の層はそこから**導出**される(「できるためには何が必要か」)。すべてが可変。
- **再節合型(refactor):** root と行為層は**固定点**。人間にとって、最終的な振る舞いが
  変わらなければ中間のコード群はどれだけ変わっても問題がない。固定した root から
  分解ツリーは**複数**導出でき、そのどれを選ぶか、複数のツリーを検討してそこから
  自立する中間ノードを考慮し、全体を解す——これがリファクタリングという操作の意味である。
  可変なのは能力層だけで、そこに向ける問いは導出ではなく**発掘**
  (「既存実装のどの断片が、どの名前の装置に属するか」)。

この軸の取り方には複数の帰結がある:

- **root は役割主語のまま**でよい。例外枝は要らない。変わるのは root の意味
  (仮説→固定点)と、root を得る作業の性格(発明→既存挙動からの回収)。
- **挙動保存の検証が構造から出る。** 行為層が緑のままであること自体が挙動保存の確認。
  既存テストが無い場合(今回の main.js がそう)、特性テスト・受け入れスケルトンが代役に立つ。
- **actor 捏造への構造的な防止。** root と行為層が既存挙動からの回収であるなら、
  そこに発明の余地がなく、作業主体(開発者)を actor に仕立てる圧力が発生しない。
  開発者の目標(名前で発見できる等)は受け入れ層のメタな Then として置かれる。
- **承認の意味が変わる。** 新規型の root 承認は「この仮説を追う価値があるか」。
  再節合型では「この列挙は既存の振る舞いを被覆しているか」(被覆確認)。

### actor が辞書に無い場合(補正)

actor の導入は比較的最近であり、辞書に actor が一つも無いプロジェクトがありうる。
その場合は refactor の中でも actor を立て、適切な受け入れテストを書く必要がある。
「発明しない」の意味はここで正確に述べておく必要がある: 禁じたいのは
**作業の主体をアプリの actor に仕立てること**(「コード保守者」の類)であって、
actor の新規登録そのものではない。actor が辞書に無い場合、それは既存エントリーポイントの
**利用者から回収**して立てる——誰がこの挙動を駆動しているかは既存コードと UI から
読み取れるので、これも発掘の一種である。判定の目安は語彙のメタ概念判定と同型にできる:
**リファクタリング完了後も、その主体はアプリを使い続けるか。** 使い続けるなら actor、
作業とともに消えるなら受け入れ層のメタ側。

## 3. 基盤節 — 辺の意味の逆転と複数 root

再節合型では、複数の行為ノード(root 含む)から共有される装置を、木の外の
**基盤節**として置くことを規範上許容する。実走の test-tree.md では
「基盤——全更新操作が共有する装置」(アプリ状態ストア・画面反映器)として
自然にこの形が現れたが、規範上の位置づけは無かった。

許容せざるをえない理由は、影響関係の向きにある。基盤(横断的機能。ログ機構が典型)の
導入は、複数の root を一括で解決することがしばしばある。このとき影響関係は
「root を分解して下位ノードが析出される」のではなく、**「共通のノードを構築したら
複数の上位ノードに影響がある」**——辺の意味が逆向きである。新規型のツリーでは
辺は上から下への導出だが、基盤節では下から上への遡及。どの root を分解しても
ログ機構は析出されない。散らばった断片への気づきから構築され、構築されて初めて
複数 root に効く。リファクタリングはしばしばそういうものである。

同じ理由で、**一つの再節合問題が複数の root を同時に固定する**ことも許容する。
これは以前から構想にあった複数ツリー機構(横断的依存)と地続きであり、
Alexander のセミラティス(重なり合う集合)の本来の意味に近いのはむしろこちらである。
既存の装置主語 root の例外枝(共有中間ノードの取り出し)は、いずれこの型の局所版
(固定点が use-case でなく装置のインターフェースである場合)として統合できる可能性が
あるが、当面は触らず保留。

許容の書き方に一つだけ実質を持たせるアイデア:
**基盤ノードには影響先の上位ノードの列挙を添える**(装置ノードに移設元を添えることの
逆向き対応物)。働きは二つ。(a) 検証範囲の確定——基盤の挙動保存は「影響先として
列挙されたすべての上位が緑のまま」で機械的に述べられる。共有が広いほど回帰面が広い、
ということがツリーから読める。(b) 発見基準——発掘中に**同じ断片が複数の枝から
出てきたら基盤候補の徴候**(実例: 20 か所以上のハンドラに散った renderCosmeList / redraw
の手動呼び出し → 画面反映器に凝集)。「横断的機能を見つけよ」という訓示ではなく、
観察可能な徴候として書ける。

## 4. 因数分解としての読み — 名前の整合と概念の錨

refactoring は造語であり、系譜がある。Forth コミュニティでコードを小さな word に
分けることを **factoring** と呼ぶ用法があり(Leo Brodie *Thinking Forth*, 1984)、
これは数学の因数分解からの借用——共通部分をくくり出す (factor out) イメージ。
そこに re- を付けて refactoring としたのが 1990 年前後の Opdyke と Johnson
(Opdyke の 1992 年の学位論文が定着点)で、Fowler の 1999 年の本で一般化した。
つまり refactoring とは語の成立からして**因数分解のやりなおし**である。

この読みで、二つの工程の名前と本設計の要素が一枚に揃う。decompose は分解という
意味で正しい: 全体(root)が最初に与えられ、それが成立するための要素へ分解する
行為が導出である。全体は合成の結果として出てくるのではない——分解による要素の
析出が合成を可能にする。refactor はその分解のやりなおしであり、全体そのものは
変わらず、分解の仕方が変わる。

対応表:

| 数学 | 本設計 |
|---|---|
| 積の不変性(12 = 3×4 = 2×6) | 挙動保存。root と行為層は固定点 |
| 分解の非一意性 | 固定 root から複数のツリーが導出できる |
| どの分解を採るかの選択 | 前提決定(例: 単一ストア vs BC 分散) |
| **共通因数のくくり出し** ab + ac = a(b+c) | **基盤節**。複数の項(行為ノード・root)に現れる断片を一度だけくくり出す |
| くくり出した因数がどの項に効くか | 基盤ノードの影響先の列挙 |
| 複数の式にまたがる共通因数 | 複数 root の一括解決(ログ機構の類) |
| 等号の確認 | 行為層(受け入れ・E2E)が緑のまま |

とりわけ**共通因数のくくり出し = 基盤節**の対応は重要である。§3 で述べた辺の意味の
逆転(共通ノードの構築が複数の上位に遡って効く)は、代数で共通因数をくくり出す操作
そのものであり、「横断的機能」という説明よりも正確に、基盤節が何であるかを言い当てる。
影響先の列挙とは、くくり出した因数がどの項に効いているかの記帳である。

類比が破れる場所が一つあり、破れていることが設計上重要である。整数の素因数分解は
一意だが(算術の基本定理)、**コードには素数がない**——挙動の一意な原子的分解は
存在しない。だから因数分解のやりなおしには常に実質的な選択があり、前提決定という
拍が必要になる。もう一つ、数学の等号は無償で成り立つが、コードで「積が同じ」で
あることは**テストを通してしか観測できない**。main.js にテストが無かったという
problem.md の致命点は、等号を確かめる手段が無かったということであり、特性テストとは
やりなおしの前に等号を敷設する作業である。

## 5. 構造の決定 — tdd-run のルーティング、tdd-refactor の再定義

置き場は次の形に決めた:

```
tdd-problem → tdd-run ─ 判定(root が仮説か固定点か)
                          ├─ decompose(導出) ──┐
                          └─ refactor(再節合) ─┴→ compose → feedback
```

- **decompose 内の分岐(読み替え節)にしない理由:** 問いの向き・root の意味・辺の意味が
  逆である二つの操作を一つの手順書にモード分岐で織り込むと、読んでいる間ずっと
  「いまどちらのモードか」を保持し続ける規律が要る。今回の迷走はまさに「文脈上の
  手がかりが手順本文に上書きされる」失敗だったので、同じ構造を増やすことになる。
  別ファイルなら、モードは「どのファイルが読み込まれているか」という事実になり、
  保持が要らない。
- **新名の独立スキルにしない理由:** tdd-refactor が既に在り、しかし有機的に役立って
  いない。役立っていない理由はおそらく定義が否定形でできていること(辞書は動かさない・
  problem 不要・振る舞いは変えない——何をしないかだけがあり、固有の作業の実体が薄い)。
  避けて別名を立てるより、**tdd-refactor をここで再定義**して受け皿にするほうが、
  置き場の問題と有機性の問題が一手で解ける。
- **run のサブコマンドとする。** 判定(仮説か固定点か)は run のルーティングに一箇所だけ
  置く。判定の根拠の目安は「problem.md が挙動保存を制約・解決条件に掲げているか」。
  判定は提示→承認の拍を経る(暗黙にやらない)。どちらの工程も出口の契約
  (承認済み成層ツリー+語彙作業+受け入れスケルトン)が同じで、compose が両方を受ける。
- **現行 tdd-refactor の軽量な性格(小さなズレの転写)は当面考えない。**
  必要になったら後で位置づけを検討する。
- **共通規範の括り出し:** 語彙規範・ツリーの整形式・承認の拍・出口ゲートは
  decompose / refactor 共通なので、norms 側へ出して両方から参照する形が候補。
  decompose.md の減量にもなる。refactor.md には差分だけを書くことで、
  decompose より薄いファイルになるはず。

## 6. refactor 工程の現在のアイデア(骨組み)

番号は手順の想定順だが、拍の切り方・統合は具体化の際の判断に委ねる。

0. **読み込み。** problem.md(申し送り含む)・辞書・対象コード。
   **申し送りの各項目を、どの手順で扱うかの対応表として提示する。**
   これは訓示(「申し送りを入力とせよ」)の代わりに置く作業の実体である。
   今回の迷走③は申し送りが読まれなかったのではなく、読まれた上で手順に上書きされた
   失敗だった。「読め」と書き足しても同じ失敗は起こりうる(書かれた規則だけでは
   遵守されない、という既存の教訓と同じ形)。対応表は一項目ずつ処理しないと作れないので、
   素通りが構造的にできない。扱えない項目はその場で露呈する。
1. **調査。** 既存実装の読解。姿勢を decompose と逆に明記する: 既存の解釈 paradigm は
   従う対象ではなく**問い直しの候補**。実装と対応しない・対応が薄い辞書エントリを
   再定義候補として列挙する。
2. **root と行為層の回収。** 役割主語のまま、既存エントリーポイントから行為を列挙する。
   作業主体を actor に仕立てない(開発者の目標は受け入れ層へ)。actor が辞書に無い場合は
   §2 の補正のとおり利用者から回収して立て、受け入れテストを対応させる。複数 root 可。
   承認の意味は被覆確認。
3. **受け入れ層。** 挙動保存(既存テスト。無ければ特性テスト・受け入れスケルトン)+
   辞書↔実装の対応。後者は手書きのメタなテストである必要がない可能性がある——
   check-vocab が「語彙から実装へ到達できるか」の検査として既にあるので、
   「check-vocab が exit 0(+src の粒度条件)」を受け入れ条件として書く形に委譲できるか
   検討する。メタな解決条件はここに置き、ノードにしない。
4. **前提決定。** 能力層の構造を分ける選択肢があれば明示し、採らなかった案と理由を
   一行残す(実例: 単一ストア集約 vs BC 分散——これは同じ固定 root の下の二つの
   再節合案の選択だった。理想としてはツリー族の比較だが、当面はこの実践の追認でよい)。
5. **能力層の発掘。** 問いは「既存実装のどの断片が、どの名前の装置に属するか」。
   各装置ノードに移設元(ファイル・関数)を添える——ツリーがそのまま作業対象の特定になる。
   割り当てられない残りは**残余として宣言する**(実例:「main.js には DOM 配線と
   描画関数のみ残す」)。全断片が「どこかの装置へ移る」か「宣言された残余」かの
   いずれかになる、という完備性条件。分解の漏れがツリー承認の時点で見える。
6. **基盤節。** §3 のとおり。影響先の列挙を添える。同じ断片が複数の枝から出たら基盤候補。
7. **語彙作業。** 新規登録に加えて、実装と対応しない・薄い既存エントリの再定義・再配線を、
   語彙登録ルールと同じ表+承認の作法で提示する。登録するのはソフトウェアを語る概念のみ。
   リファクタリング作業自体を語るメタ概念(外部化・移設・正規化など)は登録しない。
   判定の目安: **リファクタリング完了後もその概念は残るか**(「状態管理の外部化」は
   作業が終われば消える語、「アプリ状態ストア」は残る語)。
8. **出口ゲート。** ツリー承認・compose への引き継ぎ・**セッションを切るか続けるかの確認**
   (現状「どちらでもよい」とだけあり確認を求めていない、の修正)。

## 7. 独立に効く小修正(工程設計と切り離して先に入れられる)

- compose の能力ノードスケルトン `it('TODO', () => {})` → `it.todo()`(全緑偽装の直接原因)。
- 工程スキップを含意する曖昧な指示(「リファクタリングをやってほしい」等)は、
  スキップしてよいかを聞き直す。置き場は対話規範側が候補。
- tdd-vocab plan のメタ概念禁止(§6 の 7 と同じ判定を plan 側にも)。

## 8. 未決点

- run の判定の文面(「挙動保存が制約」という徴候で足りるか)。problem.md 側に
  類型宣言を持たせる案は、問題領域の言葉で書くという tdd-problem の性格に
  solution 側のメタデータを混ぜることになるため、run 入口の提示→承認で承認済み判定を
  test-tree.md ヘッダ等に記録する形を第一候補としている。
- check-vocab 委譲の実現性(src 粒度の検査を足す必要があるか)。
- user-story との関係: 再節合型では受け入れの一部(辞書↔実装)が lint に委譲されるなら、
  tdd-userstory 側への追記は短い注記で済む可能性。
- 装置主語 root の既存例外枝の扱い(当面現状維持。将来、再節合型の局所版として
  統合できるかを見る)。
- refactor.md を一枚にするか、玄関と工程本体を分けるか(嵩を測ってから判断)。
- 軽量なリファクタリング(小さなズレの転写)の位置づけ(当面保留)。

- **ルーティング:** `tdd-run/skill.md` に工程の判定を追加した。
  判定は新しいツリーセクションを作る分岐（初回・新しいスコープ）でのみ行い、problem.md の徴候（挙動保存が制約・解決条件に掲げられているか）から提示 → 承認する。
  承認された型は test-tree.md のセクション見出し（`## <スコープ>（YYYY-MM-DD・<型>）`）に記録し、以降の再入は記録に従い判定を再演しない（§8 の第一候補を採用。problem.md への類型宣言は採らなかった）。
- **共通規範の括り出し:** `tdd-run/norms/tree.md`（ツリー規範）を新設し、記法・層の意味論・コンテキスト宣言・整形式チェック・台帳規約を decompose.md から移した。decompose / refactor の両方から参照する。
- **受け入れ層の再設計（§6 手順3 からの変更）:** 受け入れは**挙動保存のみ**とした。
  「辞書↔実装の対応」（開発者が名前で発見できる）は受け入れ条件に昇格させない — 形式的一致は悪いモデルでも完備にできるため、リファクタリングの効能を認定できない。形式的一致は合成の突合（lint）が担う衛生に格下げした。
  これに伴い check-vocab 委譲（§8）の論点は消滅した。
- **効能の清算 = ブラインド品質レビュー:** `tdd-run/subcmds/review.md` を新設した。
  効能（理解容易性・拡張容易性・頑健性。加えて匿名の処理・処理の散在）は利用仮説「退行なし＋構造の改善」として記録し、合成の終了前にサブエージェントによるレビューで清算する。
  サブエージェントは会話コンテキストを引き継がないため、problem.md・辞書・ツリーを知らないブラインド評価が構造として保証される。
  リスク・ネガティブな指摘を必須で要求する。
  レビューは新規型でも標準で行う（問い方が比較評価 / 絶対評価に変わるだけで、評価軸は共通）。
- **§6 の骨組み:** 手順0（申し送りの対応表）・1（問い直しの調査）・2（回収と被覆確認・actor 補正）・4（前提決定）・5（発掘・移設元・残余の完備性）・6（基盤節と影響先の列挙）・7（語彙作業・メタ概念の登録禁止）・8（出口ゲート・セッション継続の確認）は概ね構想どおり。
